# Workflow Design Principles

- 문서 목적: 이 워크플로우가 무엇을 믿고 어떻게 설계됐는지를 정의하고, 각 원리를 **강제하는 검사**와 짝지어 둔다.
- 범위: 설계 원리 3층, 규칙을 쓰는 법, 운영 규율, 자기 적용(self-application)
- 대상 독자: workflow 설계자, 이 워크플로우를 도입하는 팀, AI 에이전트
- 상태: stable
- 최종 수정일: 2026-08-24
- 관련 문서: [global_workflow_standard.md](./global_workflow_standard.md), [workflow_configuration_layers.md](./workflow_configuration_layers.md)

## 0. 이 문서의 위치

`global_workflow_standard.md` 는 **무엇을 하는가**(세션 시작 순서, 상태값, 종료 절차)를
정한다. 이 문서는 **왜 그렇게 하는가**를 정한다. 새 기능·새 스킬·새 하네스를 설계할 때
판단 기준으로 삼는다.

가장 중요한 조항은 §5 다. **여기 적힌 것은 이 저장소 자신에게 먼저 적용된다.**

## 1. 무엇이 새는가

AI 와 일할 때 반복해서 새는 것은 시간이 아니라 네 가지다.

| 축 | 증상 | 대응 원리 |
|---|---|---|
| 시간 | 세션이 끝나면 맥락이 사라져 다음 세션이 같은 질문을 한다 | §2.1 상태를 세션 밖에 둔다 |
| 도구 | 도구마다 진입점·설정이 달라 복사한 규칙이 갈라진다 | §2.2 규칙은 한 벌만 쓴다 |
| 사람 | 각자의 에이전트가 각자의 맥락으로 일해 합류 지점에서 충돌한다 | §4.5 여럿이 함께 굴릴 때 |
| 품질 | "완료했습니다" 가 사실인지 아무도 확인하지 않는다 | §2.3 검사가 규칙을 지킨다 |

코드 충돌은 git 이 잡아 준다. **맥락 충돌은 아무도 잡아 주지 않는다.** 그래서 맥락을
git 이 볼 수 있는 자리에 둔다 — 그것이 §2.1 이다.

## 2. 설계 원리 3층

### 2.1 상태를 세션 밖에 둔다

세션이 끝나면 컨텍스트 창은 비워진다. 남기려면 결국 파일에 써야 하고, 파일이면
`git diff` 로 보이고 리뷰가 된다.

- 에이전트가 **세션을 열 때 반드시 읽는 자리**가 정해져 있어야 한다. 파일 이름과 위치는
  무엇이든 좋다 — 정해져 있다는 사실이 요점이다.
- 최소 세 가지를 남긴다: 지금 어디까지 왔나(`state`), 다음 세션이 무엇부터
  할까(`handoff`), 무엇을 하기로 했고 뭐가 남았나(`backlog`).
- 기억을 파일로 두면 병합·리뷰·되돌리기가 코드와 같은 방식으로 처리된다. 이것이
  §4.5 협업의 전제다.

### 2.2 규칙은 한 벌만 쓰고, 도구별로 내보낸다

**손으로 복사한 규칙은 반드시 갈라진다. 생성한 규칙은 갈라질 수가 없다.**

- 규칙의 정본은 하나다 (`global_workflow_standard.md` §1 · §3 · §8).
- 도구별 진입점(`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` …)은 정본에서 **생성**한다.
  진입점 파일에도, 렌더러 코드에도 규칙 문장을 직접 적지 않는다.
- 도구마다 다른 부분(진입점 파일 이름, 지원 기능)만 프로파일로 분리한다.
- 생성물은 손으로 고치지 않는다. 고쳐야 하면 정본을 고치고 다시 내보낸다.

> 이 원리는 2026-07-27 에 **위반 상태로 발견됐다**. 규칙 문장이 렌더러에 6벌 복제돼
> 있었고 §8 은 12개 진입점 중 2개에만 실려 있었다. 그래서 §5 의 검사를 만들었다.

### 2.3 지켜지는 규칙은 실행되는 규칙뿐이다

문서에만 적힌 규칙은 지켜지지 않는다. 검사는 세 층으로 둔다.

| 층 | 무엇을 보는가 | 언제 |
|---|---|---|
| 형식 검사 | 문서와 링크가 규약대로인가 | 빠르니까 매번 |
| 동작 검사 | 적어둔 대로 실제로 돌아가는가 | 매 push (릴리스 전량 포함) |
| 추세 관찰 | 어긋남이 늘고 있는가 | 대시보드에 숫자로 |

검사 설계 규칙:

- **커밋을 막지 않아도 된다.** 다음 세션 브리핑 첫 줄에 뜨는 것만으로 충분하다.
  강제로 막는 검사부터 만들면 팀이 검사를 우회하기 시작한다.
- **위양성을 내는 검사는 무시당한다.** 범위를 좁게 잡고, 못 잡는 것을 문서에 적는다.
- **재발 방지 검사는 결함 코드에서 실패해야 한다.** 결함을 되주입해 FAIL 하는 것을
  확인한 뒤에만 그 검사를 신뢰한다.
- **덜 본 것을 통과로 셈하지 않는다.** 읽지 못한 문서, 건너뛴 항목, 잘라낸 상한은
  결과에 드러나야 한다.

## 3. 규칙을 쓰는 법

차이는 하나뿐이다 — **검사로 옮길 수 있는 문장인가.** 옮길 수 없으면 그건 규칙이
아니라 소망이다.

| ✕ 지켜지지 않는 문장 | ✓ 지켜지는 문장 |
|---|---|
| 코드 품질을 유지한다 | 테스트가 통과하지 않으면 완료로 적지 않는다 |
| 문서를 항상 최신으로 유지한다 | 상태 문서 갱신은 같은 커밋에 넣는다 |
| 신중하게 작업한다 | 삭제·덮어쓰기 전에 대상 파일을 먼저 읽는다 |

새 규칙을 표준에 넣을 때는 **그 규칙을 검사할 방법을 같이 제안**한다. 검사할 방법이
없으면 규칙이 아니라 가이드로 분류한다.

## 4. 운영 규율

### 4.1 세션은 이렇게 열린다

1. 도구가 진입점 문서를 읽는다 — 규칙은 여기서 주입된다.
2. 진입점이 상태 파일을 가리킨다 — 어디까지 왔는지 에이전트가 스스로 읽는다.
3. 에이전트가 먼저 브리핑한다 — "지난번엔 여기까지, 다음은 이것으로 보입니다".
4. 사람은 맞다·아니다만 답한다 — 어긋났다면 작업을 시작하기 전에 잡힌다.

사람이 맥락을 설명하는 것이 아니라, **에이전트가 읽고 와서 확인을 받는다.** 브리핑이
틀렸다면 그 자체가 수확이다 — 상태 기록이 낡았다는 뜻이다.

### 4.2 하루 한 사이클

상태 문서 읽기 → 할 일과 범위 정리 → 작업 → 확인 → **메모리 → 커밋 → 푸시**.

순서가 중요하다. 커밋한 뒤에 따로 메모리를 적으면 협업자는 push 시점에 그 변경을 보지
못한다 (`global_workflow_standard.md` §8.3 안티패턴).

### 4.3 맡기기 전에 세 가지를 못박는다

- **크기** — 한 세션에 끝나고 커밋 하나로 설명되는 만큼.
- **완료 조건** — 무엇을 확인하면 끝인지 *일을 시작하기 전에* 적는다. 나중에 정하면
  결과에 맞춰 정하게 된다.
- **건드리지 않을 것** — 범위 밖을 먼저 못박는다. 에이전트는 친절해서 시키지 않은
  것까지 고친다.

### 4.4 다음 세션에 무엇을 남기나

결정과 **그 근거**, 확인한 것과 **확인하지 못한 것**, 다음 한 걸음. 형식은 자유다.

무엇을 했는지는 git 이 기억한다. **왜 그렇게 했는지는 아무도 기억하지 않는다.**
"확인 못 함" 한 줄이 다음 세션의 30분을 아낀다.

### 4.5 여럿이 함께 굴릴 때

- **갈라 둔다** — 상태 기록을 브랜치별로 나눠 두면 동시에 일해도 서로 덮어쓰지 않는다.
- **합친다** — 기억이 파일이라 병합도 리뷰도 코드와 똑같이 처리된다.
- **맞춘다** — 규칙이 정본 한 벌에서 나오므로 사람마다 다른 규칙이 생기지 않는다.

팀이 새로 외울 규칙은 하나뿐이다: **메모리 갱신은 그 작업의 커밋과 같이 올린다.**

### 4.6 얇게 시작한다

가장 자주 아픈 곳 하나 → 남길 자리 하나 → 검사 하나. 처음부터 다 갖출 필요는 없다.
다만 **셋을 다 갖추기 전에는 굴러가지 않는다** — 기록만 남기고 검사를 안 붙이면 결국
아무도 쓰지 않게 된다.

## 5. 자기 적용 (self-application)

**이 워크플로우는 스스로에게 먼저 적용된다.** 배포하는 것을 우리가 쓰지 않으면, 그것이
동작하는지 알 방법이 없다.

구체적으로 이 저장소는:

- 자기 진입점 파일(`CLAUDE.md` / `AGENTS.md`)을 **자기 렌더러로 생성해서** 가진다.
- 자기 상태를 자기 규약대로 둔다 (`ai-workflow/memory/active/<branch>/`).
- 자기 린터와 자기 session-start 가 **자기 저장소에서 통과**한다.
- 위 원리를 어긴 상태가 되면 검사가 실패한다.

### 5.1 원리 ↔ 검사 매핑

이 표의 검사 파일이 실재하는지, 그리고 이 저장소가 각 원리를 지키는지는
`tests/check_self_application.py` 가 확인한다. **표를 늘릴 때는 검사도 같이 늘린다.**

| 원리 | 강제하는 검사 |
|---|---|
| §2.1 상태를 세션 밖에 둔다 | `tests/check_branch_scoped_memory.py` |
| §2.1 상태 문서 3종이 실재한다 | `tests/check_self_application.py` |
| §2.2 규칙은 정본 한 벌에서 생성 | `tests/check_standard_single_source.py` |
| §2.2 규약이 한 곳에서만 정의됨 | `tests/check_convention_single_source.py` |
| §2.3 선언과 구현의 일치 | `tests/check_maturity_registry.py` |
| §2.3 쓴 코드와 읽는 코드가 만난다 | `tests/check_writer_reader_roundtrip.py` |
| §2.3 판정 지표는 근거를 함께 낸다 | `tests/check_metric_source_contract.py` |
| §2.3 덜 본 것을 통과로 셈하지 않는다 | `tests/check_workflow_linter.py` |
| §4.1 세션 열기가 이 저장소에서 돈다 | `tests/check_self_application.py` |
| §4.2 저장소를 오염시키지 않는다 | `tests/check_no_repo_write.py` |
| §5 자기 진입점을 자기 렌더러로 갖는다 | `tests/check_self_application.py` |

### 5.2 새 기능을 설계할 때

1. 이 문서의 어느 원리에 속하는지 정한다. 어디에도 속하지 않으면 원리부터 논의한다.
2. 그 기능이 만드는 **생성물의 정본이 무엇인지** 적는다 (§2.2).
3. 그 기능이 어겼을 때 **무엇이 실패하는지** 적는다 (§2.3). 실패시킬 방법이 없으면
   규칙이 아니라 가이드다 (§3).
4. 이 저장소에 먼저 적용한다 (§5).
