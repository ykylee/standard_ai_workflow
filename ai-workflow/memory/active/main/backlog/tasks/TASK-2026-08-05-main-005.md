## ✅ Outcome

- 작업 결과: 질문이 "무엇이 참이면 true 인가" 였는데, 답은 **그 질문이 성립하지 않았다** 였다. `transport_ready` 한 boolean 이 서로 다른 질문 셋에 답하고 있었다 — 런타임 능력(`mcp` import 가능한가) / 구현 단계(draft냐 SDK냐) / 정책(활성으로 붙여도 되나). 특히 `read_only_registry` 의 상수 `False` 는 **참/거짓을 가릴 수 있는 명제가 아니었다**: registry 는 도구를 기술하지 어느 transport 가 자기를 서빙할지 모른다. 조건을 못 적은 게 아니라 적을 수 있는 조건이 없었다. §2.39(`recorded` 가 다섯 번째 진행 상태가 아니라 *출처* 였던 건)와 같은 모양이다.
  축을 셋으로 쪼갰다 — `sdk_available`(런타임) / `transport_phase`(단계) / `apply_mode`(정책). 승격 기준이 필요한 것은 정책 축 하나뿐이고, 그것을 `check_mcp_apply_mode_criterion.py` 가 **실행** 한다: (1) 공식 `mcp` `ClientSession` 왕복 — 손수 만든 JSON-RPC 는 우리 구현끼리의 대화라 하네스 호환성을 증명하지 못한다, (2) bootstrap 이 emit 하는 command 그대로, **`mcp` extra 없는 인터프리터**에서 뜰 것.
  덤으로 자기모순 1건: `read_only_mcp_sdk.py` 의 `sdk_runtime_status()` 는 `sdk_available` 을 보고 `True`/`official_sdk_stable` 을 광고하는데, **같은 파일의 모든 tool 호출 결과**는 `transport_ready: False`/`optional_candidate` 를 박고 있었다. 그 자리는 SDK 서버가 실행 중일 때만 도달하므로 `True` 가 맞다.
- 검증 결과: 기준 실행 결과 — `jsonrpc-bridge` 는 extra 없는 인터프리터에서도 `tools/list` 13종 + `tools/call` 성공 → **`active_ok`**, `stdio-sdk` 는 `McpError: Connection closed` → `manual_review_only`(성숙도가 아니라 의존성). 되주입 2방향: stdio-sdk 를 `active_ok` 로 과대 선언 → `기준 미달 (McpError: Connection closed)` 로 FAIL, jsonrpc-bridge 를 과소 선언 → `[info] 기준을 통과했다. 승격을 검토할 것` (조용히 안 넘김). 격리 venv 전량 smoke **234/234**, mypy strict **123 files 0 errors**, MCP 관련 검사 6종 전부 PASS.
