## 🛠️ Implementation / Content

- 진행 현황: 완료.
- 설계 결정:
  - **trigger 단일**: `seed_workspace_memory.py --apply` 의 *마지막 단계*에서
    register. 다른 도구(survey 등) 는 register 하지 *않음* — register 는
    *내가 이 브랜치를 *담당* 한다* 는 의미의 산출물이고, *조회* 가 그 의미가
    되는 건 아님. survey 가 register 하면 *옛 branch 도 살아있는 것처럼* 잘못
    가시화될 수 있다.
  - **harness detection**: 등록 시 `harness` 를 어디서 가져올지. 환경변수
    `WORKFLOW_HARNESS` 가 있으면 그 값, 없으면 `hostname` (mavis/Claude Code/
    Codex 등 자동 식별 X — 그래도 registry 가 *진행 중* 정보는 가짐). env
    override 가 운영 형태.
  - **endpoint**: 자동 detect ❌ (호스트별 방언이 다양). *환경변수
    `WORKFLOW_ENDPOINT` 가 있으면* 채워 넣고, 없으면 None. *없어도* 정상.
  - **failure 격리**: register 자체가 어떤 이유로 실패해도 seed 자체는
    *성공*으로 본다. stderr 에 *advisory* 만 출력. ==register는 *부가 정보*
    이지 *플로우의 본 동작* 이 아니다. (역시 §5A.3 의 "in-flight 가시성" 이
    *일차 정보* 가 아니라 *보조*라는 정신.)
  - **idempotent**: `workspace_registry.register()` 가 이미 idempotent (동일
    path 재등록 시 last_seen_at only). 그래서 seed 가 --force 와 함께 재호출
    되어도 entries 1건 유지.
  - **`--no-register`**: 사용자가 명시적으로 off. 테스트 / CI env / registry
    가 *없어야 하는* 환경 (예: 회사 정책) 용.

- 비범위:
  - 다른 호스트에서 cross-host 발견 (registry 와 동시 — 다음 사이클).
  - endpoint 자동 detect (방언 다양).
  - survey 가 stale 한 branch 정리 시 registry 자동 unregister (별도 task).
