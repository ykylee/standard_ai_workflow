- 결정 사항 (사용자 채택, 2026-08-08 22:31 KST):
  - **Federation 모델** (central store ❌, git-tracking ❌). 정공법 4가지 후보 중:
    1. ❌ Central server (redis/postgres) — 항상-on infra 필요
    2. ❌ Git-tracked — §5A.3 의 "git 밖" 원칙 위반 (in-flight 정보는 per-host)
    3. ❌ S3/GCS — 외부 의존성 추가
    4. ✅ **Federation** — 각 호스트의 host-scoped file 유지 + 호스트 목록 별도 관리
  - **known_hosts.json 위치**: `~/.cache/workflow_kit/known_hosts.json` (atomic, 0o600, `WORKFLOW_KNOWN_HOSTS_PATH` env override)
  - **endpoint 형식**: `http://<host>:<port>/registry.json` 또는 `file://<path>`. registry 의 *endpoint* field 와 다른 점: endpoint 는 *entry-level* (한 워크스페이스), known_host 의 endpoint 는 *host-level* (그 호스트의 registry 위치).
  - **merge key**: `(source_host_id, path)`. 같은 path 가 다른 호스트에 있으면 둘 다 보존 (다른 physical worktree 가능).
  - **conflict resolution**: same `(source_host_id, path)` 이면 `last_seen_at` 최신 우선. 그 외 *first-wins* (정렬 순서 = 입력 순서).
  - **HTTP pull 본 task 범위 ❌** — `merge_entries()` API 만. HTTP fetch + dashboard 통합은 TASK-016.
