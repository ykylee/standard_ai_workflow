### harness — 숫자가 아니라 정의가 문제였다

`HARNESS_SPECS` 는 13, `maturity_matrix.harnesses.supported` 는 11. 처음엔
`mavis` 가 matrix 에서 빠진 **drift** 로 보고 추가했다. 그러자
`check_harness_v0_15_9` 의 *3-way set equality* 가 깨졌다 —
`harnesses/mavis/` 디렉터리가 없기 때문이다.

거기서 진짜 사실이 드러났다: **`mavis` 는 project-local 산출물이 0 인 harness** 다
(표준 §6.5.2 의 글로벌 `mcp.json` merge 만 emit, v1.1.0 TASK-007). 디렉터리가
없는 것이 **설계** 다. `custom` (자사 harness wire-up 어댑터 템플릿)도 같은 부류다.

즉 `harnesses.supported` 는 *overlay 를 배포하는* harness 목록이고 파일시스템과
1:1 이다. 11 이 맞다. matrix 를 원복하고, 그 정의를 `NON_OVERLAY_HARNESSES` 에
**이유와 함께** 선언했다.

### 검사가 하드코딩에 갇혀 있었다

`test_case_5_harness_supported_ssot_alignment` 는 이름이 "SSOT alignment" 인데
`EXPECTED_BANNER_HARNESSES` **10개 하드코딩 목록** 과만 비교했다. 그래서
**새 harness 가 추가돼도 몰랐다** — `grok-build` / `mavis` 가 늘어나는 동안 6/6
PASS 였다. 기대값을 `HARNESS_SPECS − NON_OVERLAY_HARNESSES` 로 바꿔 정본에서
유도하게 했다. 제외 항목에 이유가 없으면 그 자체를 실패로 본다.
