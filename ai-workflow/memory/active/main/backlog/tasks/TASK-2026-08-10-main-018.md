- 작업 내용: 테스트/CI 가 느리다는 요청에서 출발. 측정으로 병목이 하나임을 확인했다 —
  **CI job 604s 중 smoke 실행이 576s** (install 19s / checkout 3s 는 이미 최적).
  `run_all_checks` 는 267개 check 를 **순차** 실행한다. 시간 분포는 극단적이라
  (상위 13개가 50%, 하위 133개 합계 9.8s) 개별 최적화보다 병렬화가 압도적이다.
  8-way 프로토타입 실측: **345s → 69.8s (4.9배)**.

  그런데 병렬 실측이 **사전 존재 결함** 을 드러냈다. 3개 check 가 "경로 부재" 로
  깨졌는데 조사 후 저장소는 깨끗했다. 전후 비교 전수 조사는 0건 — 전부 스스로
  복구하기 때문이다. 실행 *중* 을 5ms 폴링으로 감시해 범인을 지목했다:
  **`check_source_without_runtime_layer` 가 원본 저장소의 `ai-workflow/` 를 통째로
  rename** 해 숨겼다가 `finally` 로 되돌린다.

  그 사이 저장소에는 `ai-workflow/` 가 **없다**. 병렬 실행이 깨지는 것은 증상일
  뿐이고, 진짜 문제는 둘이다:
  1. `finally` 는 **SIGKILL 에 돌지 않는다.** runner 의 timeout 처리는 프로세스
     그룹에 SIGTERM → SIGKILL 을 보내므로, 최악의 경우 저장소에 `ai-workflow/` 가
     사라진 채 남는다.
  2. CLAUDE.md 는 "여러 에이전트가 함께 일할 수 있다" 를 전제한다. 다른 에이전트나
     사용자가 그 순간 `ai-workflow/` 를 읽으면 실사고다.

- 완료 기준: 원본 저장소를 건드리는 check 가 없고, 전량 검사가 병렬로 돌며(기본
  auto), `--jobs 1` 이 기존 직렬 동작과 동일하고, 병렬 안전이 검사로 고정된다.

## 🛠️ Content

- **`run_all_checks --jobs`** (기본 `auto` = min(코어, 8)). `--jobs 1` 은 **기존 순차
  경로 그대로** 다 — 병렬 경로를 1-worker 로 돌려 대신하지 않는다. 재현이 필요할 때
  옛 동작과 한 치도 달라선 안 되기 때문이다. 결과는 완료 순서가 아니라 discover
  순서로 정렬한다 (출력이 타이밍에 흔들리면 두 실행을 비교할 수 없다).
- **정숙 구간** — 저장소 전역 상태를 관찰하거나 실파일을 임시 조작하는 check 는
  병렬 구간이 **완전히 끝난 뒤** 직렬로 돈다. 소속은 runner 안의 목록이 아니라
  check 파일 안의 `REQUIRES_QUIET_REPO = True` 선언으로 둔다 (§2.53 — 목록은 파일에서
  멀어지면 드리프트한다). 판정은 AST 라 주석·문자열 언급에 속지 않는다.
- **`check_source_without_runtime_layer` 격리** — 원본 `ai-workflow/` 를 rename 해
  숨기던 것을 **저장소 사본**(0.5s, ~41MB) 검증으로 교체. `.git` 은 복사한다
  (`check_handoff_git_integration` 이 실제 히스토리를 요구). 원본 무손상 계약을
  파일 끝의 (실행되지 않는) test wrapper 가 아니라 **실행 경로에서** assert 한다.
- **`check_parallel_smoke.py` 8 case 신설** — jobs 해석 / 마커 AST 판정 / 정숙 구간
  비어있지 않음 / 분류 보존 / 배타성 / **실제 동시 실행(벽시계<합계)** / 직렬·병렬
  판정 일치 / 정숙이 병렬 뒤.
