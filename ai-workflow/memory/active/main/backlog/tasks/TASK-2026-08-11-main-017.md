## 2챕터 — 4 FAIL fix (done, 2026-08-11)

**4건 전부 같은 뿌리였다** — 1챕터가 (3)(4) 를 "별도 분석 필요" 로 분류한 건 증상만
보고 나눈 것이고, 실제로는 macOS 에서 `/var`·`/tmp` 가 `/private/...` 로 가는
symlink 라는 단일 원인이다. production 코드는 **정규 경로(resolve 결과)를 방출하는
쪽이 옳고**, 검사가 `mktemp` 의 raw 경로와 string 비교를 한 것이 결함이다. 따라서
처방은 넷 다 **검사 fixture 를 정규 경로로 맞추는 것**이고 production 코드는 무수정.

| 검사 | 처방 | 결과 |
|---|---|---|
| `check_branch_resolver_agreement` | 비교 양쪽을 `.resolve()` 로 통일 | 5/5 PASS |
| `check_branch_scoped_memory` | `relative_to` 기준인 `active` 를 `.resolve()` | 10/10 PASS |
| `check_git_conflict_resolver_v0_11_24` | case 4 의 fixture `td_path` 를 `.resolve()` | 8/8 PASS |
| `check_workflow_state_refresh_hint` | fixture `root` 를 `.resolve()` (기대값 10개가 여기서 파생) | PASS |

- (3) 의 실제 원인: 도구가 `conflicts[].file_path` 를 resolve 해 돌려주는데 검사는 raw
  경로와 비교. 같은 파일의 `source_context.files` 는 raw 를 그대로 되울려서 **한 응답
  안에 두 표기가 공존**한다 — 그래서 case 5 는 통과하고 case 4 만 실패했다.
- (4) 의 실제 원인: fixture `root` 가 raw 라 기대값 10개 전부가 raw 로 조립됐고,
  helper 는 resolve 된 경로를 돌려줬다.
- **성격**: 기능 회귀가 아니라 **검사의 플랫폼 이식성 결함**이다. Linux CI 에서는
  `/tmp` 가 symlink 가 아니라 영영 안 드러난다 — darwin homelab 검증이 아니면 못 찾는
  종류이고, 이것이 이 task 의 실제 수확이다.

## 4챕터 — state.json ↔ 생성기 갈라짐 해소 (done, 2026-08-11)

3챕터에서 state.json 을 정본 생성기(`generate_workflow_state.py`)로 갱신해 봤더니
**유지되던 문서와 출력이 갈라졌다**. 아무도 생성기를 돌리지 않아 드러나지 않던 드리프트다.

| 갈라짐 | 원인 | 처방 |
|---|---|---|
| `session.in_progress_items` 에 `"(없음 — …)"` 산문이 **작업 항목으로 유입** | handoff §2 를 손으로 산문 처리했는데, 도구의 빈 목록 관례는 **빈 bullet `-`** 다 (§3 은 이미 관례를 따르고 있었다) | handoff §2 를 관례로 통일 — **production 무수정** |
| `backlog.planned_items` | `workflow-source` 전체에 **0건** (코드·테스트·릴리스 노트·템플릿 모두). 이 파일에만 있던 유령 키 | 제거 |
| `session.recent_done_items` 16건 | 생성기는 `RECENT_DONE_ITEMS_CAP=10` 으로 자른다. handoff §4 에는 같은 상한이 강제되는데 state.json 만 비대칭이었다 | 10건으로 정합 (밀려난 항목은 backlog `done_items` 와 task 파일에 보존) |

- **택하지 않은 길**: `is_meaningful_text` 에 "(없음…)" 류를 거르는 heuristic 추가.
  어떤 산문이 "없음" 인지 추측하는 코드가 되고, 저장소의 **"모름 ≠ 안전"** 원칙과
  어긋난다. 도구가 이미 가진 관례를 문서가 따르게 하는 쪽이 옳다.
- **대조 결과**: 기계 판독 필드 6종(`session`/`backlog` 의 in_progress·blocked,
  recent_done 길이, task_count) 이 생성기 출력과 **전부 일치**, 유령 키 소멸.
- **잔여 (소유자 결정 대상)**: `recent_done_items` 의 **산문 표현과 정렬 순서**는 여전히
  다르다 — 생성기는 task H1 제목 + 날짜 키 정렬, 유지본은 상세 요약 + 손 정렬.
  결함이 아니라 **"state.json 을 생성물로 볼 것인가, 손 문서로 볼 것인가"** 의 문제다.
  생성물로 정하면 요약 산문은 handoff §4 와 task 파일에 두고 state.json 은 인덱스로
  낮춘다. 손 문서로 정하면 생성기를 이 저장소의 state.json 에 쓰지 않는다고 명시해야
  한다. **지금은 어느 쪽도 명시돼 있지 않아 다음 사람이 또 밟는다.**
