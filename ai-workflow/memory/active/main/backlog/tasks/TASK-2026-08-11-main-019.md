  서로의 정숙 구간을 침범한다. **결과가 조용히 거짓이 된다** — 그 실행의 PASS 도
  FAIL 도 근거로 쓸 수 없다.

- 처방 방향: `run_all_checks.py` 진입에서 **워킹 트리 루트 기준 배타 락**. 이미
  잡혀 있으면 보유자 정보(pid / 시작 시각 / 브랜치)를 찍고 **즉시 실패**.
  선례가 이미 저장소 안에 있다 — `url_validity.py:858` (ADR-015):
  `fcntl.flock` advisory lock + sidecar `.lock` + stale 정리 + Windows no-op.

- 설계 요점 (착수 시 재검토):
  - **락 위치는 저장소 밖** — `.git/` 안이 자연스럽다 (git 이 이미 무시, worktree
    별로 갈림). 저장소 안에 두면 `check_no_repo_write` 가 그 락 파일을 오염으로 잡는다.
  - **stale 판정은 PID 생존 확인** — url_validity 의 24h 임계는 캐시용이라 전량
    검사(수 분)에는 너무 길다. 죽은 프로세스의 락이 다음 실행을 몇 시간 막으면 안 된다.
  - **획득 실패 시 조용히 진행 금지** ("모름 ≠ 안전"). `--no-lock` 탈출구는 두되 기록.
  - **3층 방어** — 규약(`CLAUDE.md`) + 도구 락 + 되주입 검사 (`--force` 때와 동형).

- **알려진 한계 (미리 명시)**: 세마포는 **도구를 거치는 쓰기만** 막는다. 에이전트가
  파일을 직접 편집하면 (2026-08-11 에 task 파일 `status` 가 두 번 되돌아간 사례)
  OS 락은 아무것도 못 한다. 그 층까지 실효를 가지려면 락이 아니라 **워크스페이스
  분리**(에이전트마다 worktree)가 정공법이고, 세마포는 그 위의 안전망이다.

- 완료 기준: 동시 2 runner 에서 두 번째가 명시적 실패 + 보유자 정보 출력 / 죽은
