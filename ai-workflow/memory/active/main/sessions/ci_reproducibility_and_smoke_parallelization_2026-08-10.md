## 1. 무엇이 있었나

세션은 "원격 최신 상태 확인" 으로 시작했는데, `gh run list` 가 **smoke 15연속 red**
를 보여줬다. 그런데 직전 세션의 handoff 는 내내 "전량 검사 green" 을 기록하고 있었다.
로컬과 CI 가 다른 것을 재고 있었다는 뜻이고, 이 세션의 나머지는 전부 그 한 문장에서
파생됐다.

## 2. TASK-016 — 15연속 red 의 정체

`smoke` 의 두 매트릭스 셀 중 `slash` 하나만 red 였다 (`native` 는 내내 PASS).
`slash` 는 `CODEX_WORKFLOW_BRANCH=feature/ci-slash-probe` 를 강제하는데 그 브랜치의
`state.json` 은 존재하지 않는다. 게이트(`cmd_validate` state)는 부재를 **정당한 통과**
로 설계했지만, `check_release_pre_check_gates` case 7 만 살아있는 저장소를 읽어
`generated_at` 을 요구했다 — **결함은 게이트가 아니라 검사였다.**

- case 7 을 되주입 블록으로 옮겨 결정적으로 만들고, 환경 의존은 7b 로 분리해
  **명시적 SKIP** 을 출력하게 했다 (모름 ≠ 안전).
- **case 11 신설** — 부재가 정당한 통과라는 계약을 *아무도 재고 있지 않았다*.
  그래서 case 7 의 오인이 드러날 자리가 없었다.
- 총계 고정을 하한이 아니라 계산식으로 (하한은 case 삭제를 놓친다).

## 3. TASK-017 — 근본은 재현 수단의 비대칭

TASK-016 은 red 를 껐지만 재발은 못 막는다. 뿌리는 **CI 는 두 컨텍스트를 돌고 로컬은
하나만 돈다**는 비대칭이었다. 저장소가 이미 아는 모양이다 — `mcp` SDK 매트릭스와
같고, 처방도 같다: 정본을 한 곳에 두고 CI 와 로컬이 그것을 읽는다.

`branch_matrix.py` 정본 + `run_all_checks --branch-context=<label|all>` +
smoke.yml 의 prepare job 주입 + `check_branch_context_matrix` 8 case + CLAUDE.md 관행.

**새 축이 첫 실행에서 결함 2건을 잡았고, 하나는 자기 자신의 것이었다.**
`--branch-context=native` 가 상속된 `CODEX_WORKFLOW_BRANCH` 를 지우지 않아,
`all` 의 slash 패스 안에서 native 를 요청하자 slash 결과가 나왔다 — *요청한 것과 다른
축을 재고 통과를 보고하는*, 이 작업이 막으려던 실패 양상 그 자체다. 선언이 아니라
end-to-end 를 재게 한 판단이 값을 했다.

## 4. TASK-018 — 병렬화

측정이 병목을 하나로 좁혔다: **CI job 604s 중 smoke 실행이 576s** (install 19s /
checkout 3s 는 이미 최적). 267개의 시간 분포는 극단적이라 (상위 13개가 50%, 하위 133개
합계 9.8s) 개별 최적화보다 병렬화가 압도적이었다.

- `--jobs auto` (기본), `--jobs 1` 은 기존 순차 경로 그대로
- **정숙 구간** — 저장소 전역을 관찰하는 check 는 병렬 뒤 직렬. 소속은 runner 의
  목록이 아니라 파일 안의 `REQUIRES_QUIET_REPO` 선언 (§2.53)
- `check_source_without_runtime_layer` 가 원본 `ai-workflow/` 를 rename 해 숨기던 것을
  사본 검증으로 교체 — **`finally` 는 SIGKILL 에 돌지 않는다.** 최악의 경우 저장소에
  `ai-workflow/` 가 사라진 채 남을 수 있었다.

**CI 실측: smoke 576s → 220s, job 604s → 245s.**

## 5. TASK-019 — 테스트가 저장소를 건드리고 있었다

병렬화가 사전 결함을 드러냈다. 네 검사가 **원본 저장소**에 `--apply` 를 돌린 뒤
되돌려 왔다 — `pyproject.toml` 의 version 을 `99.99.99` 로 바꾸거나, README/`__init__`
에 drift 를 주입하거나, memory_index/wiki 를 갱신하거나, 실빌드 산출물을 만든다.

되돌리므로 `check_no_repo_write` 의 전후 비교는 통과했다. 그러나 CLAUDE.md 는
"여러 에이전트가 함께 일할 수 있다" 를 전제한다 — 그 사이 다른 에이전트가 버전을
읽으면 99.99.99 를 본다.

`_repo_sandbox.py` 로 넷 다 사본에서 돌게 하고, 원본 무손상을 **실행 경로에서**
assert 하게 했다. 정숙 구간 9 → 3.

**성능 이득은 사실상 0이다** — 병렬로 옮겨간 25초를 사본 복사 비용이 먹었다.
착수 전 예상대로이며 값어치는 속도가 아니라 협업 안전이다.

## 6. 교훈

- **로컬에 없는 축은 반드시 갈라진다.** CI 에만 있는 매트릭스는 로컬 재현 수단을
  주지 않으면 "로컬 green + CI red" 를 만든다. 이번엔 열흘 가까이 갔다.
- **변하지 않는 지표는 자기 소비자의 결함도 숨긴다** (직전 세션의 hit_rate 교훈과
  같은 모양). 아무도 안 재는 계약(state 부재 통과)이 있으면 그 자리의 오인은
  드러나지 않는다.
- **전수 폴링은 후보를 좁히는 데만 쓰고 단독 실행으로 확정한다.** 전수 조사가 6건을
  지목했지만 2건은 오귀속이었다 — 짧은 check 라 폴링이 읽는 "현재 이름" 이 전환
  순간에 어긋났다. 재검증 없이 갔다면 멀쩡한 검사 2개를 불필요하게 직렬화했을 것이다.
- **되돌리는 것은 안 건드리는 것이 아니다.** 전후 비교로 통과한다고 안전한 게 아니다.
