## 3. 가장 중요한 발견 — 정상으로 보이던 하나도 우연이었다

전수검사에서 렌더러 32개 중 **1개만** 스크립트를 가리켰다 (`render_goose_config`).
그런데 그것조차:

- 설계 의도가 아니라 **goose config 형식이 command 문자열을 요구**해서 어쩔 수 없이
  그렇게 된 것이었고,
- 가리키는 경로 `ai-workflow/skills/.../run_*.py` 는 **bootstrap 이 만들지 않는다.**

즉 **12개 하네스 전부**에서 실행 경로가 없었다. 확인해 보니:

| 층 | 배포 | 실태 |
|---|---|---|
| 규약 `global_workflow_standard.md` | ✅ | 정본·추출·강제 모두 있음 |
| 구현 `workflow_kit` (`workflow_writes.py`) | ✅ pip | **계약이 여기 산다** |
| skill 스크립트 | ❌ | 패키지에도 번들에도 없음 |
| `wk` CLI | ✅ | 68개 중 해당 기능 **0개** |

`pyproject.toml` 주석은 "bootstrap 이 복사한다" 고 적어 두었지만 **사실이 아니었다.**
그 거짓 전제가 구현을 배포되지 않는 자리에 두어도 된다고 믿게 만든 출처다.

**에이전트가 메모리 문서를 손으로 쓴 것은 규율 부족이 아니라 다른 선택지가 없어서였다.**
그리고 손으로 쓰는 순간 `workflow_writes.py` 의 계약(빈 목록은 빈 bullet `-`, 상한 10,
index block 모양)은 한 번도 적용되지 않았다.

## 5. 교훈

- **이동의 참조 지도를 `read_text` 만으로 뜨면 부족하다.** TASK-021 에서 그렇게 분류해
  "내용을 읽는 검사 0건" 이라 보고했는데 틀렸다. **모듈 로드**(`spec_from_file_location`)
  와 **소스 문자열 스캔**이 같은 결합이고, 전량 검증이 그것을 잡았다.
- **정본·추출기·스냅샷은 한 커밋 안에서 같이 움직인다.** TASK-022 에서 `StandardRules`
  에 필드를 추가하며 **스냅샷 fallback 생성자**를 놓쳤다. 정본 파일이 없는 환경에서만
  실행되는 경로라 평소엔 안 밟는다 — mypy strict 가 아니었으면 **배포처에서만** 터졌다.
- **task 를 열거나 닫을 때 3문서(backlog/handoff/state.json)를 동시에 맞추지 않으면
  그 자체가 red 를 만든다.** 이 세션에서만 세 번 반복됐다. TASK-018 이 닫히면
  `state.json` 이 생성물이 되어 이 계열 실수 하나가 구조적으로 사라진다.
- **동시 작업 사고** — 다른 에이전트가 같은 워킹 트리에서 같은 task 를 병행했다
  (`~/tmp/run_all_checks_2chap_macOS_*` 4건). 증상: task 파일 `status` 상호 덮어쓰기,
  전량 검사 2개 동시 실행으로 **정숙 구간 상호 침범**. 후자는 `REQUIRES_QUIET_REPO`
  6검사의 전제를 깨서 **그 실행의 PASS 도 FAIL 도 근거로 쓸 수 없다.** → TASK-019.
- **게이트를 파이프에 넣으면 exit 이 덮인다** — `| tail -40` 으로 exit code 가 `tail`
  의 0 이 됐다. 저장소가 TASK-006 에서 이미 기록한 함정을 그대로 재현했다.
