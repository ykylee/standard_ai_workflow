## 어떻게 시작됐나

발표자료를 다듬다가 사용자가 물었다 — **"우리 워크플로우가 실제로 이 자료대로 동작하는지
상세하게 리뷰해보자."** 덱의 주장을 하나씩 저장소와 대조했고, 원리(문서에 적힌 것)는
대체로 맞았지만 실행(실제로 그렇게 도는가)이 상당 부분 어긋나 있었다.

가장 아팠던 세 가지:

1. 덱 11·12번 "규칙은 한 벌만 쓰고 도구별로 내보낸다" → **원본이 없었다.** 규칙 문장이
   렌더러 f-string 에 6벌 복제돼 있었고 정본을 아무도 읽지 않았다.
2. 덱 17번 "세션은 이렇게 열린다" → **이 저장소에서 실행되지 않았다.** 루트 진입점이
   없고 handoff 가 없어 `session-start` 가 `missing_required_document` 로 죽었다.
3. 덱 23번 "PR에 코드와 인계 노트가 같이 올라온다" → 최근 20커밋 중 동반 0건.

## 판단 기록

**왜 스냅샷을 두기로 했나.** 정본은 마크다운 하나여야 하는데, bootstrap 은 wheel 설치
환경에서도 돌고 그때는 `core/` 가 없어 `SOURCE_ROOT is None` 이다. 파일을 못 읽으면
규칙이 통째로 빠지는데, 조용히 빠지면 그게 바로 우리가 고치려던 결함이다. 그래서
"파일 우선, 없으면 스냅샷" 으로 하고 **스냅샷↔정본 동치를 검사로 강제**했다. 스냅샷은
사본이 아니라 생성물이다.

**왜 검사가 렌더러를 직접 호출하지 않고 bootstrap 을 돌리나.** 렌더러가 옳아도 배선이
빠지면 파일에는 안 실린다. 이 사이클에서 반복해 샌 곳이 정확히 그 조립 단계였다
(§2.21~§2.25). 그래서 temp 에 실제 bootstrap 을 돌려 산출물을 본다.

**왜 배포본 21개를 전부 덮었나.** 사본 쪽에만 있는 내용이 있는지 먼저 확인했다 — 없었다.
전부 순수 stale 이었고, `global_workflow_standard.md` 는 §8 이 통째로 빠진 채 2개월
방치돼 있었다. 진입점이 "표준 문서" 로 가리키는 것이 그 사본이다.

**왜 kind 를 generic 으로 바꿨나.** `--kind session` 으로 등록했더니
`check_appendonly_memory_layout` 이 `sessions/<stem>.md` 매핑을 요구했다. 그런데 기존
항목은 전부 `[generic]` + `sessions/` 문서 조합으로 운영돼 왔다. 관행에 맞췄다.
(`[session]` kind + `source: [[...]]` 는 마이그레이션 시기 형식으로 보인다.)
