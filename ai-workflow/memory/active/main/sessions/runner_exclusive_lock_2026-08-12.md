## 요약

두 에이전트가 같은 워킹 트리에서 전량 검사를 동시 실행하면 정숙 구간이 서로
침범되어 **그 실행의 PASS 도 FAIL 도 근거가 못 된다** (2026-08-11 실측). 이제
runner 진입에서 워킹 트리 배타 락을 잡는다.

| 설계 | 내용 |
|---|---|
| `RunnerLock` (`fcntl.flock`, 선례 ADR-015) | 계쟁 시 보유자 정보 (pid/시작시각/브랜치/argv) 출력 후 즉시 exit 2 — 조용히 진행 금지 |
| 락 위치 `.git/run_all_checks.lock` | 워킹 트리에 두면 `check_no_repo_write` 가 오염으로 잡는다. worktree 는 gitdir 추적, 비-git 루트는 경로 해시 temp |
| stale 원천 해소 | flock 은 프로세스 종료 시 커널이 해제 — 죽은 보유자의 락이 다음 실행을 막을 수 없다 (PID 생존 판정 불요, task 의 설계 요점을 착수 검토에서 단순화) |
| 재진입 승계 | runner 를 부르는 검사(parallel_smoke 등)의 자식 runner 는 env 마커로 부모 락 승계 — flock 은 fd 단위라 마커 없인 자기 부모도 못 뚫는다 |
| `--no-lock` 탈출구 | 진행하되 stderr 에 크게 기록 ("모름 ≠ 안전") |
| unlink 안 함 | 삭제/재생성 경쟁이 서로 다른 inode 의 락을 쥐여 줄 수 있다 — 내용은 정보용으로 잔류 |
