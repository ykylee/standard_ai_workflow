## 1. 잰 단위가 틀렸다 — main-009

51차는 "플러그인 스킬 4종이 인벤토리엔 있고 세션엔 없다" 를 놓고 가설 4개를 기각했다.
그중 하나가 **세션보다 늦은 설치**였고, 설치 시각을 *대화(session)* 시작 시각과 대조해
"설치가 21시간 앞선다" 며 기각했다.

그 기각이 틀렸다. **로드 단위는 대화가 아니라 프로세스다.** `/clear` 는 대화만 새로 열고
프로세스는 그대로 산다. 52차의 대조 실험이 축을 갈랐다 — 같은 cwd 에서 `claude -p`(새
프로세스)를 띄우면 4종이 전부 떴고, 실행 중이던 대화형 세션에서는 하나도 안 떴다.
호스트 프로세스는 설치보다 **35시간 먼저** 시작해 있었다. 이름 충돌도 매니페스트 파손도
아니었다. 53차가 재시작 뒤 실제 호출로 확증했다.

> **세션은 프로세스의 대리값이 아니다.** 값싼 방증 하나: 실행 중 프로세스의 버전과
> `<cli> --version`(새 프로세스)이 어긋나면 그 프로세스는 이미 디스크보다 낡았다.

그래서 이 조건을 `declared_unmeasured` 에서 **측정으로 옮겼다** — `wk doctor` 의
`runtime_load` 절(탐침 6→7절). 설치 시각(선언 기록 우선, 없으면 사본 mtime — 어느 쪽을
봤는지 결과에 남긴다)과 실행 중 호스트의 시작 시각을 대조한다. 시작 시각은 `ps` 의
`etime` 에서만 읽는다. `lstart` 는 **로케일로 번역**되어 파싱이 호스트마다 갈린다
(이 호스트: `2026년 8월 16일 일요일 …`).

남는 미측정은 그 **뒤 한 칸**이다 — 재시작이 최신이어도 실제 노출은 호출로만 재진다.

## 2. 갱신이 보고를 나쁘게 만들었다 — main-010

§7.0.2 의 채널별 재실행 계약 표는 **전부 같은 버전**(1.2.0 = 1.2.0)에서 실측된 것이라
"버전이 실제로 다를 때" 셀만 비어 있었다. v1.3.0 발행으로 처음 그 상태가 생겨 실측했다.

| 실측 | 결과 |
|---|---|
| 맨 이름 `plugin update <name>` | **rc 1 `Plugin not found`** — `install` 은 맨 이름을 받는데 `update` 는 `<plugin>@<marketplace>` 를 요구한다 |
| `marketplace update` 선행 | 불필요 — `plugin update` 가 클론을 스스로 당긴다 |
| 당겨오는 것 | **태그가 아니라 브랜치 팁** — 설치된 `1.3.0` 의 sha 는 v1.3.0 태그가 아니었다 |
| 옛 버전 디렉터리 | 남는다 (`1.2.0` 과 `1.3.0` 공존) |
| 반영 시점 | CLI 자신이 `Restart to apply changes` 라고 말한다 |

세 번째가 gap 3 의 교훈을 **소비자 쪽에서** 되살린다 — 같은 `1.3.0` 문자열이 시점마다
다른 내용을 가리킨다.

그리고 실측이 탐침 결함을 드러냈다: **갱신에 성공한 직후 발견이 6→8건으로 늘었다.**
`content_drift` 와 `runtime_load` 가 `installed_plugins.json` 의 `installPath` 선언을
안 읽고 glob 매치를 전부 동등한 설치로 셌다. 아무도 안 읽는 잔재가 드리프트로 보고되고
(`installed_version` 도 옛 버전을 말했다) 같은 발견이 사본 개수만큼 복제됐다.

**하네스는 어느 것이 설치본인지 이미 선언하고 있었다.** 안 읽고 있었을 뿐이다 —
MEM-2026-08-20-001 의 *"있는가" 가 아니라 "어느 것인가"* 가 세 번째로 같은 모양이다.
선언이 없는 채널은 glob 전부를 설치로 보되 **폴백임을 결과에 남긴다**. 옛 사본은
지우지도 숨기지도 않고 `superseded` 로 남긴다. 교정 후 8→6.

부수: 되주입 4종째(비교 쪽 `resolve()`)가 물지 않아 **도달 불가능한 분기**임이 드러났고
제거했다 — `probe` 가 `home` 을 이미 resolve 하는 한 밟을 수 없다.

## 3. 표기를 바꾸면 파서가 조용히 갈린다 — task SSOT 4단계

`TASK_FIELD_LABELS` 17개를 영어로 뒤집었다. `TASK_FIELD_ALIASES` 는 남긴다 — 기존 task
파일 160여 개가 한국어 표기다. 순서가 계약이었다: 두 표기를 아는 리더가 v1.2.x 로
소비자에게 먼저 갔고(3단계), 그 뒤에 쓰는 쪽을 바꾼다.

전환이 **레지스트리 밖 리터럴 4곳**을 드러냈다:

1. `BacklogParser` 의 잘못된 상태 형식 경고가 `- 상태:` 로만 발화.
2. `detect_confirmation_fields` 가 누락 필드 이름을 한국어 리터럴로 보고.
3. `merge_task_file` 이 상태 라벨을 리터럴로 써서 `render_task_file` 과 표기가 갈렸다.
4. **`_BODY_STATUS_LINE_RE` 가 `^- 상태:` 만 매칭.** 영어 표기 파일에서 본문 상태 줄이
   안 지워져 합성한 frontmatter 줄보다 **뒤에** 남고, 파서는 뒤에 오는 값을 쓴다 —
   **문서화된 "frontmatter 가 이긴다" 가 뒤집힌다.** 실증: frontmatter `done` + 본문
   `- Status: in_progress` → `in_progress`. 전환 후 새로 쓰이는 모든 task 의 상태가
   `state.json` 에서 조용히 틀렸을 것이다.

②는 `case 8`·`case 9` 를 **둘 다** 통과했다 — 그 그물이 `- 라벨:` 콜론 모양만 보는데
이 자리는 라벨 이름만 들고 있었다. **그물의 모양이 곧 주장의 범위다.**

그리고 **검사 3종·18곳이 그 시점 상수를 리터럴로 인코딩**하고 있어 전환하자 red 였다.
동작은 내내 옳았다. 전부 계약 파생으로 교정했고, `check_task_multivalue_fields` case 9
의 분모도 두 표기로 넓혔다 — 한국어만 세면 새로 쓰이는 파일이 분모에서 빠진다.
`check_task_ssot_source` 의 총계 `"10/10"` 리터럴도 세어서 내도록 고쳤다.

종단 검증은 **이 task 자신**으로 했다. 한국어로 적힌 문서를 새 표기 도구로 close 하면
**건드린 줄만 영어로 다시 쓰이고 나머지는 한국어를 보존한다** — 안 시킨 줄까지 다시
쓰면 갱신 하나가 문서 전체를 흔들어 diff 가 못 읽게 된다.
