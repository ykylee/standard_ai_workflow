## 0. 왜 "바꾸기" 가 아니라 "바꿀 수 있게" 인가

라벨(`- 상태:`)은 장식이 아니라 **파싱 계약**이다. 그래서 순서가 정해져 있다:

1. **리더가 두 표기를 모두 받는다** ← 이번 단계
2. 그 다음 release 에서 정본 라벨을 영어로 바꾼다

반대로 하면 — 쓰는 쪽을 먼저 바꾸면 — **소비자 저장소의 옛 리더가 새 문서를 못
읽는다.** 저장소의 deprecation 규율(1 release 경고 → 다음 release 제거)이 그대로
적용되는 자리다. 그래서 이번 단계는 전환을 **하지 않는다**.

## 1. 리터럴이 46곳에 흩어져 있었다

조사: 12개 라벨이 `backlog_update` / `workflow_writes` / `read_only_bundle` 에 46곳.
흩어진 채로는 바꿀 수가 없다 — 한 곳만 고치면 나머지가 조용히 갈라지고, 그 갈라짐은
**"필드가 사라진 문서"** 로 나타난다.

`project_docs` 에 정본 두 표를 뒀다:

- `TASK_FIELD_LABELS` — 의미 key → **현재 쓰는** 라벨
- `TASK_FIELD_ALIASES` — 읽을 때 **받아들이는** 표기들 (영어 표기를 미리 넣어 뒀다)

원칙은 **찾기는 넓게, 쓰기는 좁게**다. 옛 표기·영어 표기로 적힌 줄도 찾지만, 쓸 때는
언제나 정본 표기 하나로 쓴다.

## 2. 정본이 하나라는 것을 어떻게 증명하나

case 6 이 그 증거다 — **표를 바꾸면 산출물이 따라 바뀐다.** 정본을
`Completion criteria` 로 바꾸고 옛 표기 줄에 적용하면, 찾기는 별칭으로 되고 결과는
새 정본으로 쓰인다. 이 case 가 없으면 "정본을 모았다" 는 주장에 근거가 없다.

case 8 은 그 반대 방향이다 — **렌더 경로에 라벨 리터럴이 남아 있지 않은가**를 AST 로
훑는다 (docstring·주석은 설명이므로 제외). 실제로 세 번에 걸쳐 잔여 리터럴을
지목했고, 마지막 하나는 **읽는 비교**였다:

```python
if any(line.strip() == "- 작업 내용:" for line in existing_lines):
```

영어 표기로 적힌 문서에서는 이 비교가 항상 거짓이라, "비어 있으니 채운다" 분기가
조용히 안 돈다. `is_empty_label_line(line, "summary")` 로 바꿨다.

## 3. 되주입

별칭 인식을 무력화하자 case 4·5·6 이 실패했다 — 각각 *영어 표기를 못 읽음*,
*쓸 때 정본을 안 씀*, *정본을 바꿔도 안 따라옴*. 세 방향이 다 걸린다.

## 4. 남은 것 — 4단계 (다음 release)

이제 라벨 전환은 **`TASK_FIELD_LABELS` 한 줄씩 바꾸는 일**이다. 다만 그 시점은
release 경계여야 한다:

- 이번 release 를 받은 소비자의 리더가 두 표기를 알게 된다
- **그 다음** release 에서 쓰는 쪽을 영어로 바꾼다
- 옛 문서는 그대로 읽힌다 (별칭이 남아 있으므로 제거하지 않는다)

`read_only_bundle` 의 라벨 리터럴은 아직 남아 있다 — 그건 MCP 번들의 task 생성
경로라 별도 검토가 필요하다 (case 8 의 대상은 현재 `backlog_update` 하나다).
