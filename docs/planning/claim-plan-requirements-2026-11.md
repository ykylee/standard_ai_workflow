## 0. 요약

task 파일 `## 🧭 Plan` 절 맨 앞에 `Claims` · `Decisions` 두 라벨을 더한다. 주장 한 줄은 **80자 이내**, 결정은
task 당 5개 이하, 열리지 않은 결정이 남으면 **done 전이를 거부**한다. 결정 응답은 우리 형식
(`workflow-kit-plan-response/1`)의 markdown 파일 하나이고 **64KiB 이하**다. `plan-import` 는 task ID · 계획
지문(`plan_digest`) · 결정별 값을 대조해 하나라도 어긋난 응답은 받아들이지 않고, 응답자끼리 답이 갈린 결정은 `disputed` 로
다시 연다. 결정의 상태는 보관된 응답 집합과 `answered` 기록의 함수라 도착 순서와 무관하다. 리더와 라이터는 **같은
릴리스**에 낼 수 있다 — 옛 리더는 모르는 라벨 줄을 무시하고 보존한다 (§1.1 실측).

### 1.3 응답 크기 상한

우리 응답 형식(§6)에는 html-plan 의 `Edits`(diff) · `Walked` · `Struck` 가 없다 — 결정과 주석뿐이다. R5.1 형식 그대로
조립해 바이트를 쟀다 (task ID 51자 — 이 브랜치의 ID, 응답자 이름 한글 32자, 값 32자):

| 구성 요소 | 바이트 (UTF-8) |
|---|---|
| 머리 (frontmatter 6필드) | 351 |
| 절 머리 2개 | 28 |
| 결정 5건 (줄당 112) | 560 |
| **구조부 합** | **939** |

| 주석 20건 × 1,000자의 내용 | 주석 1건 | 파일 전체 | 64KiB |
|---|---|---|---|
| 한글, 한 줄 | 3,016 | 61,259 | 들어간다 |
| BMP 밖 문자(이모지), 한 줄 | 4,016 | 81,259 | **넘는다** |
| 한글, 한 글자마다 줄바꿈 (500자 + 줄바꿈 — 줄마다 접두 `  > `) | 4,011 | 81,159 | **넘는다** |
| 이모지, 한 글자마다 줄바꿈 | 4,511 | 91,159 | **넘는다** |
| 줄바꿈만 1,000자 (세 한도 안의 최대 — 줄바꿈 1자는 접두 포함 5바이트) | 5,016 | 101,259 | **넘는다** |

참고 실측: task 파일 크기 p50 2,583 · p90 4,994 · p99 7,674 · max 23,631 바이트 (563개).

결론: **응답 파일 상한 65,536 바이트(64KiB)** 가 지배 규칙이고, 주석 20건 이하 · 건당 1,000자 이하는 그 안의 보조 한도다 (R5.3).
세 한도는 **각각** 지켜야 한다 — 건수 · 글자 수를 지켜도 전체 바이트가 넘으면 거부다 (위 표의 둘째 행부터). 64KiB 는
"한글로 쓴 주석 20,000자가 들어가는 크기" 로 잡은 숫자이고, 가장 큰 task 파일(23,631바이트)의 2.8배다. concept 초안의 256KB 는
diff 를 싣는 html-plan 응답을 본 숫자였다. 워크벤치 POST 본문 상한 256KB(워크벤치 concept §6)와는 층이 다르다 — 한글 1자는 폼
인코딩에서 9바이트라 주석 20,000자가 180,000바이트가 되고, 256KB 안에 들어간다.

## 2. 불변 조건 (R0)

1. **기존 task 파일을 고치지 않는다.** 두 라벨은 선택이고, 없는 파일은 지금과 같게 읽힌다 (§1.1 행 1 이 근거).
2. **A 는 B 없이 완결된다.** 응답 파일이 한 건도 없어도 필드 · 린트 · 게이트 · verifier 묶음이 동작하고, 결정은
   `answered:<value>` 로 대화에서 닫을 수 있다.
3. **Claude 전용 표면에 기대지 않는다.** 정본 경로는 파일 · CLI · MCP 다 (concept §11, 워크벤치 §1-1).
4. **응답은 데이터다.** `plan-import` 는 응답 안의 어떤 문장도 실행하지 않고, 경로를 열지 않고, URL 을 따르지 않는다.
5. **task 파일을 쓰는 주체는 `backlog-update` 와 `plan-import` 뿐이다.** 워크벤치 서버는 받은편지함만 쓴다.
6. **파서는 하나다.** 린트 · 게이트 · verifier 묶음 · `plan-import` · 워크벤치 렌더러가 같은 함수로 주장 · 결정을 읽는다.
7. **모델 호출 없음.** 린트 · 게이트 · import 는 결정적이다.

## 3. 필드 문법 (R1)

### R1.1 라벨

| 의미 key | 정본 라벨 | 한국어 별칭 | 성격 |
|---|---|---|---|
| `plan_claims` | `Claims` | `주장` | 누적 — 기본 병합, `--replace-field plan_claims` 로 교체 |
| `plan_decisions` | `Decisions` | `결정` | 누적, 단 **상태 칸은 현재값** (R1.5) |

`TASK_FIELD_LABELS` · `TASK_FIELD_ALIASES` · `PLAN_FIELDS` · `CUMULATIVE_FIELDS` · `workflow_writes._PLAN_KEYS` 에 함께 들어간다.

### R1.2 위치

- `## 🧭 Plan` 절 **맨 앞**: `Claims` 묶음 → `Decisions` 묶음 → 기존 필드(`Files that change` …). 라이터는 항상 이 순서로 쓴다.
- 각 묶음은 **연속**해야 한다. 다른 라벨 줄이 끼어 묶음이 둘로 나뉜 파일은 L9 오류다 — 리더는 첫 묶음만 읽고 나머지를
  조용히 버리지 않는다(나뉜 사실을 보고한다). 근거: §1.1 행 4.
- `Out of scope` 는 지금 자리(Description 절)에 그대로 둔다.

### R1.3 주장 줄

```
- Claims: C<n>[.<n>[.<n>]] <문장>
- Claims: C<n>.<n>.<n> @ <path>:<line>[-<line>] · <symbol>
- Claims: C<n>.<n>.<n> @ new: <path> · <symbol>
```

- ID 는 `C` + 1~3 단계의 양의 정수, 깊이 = 점 수 + 1. 1 · 2단계는 문장, 3단계는 위치만.
- 부모가 없는 ID(`C1.2` 가 있는데 `C1` 이 없음)는 L2 오류다.
- 길이는 ID 와 그 뒤 공백을 뺀 **문자 수**(Unicode code point)로 센다.

### R1.4 결정 줄

```
- Decisions: D<n> [C<id>] <질문> | 기본: <value> | 선택: <value> = <설명>; <value> = <설명>[; …] | 상태: <state>
```

- `<value>` 는 `[a-z0-9_-]{1,32}` — 응답 파일과 CLI 인자로 왕복하는 식별자라 설명 문장과 분리한다.
- 칸 구분자는 ` | `, 선택지 구분자는 `; `. 질문 · 설명 안에 ` | ` 가 있으면 L6 오류다 (칸이 밀린다).
- 영어 칸 이름 `default:` · `options:` · `state:` 도 읽는다 (라벨 별칭과 같은 원칙 — 쓰기는 한 표기로, design 에서 고른다).

### R1.5 결정 상태

| 상태 | 뜻 | 누가 쓰나 | 열린 결정인가 |
|---|---|---|---|
| `proposed` | 아직 묻지 않음 (유효한 응답이 없다) | `backlog-update` (새 결정의 기본 · 지문 변경 · `answered` 걷기), `plan-import` (재계산) | **예** |
| `unopened` | 응답은 있으나 그 결정에 채택된 입장이 없다 (열어 보지 않았거나, 밝힌 응답이 다툼으로 물렸다) — 기본값 유지 | R6.3 의 계산 (`plan-import` · 재계산하는 `backlog-update`) | **예** |
| `disputed` | 서로 다른 응답자가 다른 값을 밝힘 | R6.3 의 계산 (`plan-import` · 재계산하는 `backlog-update`) | **예** |
| `kept` | 열어 보고 기본값 유지 | R6.3 의 계산 (`plan-import` · 재계산하는 `backlog-update`) | 아니오 |
| `changed:<value>` | 응답에서 다른 값을 고름 | R6.3 의 계산 (`plan-import` · 재계산하는 `backlog-update`) | 아니오 |
| `answered:<value>` | 대화에서 소유자가 직접 답함 | `backlog-update --decision-state` | 아니오 |

- 상태 칸은 현재값이다 — 병합이 아니라 그 결정 줄의 칸만 교체한다. 질문 · 선택지를 바꾸려면 `--replace-field plan_decisions`.
- `changed` · `answered` 의 `<value>` 는 그 결정의 선택지 안에 있어야 한다 (L6).

### R1.6 CLI

`backlog-update` 에 `--plan-claim` · `--plan-decision` (반복 가능), `--decision-state D<n>=<state>` (반복 가능),
`--replace-field` 의 선택지에 `plan_claims` · `plan_decisions`. 모르는 결정 ID 를 가리키는 `--decision-state` 는 거절한다.

- `--decision-state` 가 받는 상태는 `answered:<value>` 와 `proposed`(`answered` 걷기) 둘뿐이고, 쓰면서 모든 결정을 다시 계산한다 (R6.3). `kept` · `changed` · `unopened` 는
  `disputed` 와 함께 CLI 인자로 지정할 수 없고 R6.3 의 계산만이 만든다 — CLI 로 `D1=kept` 를 받으면 응답 없이 게이트를 지나는 길이 된다.
- `--replace-field plan_decisions` 가 **열린 결정을 없애는** 호출은 같은 호출에 `--progress-note` 가 있어야 한다 (없으면 거절).
  결정을 걷는 길은 concept §4.4 가 둔 것이고, 여기서는 그 사유 기록을 강제한다.

|---|---|---|---|
| L1 | 1단계 주장 ≤ 5, 각 노드의 자식 ≤ 5, 깊이 ≤ 3 | 경고 (깊이 4 이상은 문법상 쓸 수 없다 — R1.3) | — |
| L2 | 주장 ID 는 유일하고, 형제 사이에서 1 부터 연속이고, 부모가 있다 | **오류** | 근거가 바뀌었다 — html-plan 번호 정합이 아니라 **응답 · 완료 기준 · verifier 가 ID 로 주장을 가리키기 때문** |
| L3 | 1 · 2단계 주장은 한 문장이고(`;` 가 없다) **80자 이내** | 경고 | 마침표 요구 삭제, 80자 확정 (§1.2) |
| L4 | 1단계 주장이 경로 · 파일명으로 시작한다 ("파일 단위 분할") | 경고 | — |
| L5 | 3단계 `@ path:line` 의 파일이 HEAD 에 있고 줄 범위가 파일 길이 안이다 | 경고 (`@ new:` 는 면제, git 밖이면 건너뛰고 그 사실을 보고) | — |
| L6 | 결정 ≤ 5, 결정 ID 유일, 가리키는 주장이 있다, 선택지 ≥ 2, 기본값과 상태의 값이 선택지 안에 있다, 칸 형식이 맞다 | **오류** | 값 문법 · 칸 구분자 검사 추가 (R1.4) |
| L7 | 자신 또는 후손(`[C1]` · `[C1.2]` · `[C1.2.1]`)을 인용한 `Completion criteria` 가 하나도 없는 1단계 주장 ("재지 않는 주장") | 경고 | 후손 인용도 센다 (R4 의 묶음 규칙과 같게) |
| L8 | 주장에 진척률(`\d+\s*%`) · 상태 표현(`완료` · `done` · `✅` 로 끝남)이 있다 | 경고 | 판정식을 고정 |
| L9 | `Claims` 또는 `Decisions` 묶음이 둘 이상으로 나뉘어 있다 | **오류** | 신설 (§1.1 행 4) |
| L10 | `Completion criteria` 의 `[C<id>]` 인용이 없는 주장을 가리킨다 | 경고 | 신설 (R4) |

### R2.2 강도의 뜻

- **오류** — `backlog-update --apply` 가 쓰지 않는다 (dry-run 은 오류를 그대로 보고한다). `status: error` + 규칙 번호 + 줄.
- **경고** — 쓰고, `warnings` 에 규칙 번호와 함께 싣는다. 종료 코드는 0.
- 린트는 **이번 호출이 `Claims` · `Decisions` 를 건드릴 때**와 **상태 전이 때** 돈다. 그 밖의 update(진행 메모 한 줄)는
  경고를 되풀이하지 않는다 — 매번 같은 경고를 내면 읽히지 않는다. (concept §4.3 초안의 "쓰기 경로 전부" 를 좁혔다.)
- 이미 오류 상태인 파일(손 편집 · 옛 kit)을 만나면: 주장 · 결정을 건드리지 않는 update 는 **통과**시키고 경고 하나,
  상태 전이는 R3 을 따른다.

### R2.3 `Claims` 권고 (D1)

`Claims` 는 선택이다. `Files that change` 에서 `ai-workflow/` 로 시작하는 줄을 뺀 수가 **3 이상**인데 `Claims` 가 비면,
**create 와 → `in_progress` 전이에서 한 번씩** 경고한다: `Claims 가 없다 — 바뀌는 파일 n개 (R2.3)`.

## 5. 게이트 (R3) · verifier (R4)

### R3.1 열린 결정

열린 결정 = **다시 계산한** 상태(R6.3)가 `proposed` · `unopened` · `disputed` 인 결정 (R1.5). 상태 칸에 적힌 값으로 판정하지 않는다.

### R3.2 전이별 동작 (D2)

| 전이 | 열린 결정 n ≥ 1 | 문구 (고정) |
|---|---|---|
| → `in_progress` | 쓰고 **경고** | `열린 결정 n건 (D1 proposed, D3 disputed) — 묻지 않았거나, 열리지 않았거나, 답이 갈렸다. 기본값은 동의가 아니다.` |
| → `done` | **거부** — 파일을 쓰지 않는다, `status: error`, 종료 코드 1 | `done 거부: 열린 결정 n건 (D1, D3). --decision-state D1=answered:<value> 로 답을 기록하거나, --replace-field plan_decisions 로 결정을 걷고 사유를 Progress 에 남긴다.` |
| → `blocked` · `planned` | 영향 없음 | — |

- 결정 줄이 L6 오류라 상태를 읽을 수 없으면 그 결정은 **열린 것으로 센다** — 읽지 못한 것을 닫힌 것으로 치지 않는다.
- → `done` 전이 때 그 task 의 **미반영 응답이 받은편지함에 있으면 거부**한다: `done 거부: 계획 응답 n건 미반영 — plan-import 로 반영하거나 --discard 로 거둔다.`
  상태 칸은 마지막 import 시점의 계산이라, 그 뒤에 온 반대 응답을 모른다 (Q7 이 서려면 필요하다).
- 결정이 없는 task 는 영향이 없다.

### R3.3 기존 게이트와의 순서

`done` 전이의 기존 조건(검증 결과 없음 → `determine_conservative_task_status` 가 `in_progress` 로 **강등**하고 쓴다, rc 0)과
독립이고, 동작이 다르다 — 이 게이트는 강등이 아니라 **거부**다. 강등은 종료 코드가 0 이라 호출자가 닫혔다고 읽기 쉽다.
둘 다 어기면 거부가 이기고(파일 무변경), 두 사유를 함께 보고한다.

### R3.4 우회 검출

옛 kit 은 게이트 없이 닫는다 (§1.1 행 3). 그래서 **`done` 인데 열린 결정이 있는 task** 를 사후에 드러낸다:
`refresh-state` 와 `session-start` 의 `warnings` 에 `done 인데 열린 결정이 있다: <TASK-ID> (D1)` — 재생성은 막지 않는다
(이미 일어난 일이다). 판정은 R0-6 의 같은 파서와 R6.3 의 같은 계산을 쓴다 — 칸이 아니라 계산값으로 본다. `refresh-state` 와 `session-start` 는
읽기 전용 판정이라 칸을 고쳐 쓰지 않는다 (경고만).

### R4 verifier 주장별 묶음 (D3)

- 완료 기준 줄 머리에 `[C<id>]` 를 **하나** 둘 수 있다 (선택). 가리키는 주장이 없으면 L10 경고.
- **묶음은 kit 이 만든다 (Q5).** 주장 × 인용 기준 × 열린 결정의 표를 kit 명령이 결정적으로 낸다 — R0-6 의 같은 파서, 모델 호출 없음.
  판정 칸만 비어 있고, 검증하는 쪽(어느 하네스의 verifier 든, 사람이든)이 기준별 판정을 채운다. 명령을 새로 둘지 기존 명령의
  출력 필드로 둘지는 design 이 정한다 (§11.1 과 스킬의 1:1 규칙을 함께 본다).
- `.claude/agents/verifier.md` 는 "그 출력을 받아 보고에 붙여라" 는 한 줄만 는다. 묶음의 형식 · 계산은 하네스 파일에 두지 않는다.
- 검증 보고의 기준 표 **뒤**에 붙는 모양 — 주장이 없는 task 는 kit 이 이 절 자체를 내지 않는다:

```
### 주장별

| 주장 | 기준 | 판정 |
|---|---|---|
| C1 <문장> | #1, #3 | PASS 1 · UNMEASURED 1 |
| C2 <문장> | — | 재지 않은 주장 |

- 열린 결정: D1 (proposed)
```

- 2 · 3단계 주장을 인용한 기준은 그 1단계 조상에 묶는다 — L7 의 "재지 않는 주장" 과 **같은 판정**이다 (같은 함수).
- 최종 판정 규칙은 바꾸지 않는다 — "닫아도 된다" 는 모든 기준이 PASS 일 때뿐이다. "재지 않은 주장" 과 열린 결정은
  판정 줄 옆에 **따로** 센다 (주장은 완료 기준을 대체하지 않는다 — D3).

## 6. 응답 형식 (R5)

### R5.1 파일

```markdown
---
format: workflow-kit-plan-response/1
task: TASK-2026-11-12-main-001
plan_digest: sha256:<64 hex>
responder: owner
role: approver
received_at: 2026-11-12T21:04:11+09:00
---

## Decisions

- D1 [C1] value: block | default: block | opened: yes
- D2 [C1.2] value: warn | default: block | opened: yes
- D3 [C2] value: a | default: a | opened: no

## Comments

- [C1.1]
  > 사용자가 쓴 글. 여러 줄이면 줄마다 "  > " 로 시작한다.
```

- `## Decisions` 에는 응답 시점 task 의 **모든** 결정이 ID 순으로 한 줄씩 있다 — 빠진 결정이 있으면 닫힌다 (R7).
- `opened` 는 화면에서 그 결정이 열렸는지의 기록이다 (W2 — `toggle` 측정). 기록이 없으면 `no`.
- `## Comments` 는 선택. 대상은 주장 ID · 결정 ID · 대상 없음(`[-]`) 중 하나.
- 줄 끝은 LF, 인코딩은 UTF-8 (BOM 없음).
- `received_at` 은 ISO 8601 이고 시간대 오프셋이 있다. 소수 초(마이크로초까지)가 올 수 있고 읽는 쪽은 받는다 — 쓰는 쪽이 응답자별로
  겹치지 않게 쓰려면 초 단위로는 모자란다 (워크벤치 R5.3, 2026-11-13 추가).

### R5.2 계획 지문 `plan_digest`

응답이 **어느 계획에 대한 것인지**를 묶는 값이다 (html-plan 의 위치 번호 · 질문 문장 3중 대조를 대신한다).

- 입력: `Claims` 줄 전부 + `Decisions` 줄 전부에서 **상태 칸을 뺀 것**, 라벨을 정본 표기로 정규화, 줄 끝 공백 제거, LF 로 이음.
- 상태 칸을 빼는 이유: 결정 하나에 답했다고 나머지 결정에 대한 응답이 무효가 되면 안 된다.
- 주장 문장 · 질문 · 선택지 · 기본값 중 하나라도 바뀌면 지문이 바뀐다 — 그 전에 쓴 응답은 다른 계획에 대한 것이다.
- 계산 함수는 하나다 (R0-6). 워크벤치가 화면을 그릴 때 계산한 값을 폼의 숨은 필드로 싣고, import 가 다시 계산해 대조한다.

### R5.3 크기 (§1.3)

파일 전체 **65,536 바이트 이하** · 주석 **20건 이하** · 주석 한 건 **1,000자 이하** · `responder` 32자 이하.
`\n` · `\t` 밖의 제어 문자(U+0000–U+001F, U+007F)가 있으면 거부.

- 주석의 "자" 는 Unicode code point 이고 **줄바꿈도 센다** (접두 `  > ` 는 세지 않는다).
- 한도는 **각각** 적용한다. 건수 · 글자 수 안이어도 파일 전체가 65,536 바이트를 넘으면 거부다 (§1.3).
- 거부는 두 곳에서 한다: **쓰는 쪽**(워크벤치)은 넘는 응답을 받은편지함에 쓰지 않고 사용자에게 사유를 보이고(M-025),
  **읽는 쪽**(`plan-import` R6.2-1)은 다시 잰다 — 받은편지함 파일은 손으로도 놓일 수 있다.

## 7. `plan-import` (R6) · 닫힘 (R7)

### R6.1 명령

`python -m workflow_kit plan-import --task=<TASK-ID> [--response=<파일>] [--apply]`

- `--response` 를 생략하면 그 task 의 받은편지함 파일 전부를 `received_at` 순(같으면 `n` 순)으로 본다. 기본은 dry-run(무엇을 쓸지 JSON).
- `plan-import --discard=<파일> --reason=<사유> [--apply]` — 응답을 거둔다 (R8.3). 받은편지함의 것도, 이미 보관된 것도 거둘 수 있다 —
  거둔 뒤 상태는 남은 유효 응답으로 다시 계산한다.
- 모르는 인자는 거절한다.

### R6.2 대조 — 순서대로, 하나라도 어긋나면 R7

0. task 파일의 `Claims` · `Decisions` 에 오류 규칙(L2 · L6 · L9) 위반이 없다 — 있으면 지문도 대조도 설 수 없으므로 어떤 응답도 반영하지 않는다.
1. 크기 · 제어 문자 · 인코딩 (R5.3).
2. `format` 이 아는 판(`workflow-kit-plan-response/1`)이다.
3. `task` 가 `--task` 와 같고 그 task 파일이 현재 브랜치에 있다.
4. `plan_digest` 가 지금 task 파일에서 계산한 값과 같다.
5. `role` 이 `approver` 다.
6. `## Decisions` 의 결정 ID 집합이 task 의 결정 ID 집합과 **같다**; 각 줄의 주장 ID · `default` 가 task 와 같다;
   `value` 가 그 결정의 선택지 안에 있다; `opened` 가 `yes` · `no` 다.
7. **다툼에 들지 않았다** (R6.3). 다툼에 든 응답은 그 파일의 어떤 입장도 채택하지 않는다 — 결정 하나만 건너뛰는 부분 반영은 없다 (W7, 워크벤치 §11.4).

1~6 을 통과한 응답을 **자격 있는 응답**이라 부른다. 자격 있는 응답은 다툼 여부와 무관하게 **전부 보관 경로로 옮긴다** (R8) — 반대가
있었다는 사실도 결정의 근거다 (D5). 7 이 막는 것은 보관이 아니라 **입장의 채택**이다.

### R6.3 상태 사상 · 다툼

결정의 상태는 **보관된 응답 집합과 `answered` 기록의 함수**다 (`answered` 는 그 결정 자신의 상태이면서, 다툼 1 을 통해 다른
결정의 상태에도 입력이다). task 파일의 상태 칸은 그 계산 결과를 적어 둔 것이고, `answered` 인지 여부 말고는 계산의 입력이 아니다 —
그래서 응답이 도착한 순서, 그 사이에 import 가 돌았는지, 일괄로 불렀는지 하나씩 불렀는지, `answered` 를 import 앞에 적었는지 뒤에
적었는지가 결과를 바꾸지 않고, 같은 입력에서 다시 돌려도 같다 (Q7).

**입력이 바뀌는 쓰기는 모두 같은 쓰기 안에서 다시 계산한다.** `plan-import`(보관 · `--discard`), `backlog-update --decision-state`
(`answered` 를 적거나 걷음), 지문을 바꾸는 `backlog-update` — 넷 다 이 절의 함수로 그 task 의 **모든** 결정 상태 칸을 다시 쓴다.
그리고 **게이트는 칸을 믿지 않는다**: 상태 전이(R3.2)와 사후 검출(R3.4)은 이 함수를 다시 돌린 값으로 **판정**한다. 칸이 계산값과
다를 때(손 편집 · 옛 kit 이 남긴 칸) 칸을 고쳐 쓰는 것은 **task 파일을 쓰는 경로뿐**이다 — 통과한 상태 전이 · `plan-import --apply` ·
`--decision-state` 는 고쳐 쓰고 경고하고, **거부된 `done`(파일 무변경 — R3.2)과 읽기 전용 판정(`refresh-state` · `session-start` — R3.4)은
쓰지 않고 경고만** 한다 (R0-5).

**입장** — 응답 한 건이 결정 하나에 대해 실제로 밝힌 값이다:

| 응답의 그 결정 줄 | 입장 |
|---|---|
| `value` ≠ `default` | `<value>` — `opened` 와 무관하다. 다른 값을 고른 것은 명시적 행위다 (JS 가 꺼진 브라우저 포함, Q6) |
| `value` = `default`, `opened: yes` | 기본값 |
| `value` = `default`, `opened: no` | **없음** — 열리지 않은 기본값은 동의가 아니다 |

**유효 응답** — 그 task 의 보관된 응답 중 **지금 계획 지문과 맞는 것**에서 응답자마다 `received_at` 이 가장 늦은 하나다 (같은 응답자의 두 응답이 `received_at` 까지 같으면 파일 내용의 sha256 이 큰 것 — 도착 순서로
가르지 않는다; 쓰는 쪽은 응답자별로 `received_at` 이 겹치지 않게 쓴다, M-025). 같은 응답자의 앞 응답은 세지 않는다 — 번복은 그 사람의 권리다. 거둔 응답(`.rejected.md`)은 처음부터 없던 것으로 친다:
뒤 응답을 거두면 그 사람의 앞 응답이 다시 유효해진다. 대체된 앞 응답에 **표식을 붙이지 않는다** — 파일명은 계산의 입력이 아니고,
"대체됨" 은 매번 계산해서 보고한다.

**다툼** — 유효 응답 P 가 어떤 결정에 입장 `s` 를 밝혔고 다음 중 하나면 P 는 다툼에 든다:

1. 그 결정이 `answered:<v>` 이고 `v` ≠ `s` (대화에서 소유자가 답한 것이 우선이다 — 그 결정의 상태는 `answered` 그대로다);
2. 그 결정이 `answered` 가 아니고, **다른 응답자**의 유효 응답(다툼 1 로 이미 물린 응답도 포함한다 — 물렸어도 반대는 반대다)이 같은 결정에 입장 `s'` ≠ `s` 를 밝혔다 — 둘 다 다툼에 들고, 그 결정은 `disputed` 다.
   한쪽이 먼저 반영돼 있었어도 같다: **결정을 다시 연다** (Q7).

다툼에 든 응답은 **파일 전체**의 입장을 채택하지 않는다 — 다른 결정에 밝힌 입장도 물린다. 입장이 없는 줄은 누구와도 다투지 않는다.

**상태** — 다툼에 들지 않은 유효 응답의 입장을 결정별로 모으면 값은 많아야 하나다. 위에서부터 처음 맞는 행을 쓴다:

| 그 결정 | 결과 |
|---|---|
| `answered:<v>` | 그대로 둔다 |
| 다툼 2 가 걸렸다 | `disputed` |
| 모인 입장이 기본값 | `kept` |
| 모인 입장이 기본값이 아닌 `<value>` | `changed:<value>` |
| 모인 입장이 없고, 유효 응답이 하나라도 있다 | `unopened` |
| 유효 응답이 없다 | `proposed` |

현재 상태 칸이 무엇이었든(6종) 결과는 이 여섯 행으로 정해진다 — `answered` 여부만 읽는다.

- **보관 응답이 뒷받침하지 않는 `kept` · `changed`** (손 편집 · 옛 지문의 응답 · 거둔 응답 · 브랜치 이어받기)는 다음 재계산에서 위 표대로
  판정되고, task 파일을 쓰는 경로(import · `--decision-state` · 통과한 상태 전이)에서 칸이 고쳐진다. 바뀐 결정은 보고에 `뒷받침 없는 상태를 되돌렸다: D<n> changed:x → proposed` 로 싣는다.
  소유자의 답으로 남겨야 하는 값이면 `answered` 로 적는다.
- **계획이 바뀌면** (주장 · 질문 · 선택지 · 기본값 — 지문이 달라진다) 그 전 응답은 유효하지 않다. `backlog-update` 는 지문을 바꾸는
  쓰기에서 모든 결정을 다시 계산하고(새 지문에 맞는 보관 응답이 없으면 `proposed`) 바뀐 상태를 경고한다.
- `--response` 로 파일을 지정하면 그 파일만 보관으로 옮기고, 상태는 옮긴 뒤의 보관 집합으로 계산한다. 받은편지함의 모든 자격 있는
  응답을 옮기고 나면 어느 순서로 불렀든 같은 상태가 된다.
- 같은 응답자의 받은편지함 응답이 여럿이어도 자격 있는 것은 전부 보관한다. 어느 것이 유효한지는 보관 집합에서 계산한다.
- 다툼을 끝내는 길: ① 소유자가 대화로 정해 `--decision-state D<n>=answered:<value>` 로 적는다 (그 값과 다른 응답은 다툼 1 로 채택되지
  않은 채 보관에 남는다) ② 응답자가 새 응답으로 번복한다 ③ 한쪽 응답을 `--discard` 한다.
- `--decision-state D<n>=proposed` 는 `answered` 를 걷는 길이다. 걷는 그 쓰기가 보관 집합에서 모든 결정을 다시 계산한다 — 결과가
  `proposed` 가 아닐 수 있다 (보관된 응답이 있으면 `kept` · `changed` · `disputed`).
- concept §5.4-4 초안의 "`answered` · `changed` 는 덮지 않는다" 와 다른 점: `changed` · `kept` 는 응답 집합에서 계산되는 값이라
  같은 응답자의 번복과 다른 응답자의 반대로 바뀐다. 덮지 않는 것은 `answered` 뿐이다.
- 워크벤치 §11.4 의 "그 응답 묶음 전체를 쓰지 않고" 는 여기서 **결정 상태에 채택하지 않는다**는 뜻이다 — 원문 파일은 보관한다 (D5).

### R6.4 쓰는 것 (D4)

`--apply` 가 하는 일은 셋뿐이다: ① task `Decisions` 의 상태 칸을 R6.3 의 계산 결과로 갱신 ② 자격 있는 응답 파일을 받은편지함에서 보관 경로로 이동 (R8)
③ task `Progress` 한 줄 — `plan 응답 <n> (<responder>): 결정 3 (바뀜 1 · 유지 1 · 미열람 1 · 다툼 0) · 주석 2 · 대체 0 — <보관 경로>`.
주석은 반영하지 않는다 — 원문 파일에만 있고, 에이전트가 읽고 소유자와 대화로 처리한다.

### R7 닫힘

- **0 단계**(task 파일의 오류)면 task 전체가 닫힌다 — 아무것도 옮기지 않고 상태도 바꾸지 않는다 (`status: error`).
- **1~6 단계**에서 어긋난 응답은 자격이 없다 — 옮기지 않고, 입장을 세지 않고, 파일별 결과로 단계 번호와 사유를 보고한다. 받은편지함에
  남아 다음 당겨 오기(R9.2)마다 다시 보고된다. 자격 없는 응답은 다른 응답의 판정에 영향을 주지 않는다 — 손으로 놓인 `viewer` 파일이나
  옛 지문의 응답이 다른 응답을 닫지 못한다.
- **7 단계**(다툼)에 든 응답은 보관되지만 입장이 채택되지 않는다. 다툼은 매 import 의 보고와 결정의 `disputed` 상태로 드러난다.

닫힘의 단위는 **응답 파일 하나**다. 부분 채택은 없다.

## 8. 보관 (R8) · state.json (R9)

### R8.1 경로

| 무엇 | 경로 | git |
|---|---|---|
| 받은편지함 (미반영) | `ai-workflow/memory/active/<branch>/plan_responses/inbox/<TASK-ID>-<n>.md` | **무시** (`.gitignore`) — Q1 |
| 보관 (자격 있는 응답 — 채택됐든 다툼에 들었든) | `ai-workflow/memory/active/<branch>/plan_responses/<TASK-ID>-<n>.md` | **커밋** (D5) |
| 보관 (거둠) | `ai-workflow/memory/active/<branch>/plan_responses/<TASK-ID>-<n>.rejected.md` | **커밋** |

- `<n>` 은 task 별 1 부터 — 받은편지함과 보관을 **합쳐** 가장 큰 번호 + 1. 파일명은 쓰는 쪽(워크벤치)이 정하고, 이미 있는
  이름으로는 쓰지 않는다 (배타 생성).
- **import 는 잠금 아래에서 한 번에 하나만 돈다**, 그리고 이동은 **배타**다 — 보관에 있는 이름을 덮지 않고, 이름이 이미 있으면 그 응답에
  다음 번호를 주고 옮긴다 (받은편지함의 번호는 임시, 보관의 번호가 정본). 같은 브랜치에 세션이 둘이면 잠금을 못 쥔 쪽은 "다른 import 가
  돌고 있다" 를 보고하고, 뒤에 돈 쪽에게 이미 옮겨진 응답은 받은편지함에 없다 — 그것이 "이미 반영됨" 이다. 평범한 rename 은 쓰는 쪽이
  살아 있을 때 보관 파일을 조용히 덮어쓰고, 잠금 없는 배타 이동은 같은 응답을 두 번 보관한다 —
  [`plan-workbench-requirements-2026-11.md`](./plan-workbench-requirements-2026-11.md) §1.2 행 7~11 실측 · R5.5 (2026-11-13 수정).
- 브랜치 합류 아카이브는 `plan_responses/` 를 브랜치 디렉터리의 다른 파일과 같게 다룬다 (별도 규칙 없음).

### R8.2 받은편지함을 커밋하지 않는 이유 (Q1)

웹에서 응답이 올 때마다 추적 파일이 생기면, 전량 게이트가 도는 중이거나 통과 기록을 남긴 직후의 작업 트리가 사용자
클릭 하나로 더러워진다 (게이트는 깨끗한 트리를 요구한다). 미반영 응답은 그 호스트의 서버와 세션만 쓰는 **전달 중 상태**이고,
소유자 결정의 근거로 남아야 하는 것은 **import 가 보관한 원문**(자격 있는 응답 — R6.2)이다 — `plan-import --apply` 는 task 파일 변경과 보관 파일을 **같은 작업 트리 변경**으로 만들고(명령은 커밋하지 않는다 — R6.4), 세션이 그 둘을 한 커밋에 싣는다.

### R8.3 거둔 응답

응답을 지우는 명령은 없다. `--discard` 가 받은편지함 또는 보관의 응답을 `.rejected.md` 로 옮기고 Progress 에 사유 한 줄을 남긴다 —
"왜 반영하지 않았나" 도 결정의 기록이다.

### R9.1 state.json

- 주장 · 결정 **전문은 싣지 않는다** (세션 시작 컨텍스트 예산, ADR-029).
- `in_progress` · `blocked` · `planned` task 중 열린 결정이 있는 것만 **숫자 하나**: `open_decisions: {"<TASK-ID>": n}`.
  0 건인 task 는 싣지 않고, 하나도 없으면 key 자체를 싣지 않는다 — 기존 `state.json` 과 바이트가 같다.
- 출처는 task 파일뿐이다 (생성기 입력은 지금과 같다 — `backlog/tasks/` + `session_handoff.md`). 그래서 이 숫자는 **상태 칸 기준**이다 —
  칸이 낡았으면(손 편집 · 옛 kit) 게이트의 계산값(R3.1)과 다를 수 있고, 판정의 정본은 게이트다. 어긋남은 R3.4 의 경고가 드러낸다:
  R3.4 는 `plan_responses/` 를 읽는 **별도 판정**이고 state.json 의 입력을 늘리지 않는다.

### R9.2 받은편지함 건수는 state.json 에 싣지 않는다

받은편지함은 `refresh-state` 없이 바뀐다 — 실으면 `refresh-state --check` 가 응답이 올 때마다 drift 를 낸다.
`session-start` · `backlog-update` 가 **명령 시점에 디렉터리를 세어** `warnings` 에 싣는다 (W1 ①):
`계획 응답 n건 미반영 (<TASK-ID> …) — plan-import 로 확인`. 응답 내용은 싣지 않는다.

## 10. 검증 (R11) · design 진입 조건 (R12) · 남은 실측 (R13)

**R11 검사** — 각 case 는 되주입으로 red 를 확인한다:

1. 호환: 두 라벨이 없는 기존 task 파일 전수에서 필드 값 · `state.json` 이 도입 전과 같다.
2. 린트: L1~L10 각각의 최소 위반 fixture — 오류 규칙은 `--apply` 가 파일을 쓰지 않음을, 경고 규칙은 씀을 본다.
3. 게이트: 칸을 손으로 `kept` 로 고친(보관 응답 없음) 파일에서 → `done` 거부(계산값은 `proposed`) · 파일 무변경 · 칸 불일치 경고, 같은 파일의 → `in_progress` 는 통과하며 칸을 `proposed` 로 고쳐 씀; 열린 결정 1건(세 상태 각각)으로 → `in_progress` 경고 · → `done` 거부(파일 무변경 · rc 1) · `answered` 뒤 통과; 받은편지함에 미반영 응답이 있으면 `done` 거부.
4. 우회 검출: `done` + `proposed` 인 파일에서 `refresh-state` warning.
5. import: R6.2 의 0~6 단계마다 하나씩 어긋난 fixture → 무변경이고 다른 응답의 판정에 영향 없음; R6.3 의 입장 세 행 · 다툼 두 조건 ·
   상태 여섯 행 전부; 다툼에 든 응답의 다른 결정 입장이 물리는 것; 뒷받침 없는 `changed` 가 되돌려지고 보고되는 것.
   **순서 무관성 · 멱등**: 같은 응답 집합을 ①도착할 때마다 import ②모은 뒤 일괄 ③모은 뒤 `--response` 로 하나씩, 도착 순서를 바꿔 넣어도
   모든 결정의 최종 상태가 같고, 같은 상태에서 한 번 더 돌려도 변화가 없다 — 집합 {alice x, bob y} · {alice x, bob x, bob y(뒤)} ·
   {alice x(D1) · p(D2)} 에 `answered D1=y` 를 import 앞 / 뒤에 적기(둘 다 D2 가 물리고 done 거부) ·
   {alice x, alice y(뒤)} · {alice x, alice 입장 없음(뒤)} · {alice x 반영 뒤 `--discard`} 와 {`--discard` 뒤 import} · {alice x, alice y(뒤)} 에서 y 를 import 전 / 후에 `--discard`.
6. 지문: 상태 칸만 바꾸면 같고, 주장 · 질문 · 선택지 · 기본값 중 하나를 바꾸면 다르다.
7. 경합: 같은 받은편지함을 두 프로세스가 동시에 import → 응답마다 한 번만 보관되고(중복 0 · 유실 0), 잠금을 못 쥔 쪽은 그렇게 보고한다. 쓰는 쪽이 살아 있는 동안에도 같다 (워크벤치 R10-4).
8. 파서 단일성: 린트 · 게이트 · 주장별 묶음 · import · state 생성기가 같은 함수를 부른다 (호출 그래프 또는 import 대조). 워크벤치 렌더러는 M-025 의 검사가 같은 대조를 한다.
9. 주장별 묶음(R4): 주장 · 인용 · 열린 결정이 있는 fixture 에서 출력이 기대 표와 같고, 주장이 없는 task 는 절을 내지 않는다; L7 의 "재지 않는 주장" 집합과 묶음의 그것이 같다.
10. CLI 한정(R1.6): `--decision-state D1=kept` 거절 · 사유 없는 열린 결정 제거 거절.

## 12. sign-off 기록

2026-11-12 (124차), 소유자 — 하나씩 확인, Q1~Q3 권고안:

1. **Q1** 받은편지함(`plan_responses/inbox/`)은 **gitignore**. import 가 보관한 원문만 커밋한다 (R8 — 자격 있는 응답 전부와 거둔 응답). 워크벤치 concept §3 그림의

verifier(새 컨텍스트)가 소유자 결정에서 벗어난 두 곳을 지적해 Q4 · Q5 로 올렸고, 같은 날 확정:
