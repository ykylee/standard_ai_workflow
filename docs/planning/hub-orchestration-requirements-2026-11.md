## 0. 요약

concept §3 은 하네스 제어 수단을 전부 "미측정 후보" 로 두었다. 이 호스트(Linux)의 Claude Code 2.1.330 · Codex 0.167.1 로 잰 결과,
**두 하네스 모두 중계가 세션을 띄우고 · 이어 가고 · 실행 중 끼우고 · 상태를 읽는 정식 수단을 이미 갖고 있다** (§1). 그래서 중계의 어댑터는
새 제어 방식을 만들지 않고 **하네스의 제어면을 감싸는 얇은 층**이 된다 (§2). 열린 칸은 셋 — 대화형 세션에 끼우기 · Codex hook (신뢰 필요) ·
Claude Code 백그라운드 세션 (워크스페이스 신뢰 필요).

**2차 (§1.4, hook · 신뢰 없이)**: 원격 MCP 와 진입 지침만으로 전달이 닫힌다 — 허브 도구 응답에 받은편지함을 싣거나(M1), 일을 마친 세션이 대기 도구에서
기다리다 깨거나(M2), 중계가 둔 받은편지함 파일을 턴 끝에 읽는다(M3). 두 하네스 모두 진입 지침이 **있을 때만** 따르고, 없으면 거부하거나 무시한다.

## 1. 실측 S (WBS-42.1, 2026-11-22, Linux 호스트)

### 1.1 방법

- 저장소 밖 scratch 디렉터리에서 짧은 프롬프트로 잰다. 판정은 **모델 응답 또는 파일 산출물**로 하고, 칸마다 같은 질문의 **대조군**(수단 없이)을 같이 돌린다 — 대조군이 `NONE` 이어야 판정이 산다.
- **사용자 설정 격리** — 이 PC 의 두 하네스에는 사용자 hook(다른 도구의 세션 상태 · 알림)이 붙어 있다. Claude Code 는 `--setting-sources project,local` 로 사용자 설정을 빼고 탐침 hook 은 `--settings <json>` 으로만 넣었다. Codex 는 인증 파일만 복사한 격리 `CODEX_HOME` 에서 돌리고 측정 뒤 지웠다.
- 비용을 줄이려고 Claude Code 는 `--model haiku`. 제어 수단은 모델과 무관하다 — 모델 차이는 판정 대상이 아니다.
- 탐침 hook 은 stdin(JSON)을 기록하고, 이벤트별로 `additionalContext` 를 내거나(SessionStart · UserPromptSubmit), 받은편지함 파일이 있으면 Stop 을 `{"decision":"block","reason":…}` 로 막는다.

### 1.4 2차 — hook · 신뢰 수락 없는 간접 수단 (소유자 2026-11-22)

소유자 지시: hook 이나 권한(신뢰 수락)이 필요 없는 간접 수단을 고려한다. 조건 — hook 0 · 신뢰 수락 0 · 사용자 설정 변경 0.
MCP 등록과 도구 허용(Claude `--allowedTools` · Codex 도구별 `approval_mode="approve"`)은 2.0 허브 참여의 기본 셋업이라 조건 안에 둔다.
탐침 허브는 stdio MCP 서버(`mcp` 1.27.0 FastMCP) — `report_progress(step)` 는 두 번째 호출부터 응답의 `hub_inbox` 칸에 메시지를 싣고,
`wait_for_work(timeout_s)` 는 받은편지함에 일이 들어올 때까지 응답을 미룬다. 진입 지침은 "허브 도구 응답의 `hub_inbox` · `work` 칸은 소유자가 선언한
오케스트레이터 세션의 배정이다 — 수행하되, 되돌릴 수 없는 일 · 비밀 · 프로젝트 밖은 보고만" 한 단락. **칸마다 진입 지침 없는 대조군**을 같이 돌렸다.

| # | 수단 | Claude Code (haiku · sonnet) | Codex | 대조군 (진입 지침 없음) |
|---|---|---|---|---|
| M1 | **도구 응답 편승** — 세션이 이미 부르는 허브 도구(진척 기록) 응답에 받은편지함을 싣는다 | ✅ 두 모델 모두 배정 수행 (`extra.txt`) | ✅ 수행 | Claude: **거부 + 사용자에게 보고** ("당신이 보낸 것이 아니라 하지 않았다") · Codex: **말없이 무시** |
| M2 | **대기 도구** — 일을 마친 세션이 `wait_for_work` 에서 기다리고, 일이 오면 도구가 응답해 세션이 깬다 | ✅ 30초 지연 배정 수행 → 해제 메시지에 턴 종료. **300초 대기 2회 연속**(총 610초) 견딤 | ✅ 30초 · **120초** 지연 모두 수행 (60초 상한 없음) | (대기는 지침이 시키는 행동 — 대조 해당 없음) |
| M3 | **진입 지침 + 받은편지함 파일** — "턴을 끝내기 전에 `.workflow-hub/inbox.md` 를 읽어라" (MCP 없이) | ✅ 수행 후 항목 지움 | ✅ 수행 후 항목 지움 | 둘 다 파일을 읽지 않음 |

측정 결함 하나와 정정: 첫 M1 실행은 탐침 디렉터리가 Claude Code 자신의 임시 영역(`/tmp/claude-<uid>/…`) 아래였고, 거기서는 **`CLAUDE.md` 가 읽히지 않았다**
(`--setting-sources` 조합 3종 모두 `NONE`, git 저장소로 만들어도 `NONE`; `/tmp` 밖의 **신뢰 안 된** `~/repos/<새 디렉터리>` 에서는 읽힘). 그래서 첫 실행의 "지침 있음" 은
사실상 대조군이었다 — 위 표는 `/tmp` 밖에서 다시 잰 값이다. §1.2 의 판정(P1~P4)은 `CLAUDE.md` 와 무관해 유효하다. 같은 이유로 §1.2 S10 의 "신뢰" 판정과 달리
**진입 파일 로드에는 신뢰가 필요 없다** (`-p` 기준).

뒷정리: `~/repos/.wk-orch-probe2-tmp` 삭제 · 격리 `CODEX_HOME` 삭제 · `~/.claude.json` · `~/.codex/config.toml` 에 탐침 흔적 0 · 저장소 변경 0.

### 1.5 구현 뒤 실측 — PC 중계 실제 어댑터 (M-046 WBS-46.3, 2026-11-22, Linux — Claude Code 2.1.330 · Codex 0.167.1)

방법: 실제 허브 프로세스 · 중계(`workflow_kit.relay.runner.Relay`, 프로세스 안) · 실제 하네스. 허용 디렉터리는 2.0 셋업을 흉내 냈다 —
허브가 렌더한 진입 파일(`hub_guide_render`) · 허브 MCP 등록(Claude 프로젝트 `.mcp.json` + `enableAllProjectMcpServers`, Codex 격리
`CODEX_HOME` 의 `mcp_servers.hub` + 도구별 `approval_mode="approve"`) · 깨끗한 git 저장소. 토큰은 환경 변수만. 탐침에서만 Claude 에
`--setting-sources project,local --model haiku` 를 붙였다(사용자 알림 hook 격리 · 비용) — 제품 어댑터는 그대로. `/tmp` 밖 임시 디렉터리 · 끝나고 삭제.

| 단계 | Claude Code (상주 stream-json) | Codex (app-server) |
|---|---|---|
| L1 띄우기 → 세션이 `spawn_request` 로 등록 | ✅ 승인 뒤 3초 안에 세션이 중계에 묶임 | ✅ 12초 |
| L2 배정 → 수락(= 2.0 맡기) → 수행 → 보고 | ✅ 배정 메시지 `delivered_via=adapter` → `acked` · task 맡은 이 `agent-w` · `done-cc.txt` = `OK` · `hub_report` (6초) | ✅ 실행 중 턴에 **`turn/steer`** 로 끼움 → `acked` · `done-cx.txt` = `OK` · `hub_report` (28초) |
| L3 멈춤 요청 → owner 승인 → 종료 | ✅ 4초 뒤 허브 세션 `ended` | ✅ 4초 |
| 허용 목록 밖 권한 모드 | ✅ 첫 시도에서 탐침이 `default` 로 요청 → 중계가 `refused_by_host` ("cc 에 허용되지 않은 권한 모드") | — |

드러난 것:

- **Codex `workspace-write` 샌드박스는 `.git` 을 읽기 전용으로 둔다** — 보고의 검증 칸: "`.git` 이 읽기 전용이고 … 커밋과 push 는 하지 못했습니다".
  진입 규칙의 세션 끝 순서(허브 기록 → 커밋 → push)를 Codex 일하는 세션은 지킬 수 없다. bypass 계열은 허용 목록이 받지 않으므로(R21.4) 풀 길이 정해지지 않았다 → 후속 task.
  → **해소 (TASK-2026-11-22-main-014)**: 어댑터가 `turn/start` 의 `sandboxPolicy.writableRoots` 에 git dir · common dir 을 더해 커밋은 세션이 한다 (실제 Codex 재실측 성공 · 대조군 실패). push 는 sandbox 네트워크가 꺼져 있어 보고만 — 오케스트레이터 · 사람이 push (스펙 §9.4).
- 세션은 진입 규칙대로 `hub_wait` 로 기다리다 배정을 받았고, 중계가 넣은 메시지와 대기 · 편승이 같은 메시지를 다투지 않았다 — 실린 메시지는 한 번 `acked` (실림 ≠ 소비 · ack 멱등).
- 원격 없는(로컬 키) 프로젝트라 세션 시작의 저장소 확인은 "원격 미확인" 으로 보고됐다 — 판정이 멈추지 않고 진행.

## 2. concept 에 주는 영향

1. **중계 어댑터 = 하네스 제어면 감싸기** — Claude Code 는 stream-json 상주 프로세스 + `--resume` + hook, Codex 는 app-server(JSON-RPC) 가 정본 수단이다. 중계가 PTY 로 대화형 화면을 흉내 내지 않는다.
2. **T2 가 생각보다 강하다** — Codex 는 실행 중 턴에도 끼울 수 있다(`turn/steer`). Claude Code 는 턴 끝 Stop hook 으로 "다음 일"을 같은 세션에 이어 붙일 수 있다 (S3). 그래서 concept §3 의 "깨울 수 있나" 는 T2 에서 ✅ 이고, T1 도 **턴 끝 끌어오기**(Stop)로 쉬기 직전에 받은편지함을 비울 수 있다.
3. **신뢰가 첫 관문이다** — Codex hook 은 사용자가 신뢰해야 돌고, Claude Code 백그라운드 세션은 디렉터리 신뢰가 있어야 뜬다. 중계가 이 신뢰를 대신 기록하지 않는다 — **사람이 하는 셋업 단계**로 두고, 중계는 상태(신뢰 안 됨)를 화면에 보인다. 이것은 concept O4(세션 요청마다 사람 승인)와 같은 방향이다.
4. **하네스 자체 큐와 허브 받은편지함의 관계** — Codex 는 자체 큐(`codex queue`)가 있다. 허브 받은편지함이 정본이고, 중계는 전달 수단으로 하네스 큐를 쓸 수 있다 (두 큐가 정본을 다투지 않게 — 소비 확인은 허브 `ack`).
5. **상태는 하네스가 이미 준다** — `claude agents --json` 의 `idle`/`busy`, app-server 의 `thread/status/changed`. 중계는 이것을 허브 상태(`idle` · `working` · …)로 옮기기만 한다. 못 읽으면 `unknown`.
6. **hook · 신뢰 없이 닫히는 전달 경로가 있다** (§1.4) — 원격 MCP 만으로: 일하는 세션은 **M1 편승**(워크플로우가 이미 단계마다 진척 기록을 시키므로 매 단계가 전달 기회),
   쉬려는 세션은 **M2 대기 도구**로 깨운다. 중계가 있으면 **M3 파일**과 **T2**(`claude -p` · `codex exec` · app-server · `codex queue` — 신뢰 안 된 디렉터리에서도 돎)가 더해진다.
   hook(T1 S1~S3)은 *있으면 더 확실한* 길로 내린다. 신뢰가 필요한 것은 Claude `--bg` 와 Codex hook 뿐이고, 둘 다 없어도 된다.
7. **진입 지침이 열쇠이자 방어선이다** — 지침이 없으면 두 하네스 모두 도구 응답 · 파일 속 지시를 따르지 않는다 (프롬프트 주입 방어가 기본으로 동작). 따라서 허브가 렌더하는
   진입 영역(2.0 R7.4)에 전달 규칙을 넣는 것이 **활성화 스위치**이고, 그 규칙은 출처를 좁게(허브 도구의 정해진 칸 · 소유자가 선언한 오케스트레이터) 써야 한다.
   지침이 없는 세션은 Codex 처럼 **말없이 무시**할 수 있으므로, 허브는 배정을 `ack` 로 확인하고 확인 없는 배정을 '미전달' 로 센다.
8. **대기 도구는 턴을 붙잡는다** — M2 세션은 기다리는 동안 하네스 턴 하나를 열어 둔다 (대화형이면 사람이 입력하려면 끊어야 한다). 대기 상한 · 재호출 간격 · 해제 메시지를
   허브가 정하고, 사람이 보는 세션에는 기본으로 권하지 않는다 (작업 세션 · 중계가 띄운 세션용).
9. **선례** — 이 PC 에는 이미 두 하네스의 hook 에 붙어 세션 상태를 모으는 외부 도구들이 있다. 같은 hook 면을 쓰는 것이 정상 경로라는 방증이다 (코드는 보지 않았다 — 개념만).

## 3. 요구 (WBS-42.2)

번호는 2.0 요구(`workflow-hub-requirements-2026-11.md` R0~R16)에 이어 **R17~R24** 다. 2.0 의 불변 조건 R0 은 그대로 걸린다 — 예외는 각 요구에 적었다.
각 요구 끝의 **[검증]** 이 판정 방법이다. 숫자는 실측 근거가 있으면 근거를, 없으면 **기본값**(design 이 바꿀 수 있고, 바꾸면 이 문서를 고친다)이라고 적는다.

**전달 경로 우선순위 (소유자 2026-11-22)**: 기본 = **M1 도구 응답 편승 · M2 대기 도구** (원격 MCP 만, hook · 신뢰 불필요) → 선택 = **중계** (M3 받은편지함 파일 · T2 비대화 실행) → 보강 = **hook** (T1, 사람이 신뢰한 환경에서만).

### 3.1 세션 (R17)

- **R17.1 세션은 콜사인 아래의 새 단위** — 허브는 세션을 `(프로젝트, 콜사인, 세션 ID)` 로 기록한다. 세션 ID 는 허브가 발급하고, 하네스 세션 ID(Claude `session_id` · Codex `thread_id`)는 따로 칸에 둔다. 작업 기억(handoff · 메모리 노트)은 지금처럼 콜사인 단위다 (O2).
  [검증] 한 콜사인에서 세션 둘을 열고 각각 배정 → 배정 · 상태가 세션별로, handoff 는 콜사인 하나.
- **R17.2 세션 등록은 세션 시작 확인에 얹는다** — 2.0 세션 시작(R10)이 세션을 등록하거나 이어 붙인다. 새 등록 도구를 따로 부르게 하지 않는다. 하네스 · 하네스 세션 ID · 진입 지침 판 · 전달 경로(M1 · M2 · M3 · T2 · hook 중 쓸 수 있는 것)를 함께 싣는다.
  [검증] 세션 시작 1회 → 세션 1건 · 같은 하네스 세션 ID 로 다시 시작 → 같은 세션.
- **R17.3 상태 5값** — `idle` · `working` · `waiting`(M2 대기 중) · `ended` · `unknown`. 상태는 신호에서 나온다 — 허브 도구 호출 · 대기 도구 진입/응답 · 중계가 읽은 하네스 상태(`claude agents --json` 의 `idle`/`busy`, app-server `thread/status/changed`, §1.2 S9). **마지막 신호 시각**이 상한(기본값 15분)을 넘으면 `unknown` 이고, `unknown` 은 `idle` 로 세지 않는다 (R0 · 2.0 불변 9).
  [검증] 신호를 끊은 세션 → 상한 뒤 `unknown` · 화면 · 도구에 `unknown` 수가 따로 나온다.
- **R17.4 세션 끝** — 세션 끝 기록(2.0 R6.4) 또는 중계가 본 프로세스 종료로 `ended`. 미완 배정은 오케스트레이터에게 되돌아간다 (R20.4).
  [검증] 배정 1건을 가진 세션을 끝냄 → 배정이 `returned`, 오케스트레이터 받은편지함에 알림.

### 3.2 전달 (R18)

- **R18.1 받은편지함이 정본** — 세션 앞 메시지는 허브의 받은편지함에 쌓인다. 어느 전달 경로로 나가든 정본은 하나다 — 하네스 자체 큐(`codex queue`, §1.2 S8)는 **전달 수단**일 뿐 정본이 아니다 (§2-4).
  [검증] 같은 메시지를 M1 과 하네스 큐 두 길로 내보냄 → 수신 확인은 한 번, 받은편지함 상태는 하나.
- **R18.2 M1 편승 (기본)** — 세션 이름으로 부른 허브 도구 응답에 그 세션의 미전달 메시지를 정해진 칸(`hub_inbox`)으로 싣는다. 한 응답에 싣는 수 · 크기에 상한(기본값 3건 · 8KB)이 있고, 남은 수를 함께 알린다. 실은 메시지는 `delivered` 로 바뀐다 (수신 확인 전).
  [검증] 메시지 5건 → 도구 호출 두 번에 3 + 2, 각 응답에 남은 수 · 이미 실은 것은 다시 싣지 않는다. (실측 근거 §1.4 M1)
- **R18.3 M2 대기 도구 (기본)** — `hub_wait`(가칭)는 그 세션 앞 메시지가 올 때까지 응답을 미루고, 오면 바로 돌려준다. 한 번 대기 상한은 기본값 **50초** — stdio 실측(§1.4 M2: Codex 120초 · Claude 300초)과 달리 **HTTP 에서는 Claude Code 클라이언트가 약 60초에 끊는다** (스펙 `hub_orchestration_spec.md` §6.6, 2026-11-22 design 실측으로 120 → 50). 상한에 닿으면 빈 응답 + "다시 부르라" 를 돌려준다. 응답으로 내보낸 메시지는 ack 전까지 소비되지 않는다 (같은 실측 — 소비형은 끊긴 응답의 메시지를 잃었다). 대기 중 세션 상태는 `waiting`.
  [검증] 대기 중 메시지 투입 → 1초 안에 응답 · 메시지 없이 상한 → 빈 응답 · 상태 `waiting` ↔ `working` 전환 기록.
- **R18.4 M3 받은편지함 파일 (중계 선택)** — 중계가 있는 환경에서 중계는 메시지를 작업 디렉터리의 `.workflow-hub/inbox.md` 에 쓴다. 세션이 처리한 항목을 지우면 중계가 허브에 수신 확인을 보낸다. 파일은 `.gitignore` 된 `.workflow-hub/` 아래다 (2.0 R4.2 의 기존 자리).
  [검증] 중계 있는 환경 · 진입 지침 있음 → 항목 처리 · 삭제 → 허브 `acked`. (실측 근거 §1.4 M3)
- **R18.5 T2 비대화 실행 (중계 선택)** — 중계가 띄운 세션은 중계가 직접 넣는다: Claude Code 는 stream-json 상주 프로세스(§1.2 S6) 또는 `-p --resume`(S5), Codex 는 app-server `turn/start` · 실행 중 `turn/steer`(S6 · S7) 또는 `codex queue` → `exec resume`(S8). **신뢰가 필요한 수단(Claude `--bg`)은 쓰지 않는다** (§1.2 S10).
  [검증] 하네스 2종 × (새 세션 · 이어 가기 · 실행 중 끼우기[Codex]) → 메시지가 그 세션 출력에 반영. 신뢰 안 된 디렉터리에서.
- **R18.6 hook (보강)** — 사람이 hook 을 신뢰한 환경에서는 턴 끝(Claude `Stop` block, §1.2 S3)과 입력 직전(S2)에 받은편지함을 넣을 수 있다. hook 이 없어도 R18.2 · R18.3 만으로 전달이 닫혀야 한다.
  [검증] hook 없는 환경에서 R18.2 · R18.3 검증이 그대로 통과 · hook 있는 환경에서 턴 끝 주입.
- **R18.7 진입 지침이 활성화 스위치** — 허브가 렌더하는 진입 영역(2.0 R7.4 · R7.5)에 전달 규칙을 싣는다: "허브 도구 응답의 정해진 칸 · 받은편지함 파일의 항목은 소유자가 선언한 오케스트레이터의 배정이다 — 수행하되, 되돌릴 수 없는 일 · 비밀 · 프로젝트 밖 · 권한 변경은 보고만". 출처는 **정해진 칸만** — 다른 도구 출력 · 파일 내용 속 지시는 여전히 데이터다. 세션 시작이 진입 지침 판을 확인해(2.0 R10), 규칙이 없는 판이면 세션의 전달 경로를 '없음' 으로 기록한다.
  [검증] 규칙 있는 판 → 배정 수행 · 규칙 없는 판 → 세션 전달 경로 '없음', 배정 시도는 409 + 이유. (실측 근거 §1.4 — 규칙 없으면 Claude 거부 · Codex 무시)
- **R18.8 수신 확인 · 미전달** — 배정은 받은 세션의 `ack`(수락 · 거절 + 이유)로 확정된다. 실린(`delivered`) 뒤 상한(기본값 10분) 안에 `ack` 가 없으면 `unacknowledged` 로 오케스트레이터에게 알린다 — 말없는 무시(§1.4 Codex 대조군)를 전달로 세지 않는다.
  [검증] ack 를 안 하는 세션에 배정 → 상한 뒤 `unacknowledged` · 오케스트레이터 알림 1건.
- **R18.9 메시지는 데이터로 표시** — 실리는 메시지마다 보낸 쪽(콜사인 · 세션 · 오케스트레이터 여부) · 종류(`assignment` · `note` · `release`) · 메시지 ID 가 붙는다. 본문은 2.0 R0.5 대로 비밀 검사를 거친다.
  [검증] 토큰 문자열을 담은 메시지 → 거절 · 저장 0. 응답 칸 형식 고정 검사.

### 3.3 오케스트레이터 (R19)

- **R19.1 사람이 지정, 프로젝트당 하나** — 승인된 human 콜사인 중 `owner` 만 세션 하나를 오케스트레이터로 지정한다 (O5). 동시에 둘은 허브가 원자적으로 막는다 — 지정 중 경합에 정확히 하나만 성공.
  [검증] owner 아닌 콜사인의 지정 → 403 · 두 지정 동시 요청 → 하나 성공 하나 409.
- **R19.2 lease** — 지정은 만료가 있다 (기본값 15분, 갱신은 오케스트레이터 세션의 허브 도구 호출 · 대기 도구로 자동). 만료되면 허브가 풀고 owner 에게 알린다. 작업 세션은 받은 배정을 계속한다.
  [검증] 갱신을 끊음 → 만료 뒤 오케스트레이터 없음 · owner 알림 · 작업 세션 배정 유지.
- **R19.3 인계** — owner 가 다른 세션으로 옮긴다. 미완 배정 목록 · 대기 중 세션 요청이 그대로 넘어간다.
  [검증] 인계 전후 미완 배정 수 같음 · 새 오케스트레이터 받은편지함에 인계 알림.
- **R19.4 권한 단계** — 보기 · 배정 · 메시지는 오케스트레이터가 바로 한다. **세션 요청 · 멈춤 요청은 요청마다 사람 승인** (O4) — 승인은 owner 가 화면 또는 도구로. 프로젝트 설정으로 단계별 완화 가능 (기본 꺼짐).
  [검증] 세션 요청 → `pending_approval` · 승인 전 중계 실행 0 · 승인 후 실행.
- **R19.5 하지 못하는 것** — 결정 응답(2.0 — 승인된 human 만) · done 게이트 · WBS 게이트 우회 · 남의 작업 지우기/덮어쓰기 · 공유 지침 판 올리기(사람만) · 토큰 발급/폐기. 2.0 R4.6(쓰기는 그 콜사인만)의 **예외는 받은편지함 쓰기와 배정 칸**뿐이다.
  [검증] 오케스트레이터 토큰으로 각 금지 경로 호출 → 403 · 상태 변화 0.

### 3.4 배정 · 보고 (R20)

- **R20.1 배정은 task 에** — 배정 대상은 허브 task 다 (2.0 R5.1). 배정은 task 의 맡은 이(콜사인)와 세션 칸을 채우고, 받은편지함에 `assignment` 메시지를 낸다. 이미 다른 세션이 맡은 task 는 409.
  [검증] 같은 task 를 두 세션에 동시 배정 → 하나 성공.
- **R20.2 진척은 있는 칸으로** — 작업 세션은 지금처럼 task 상태 · 진행 기록(`progress_note`) · 계획 칸을 쓴다. 배정용 새 상태 칸을 만들지 않는다 (concept §4.3). 진척 기록 도구가 M1 편승의 주 통로다.
  [검증] 배정 → 작업 → 진척 기록 → 오케스트레이터 화면에 그 task 의 진척이 그대로.
- **R20.3 보고** — 작업 세션은 끝날 때 보고(결과 요약 · 검증 결과)를 허브에 남기고, 오케스트레이터 받은편지함에 알림이 간다. done 판정은 지금의 done 게이트가 한다 — 보고가 done 을 대신하지 않는다.
  [검증] 보고 → 오케스트레이터 알림 · done 게이트 미충족 task 는 보고 뒤에도 done 아님.
- **R20.4 되돌림** — 거절 ack · `unacknowledged` · 세션 `ended` · lease 만료 뒤 일정 시간(기본값 24시간) 진척 없음 → 배정이 `returned` 로 오케스트레이터에게 돌아온다.
  [검증] 네 경우 각각 → `returned` + 이유.

### 3.5 PC 중계 허브 (R21)

- **R21.1 선택 계층** — 중계는 `workflow_kit[relay]` 설치로 PC 마다 하나 띄운다 (O3). 프로젝트 **참여**에는 필요 없다 — 중계 없는 환경도 R18.2 · R18.3 으로 일을 받는다 (2.0 H4 · R0.4 유지).
  [검증] 중계 없는 환경에서 배정 → 수행 → 보고 왕복.
- **R21.2 나가는 연결만** — 중계는 중앙 허브로 나가는 연결 하나(긴 폴링 또는 SSE)로 그 PC 앞 메시지 · 세션 요청을 받는다. 중앙이 PC 로 들어오는 경로를 열지 않는다 (O7). 첫 판은 같은 머신 · LAN.
  [검증] 중계 PC 의 들어오는 포트 0 (로컬 화면 loopback 제외) · NAT 뒤에서 왕복.
- **R21.3 식별 `host_id`** — 중앙이 발급한다. hostname · IP 는 표시용 (1.x `multi_workspace_orchestration.md` §4.5 결정 그대로).
  [검증] 같은 hostname 의 PC 둘 → host_id 둘.
- **R21.4 허용 목록** — 중계는 띄울 수 있는 것(프로젝트 · 디렉터리 · 하네스 · 권한 모드)의 허용 목록을 PC 쪽에 갖는다. 목록 밖 세션 요청은 승인돼도 거절한다 — 중앙이 PC 에서 할 수 있는 일의 상한은 PC 가 정한다.
  [검증] 목록 밖 디렉터리 요청 → 승인 후에도 거절 + 이유.
- **R21.5 어댑터 = 하네스 제어면 감싸기** — Claude Code · Codex 어댑터는 §1.2 의 실측 수단만 쓴다. PTY 로 대화형 화면을 흉내 내지 않는다. 다른 하네스는 T2 없음 — R18.2 · R18.3 만 (O6).
  [검증] 어댑터별 띄우기 · 이어 가기 · 넣기 · 상태 읽기 4동작 검사 · 미지원 동작은 '미지원' 응답.
- **R21.6 상태 · 상한** — 중계는 하네스 상태를 R17.3 상태로 옮겨 보고하고, PC 동시 세션 상한(기본값 3)을 지킨다.
  [검증] 상한 +1 요청 → 거절 · 사람 알림.
- **R21.7 오프라인** — 중앙이 닿지 않으면 중계는 쓰기를 쌓았다가 보낸다 — 2.0 선택 클라이언트의 보낼편지함 규칙(R12.2 — `request_id` 로 한 번 반영 · 409 는 자동 병합 안 함)을 그대로 쓴다.
  [검증] 중앙을 끈 채 보고 → 쌓임 → 켜면 한 번 반영.

### 3.6 화면 (R22)

- **R22.1 로컬 웹 먼저** — 중계는 `127.0.0.1` 에 그 PC 의 세션 · 받은편지함 · 승인 대기 · 허용 목록을 보여 준다. 중앙 허브 화면(`/ui/`, 2.0 §4.7)의 자산 · 인증 방식(2.0 R13.2a)을 재사용한다.
  [검증] 실브라우저(CDP)로 로컬 화면 — 세션 목록 · 승인 1건 처리.
- **R22.2 중앙 화면에 오케스트레이션 판** — 중앙 허브 화면에 프로젝트의 세션 · 상태(`unknown` 수 따로) · 배정 · 미전달 · 승인 대기를 더한다.
  [검증] 실브라우저로 각 칸 · `unknown` 수 표시.
- **R22.3 VS Code 확장은 껍데기만** — 확장은 로컬 웹을 webview 로 띄우고 상태 표시줄에 승인 대기 수를 보이는 것까지. 화면 로직은 Python 쪽 한 벌 (O8 · PURPOSE 예외). **wheel 에 싣지 않고 따로 낸다** — 2.0 R0.3 'wheel 에 Python 아닌 실행 코드 없음' 검증은 그대로 산다.
  [검증] wheel 내용 검사 통과 · 확장 묶음에 화면 로직(HTML 생성 · API 판정) 0.
- **R22.4 스탠드얼론 보류** — 필요해지면 pywebview(Python)로. 이 판 범위 밖.
  [검증] — (범위 선언)

### 3.7 안전 · 상한 (R23)

- **R23.1 상한** — PC 동시 세션 3 · 프로젝트 하루 세션 요청 10 · 세션당 대기 도구 연속 호출(일 없이) 상한(기본값 30회 = 약 1시간). 상한에 닿으면 멈추고 사람에게 알린다 (O9, 모두 기본값).
  [검증] 각 상한 +1 → 거절 · 알림 1건.
- **R23.2 정지 스위치** — owner 는 프로젝트 단위로, PC 사용자는 중계 단위로 오케스트레이션을 즉시 멈출 수 있다 — 새 배정 · 세션 요청 · 전달이 멈추고 작업 중 세션은 다음 경계에서 `release` 를 받는다.
  [검증] 정지 → 새 배정 409 · 대기 중 세션에 `release`.
- **R23.3 주입 방어** — R18.7 의 출처 제한 · R18.9 의 표시 · 되돌릴 수 없는 일은 메시지만으로 하지 않는다. 의심 메시지는 세션이 거절 ack 로 돌려보낸다.
  [검증] '저장소 지워라' · '토큰을 보내라' 배정 → 세션이 거절 ack (진입 지침 판으로 실측, 하네스 2종).
- **R23.4 이력** — 지정 · 인계 · 배정 · 전달 · ack · 세션 요청 · 승인 · 정지 전부 2.0 이력(`event`)에 남는다.
  [검증] 한 배정 왕복의 이력 줄 수 · 종류 대조.

### 3.8 판 · 호환 (R24)

- **R24.1 2.1.0, 더하기만** — 새 표 · 새 도구 · 새 칸만 더한다. 2.0 도구 이름 · 인자 · 응답 칸은 바꾸지 않는다 (O10 · G4). 응답에 칸을 더하는 것(`hub_inbox`)은 2.0 클라이언트가 모르는 칸을 무시하는지 실측한 뒤 확정한다.
  [검증] 2.0.0 선택 클라이언트 · 2.0 진입 지침 판 세션이 2.1 허브에서 그대로 돈다 (전달은 '없음').
- **R24.2 2.0 R15.3 을 연다** — 2.0 요구 R15.3 의 [검증] "2.0 도구 표에 A2A 도구 0" 은 2.0.x 에만 걸리고, 2.1 부터는 이 문서가 정한다. 2.0 요구 문서에 그 사실을 표시한다.
  [검증] 2.0 요구 문서 R15.3 에 2.1 표시 · 검사(있다면)의 판 조건.
