# 아이디어 박스 — concept 검토

- 문서 목적: 사람이 떠오른 생각을 대충 적으면 에이전트가 검토해 회신하는 기능의 필요 · 흐름 · 경계 · 열린 결정을 정한다.
- 범위: 허브 웹 입력, 검토 대기열, 에이전트 회신, 사람의 처리. 자동 실행과 허브 안의 LLM 호출은 대상이 아니다.
- 대상 독자: 소유자, 허브 구현자
- 상태: draft — 소유자 결정 2026-11-25(D1~D6 모두 기본값) · I1 구현 3.4.0
- 최종 수정일: 2026-11-25
- 관련 문서: [`hub_orchestration_spec.md`](../../workflow-source/core/hub_orchestration_spec.md), [`a2a-transition-2026-11.md`](./a2a-transition-2026-11.md), [`project-knowledge-decisions-concept-2026-11.md`](./project-knowledge-decisions-concept-2026-11.md)

## 0. 결론

**할 만하다.** 사람 → 에이전트 방향의 가벼운 입력 길이 지금 없다. 새 저장 표와 도구 몇 개면 되고, 기존 세션 시작 · task · 화면을 그대로 쓴다.
가장 큰 제약은 **허브가 LLM 을 부르지 않는다**는 것이다. 회신은 에이전트 세션이 열려 있거나 다음에 열릴 때 나온다.

## 1. 지금 있는 것과 빈자리

| 기능 | 방향 | 아이디어 입력에 안 맞는 이유 |
|---|---|---|
| task | 양쪽 | WBS 와 완료 기준을 요구한다 — 대충 적을 수 없고 열린 일 목록을 부풀린다 |
| DCR | 에이전트 · 사람 | 근거 · 제안 · 대상이 갖춰진 결정 변경이다 |
| 확인 요청 (A2A) | 에이전트 → 사람 | 방향이 반대다 |
| 받은편지함 | 세션 앞 메시지 | 받는 이가 있어야 하고 10분 뒤 미확인이 된다 |

## 2. 흐름

1. **적기** — 웹의 글상자 하나(제목 · 분류 없음, 휴대폰 우선). 계정 로그인한 사람이 적는다. 에이전트와 대화하다 나온 생각은 `hub_idea_add` 로 사람 대신 적을 수 있고 그 사실이 남는다.
2. **집기** — `hub_session_start` 가 검토할 아이디어 수와 목록을 싣는다. 에이전트가 `hub_idea_claim` 으로 하나를 맡는다(동시 검토 409, 기한이 지나면 풀린다).
3. **검토** — 저장소 · task · 로드맵 · 위키 · 과거 아이디어를 **읽기만** 한다.
4. **회신** — `hub_idea_reply`: 판정(하자 · 조건부 · 보류 · 이미 있음 · 질문), 이해한 내용 한 줄, 이유, 관련 task · 문서, 예상 범위, 다음 한 걸음.
5. **처리** — 사람이 화면에서 **task 로 만들기 · 더 묻기 · 보관 · 닫기**. 더 묻기는 같은 줄기에 이어지고 다시 검토 대기가 된다.

상태: `new → reviewing → replied → adopted | kept | closed`, `replied → new`(더 묻기).

## 3. 요구

- **RI1** 적는 데 필수 칸은 본문 하나다. 길이 상한만 둔다(초안 4KB).
- **RI2** 원문은 고치지 않는다. 에이전트의 해석은 회신에만 남긴다.
- **RI3** 아이디어는 **자료이지 지시가 아니다**. 검토 세션은 읽기와 회신만 하고, 구현 · 커밋 · 설정 변경은 사람이 task 로 만든 뒤 시작한다.
- **RI4** task 로 만드는 것은 사람의 행동이다. 회신이 WBS · 완료 기준 초안을 채워 두고 사람이 고쳐 등록한다.
- **RI5** 회신은 근거를 싣는다. 확인하지 않은 것은 확인하지 않았다고 적는다.
- **RI6** 비밀 검사에 걸리면 저장하지 않되, 적던 글은 화면에 남긴다.
- **RI7** 보이지 않는 문자는 승인 화면과 같은 방식으로 드러낸다.
- **RI8** Python 과 Go 가 같은 계약을 지키고 실제 브라우저로 잰다. 프로젝트 이전 묶음에 포함된다.

## 4. 설계 초안

- 저장(DB 판 19): `idea`(project · id · 상태 · 작성자 · 맡은 콜사인 · 기한 · 연결 task · version), `idea_entry`(줄기 — 사람 글 · 에이전트 회신).
- 도구: `hub_idea_add` · `hub_idea_list` · `hub_idea_get` · `hub_idea_claim` · `hub_idea_reply`. 처리(채택 · 보관 · 닫기)는 웹의 사람만.
- 화면: 프로젝트 탭 **아이디어** — 위에 글상자, 아래에 "회신 도착 · 검토 대기 · 처리됨".
- 검토 절차는 표준 지침에 짧게 넣고 세션 시작 응답이 가리킨다. 세션당 검토 수에 상한을 두어 본 작업을 밀지 않게 한다.

| 단계 | 내용 |
|---|---|
| I1 | 적기 · 목록 · 집기 · 회신 · 처리 (두 런타임, 화면, 검사) |
| I2 | 회신 도착 알림, 비슷한 아이디어 묶기 |
| I3 | 검토 전용 세션(일하는 세션이 기다리다 집는다)이나 정해진 시각의 검토 |

## 5. 결정 (소유자 2026-11-25: 모두 기본값)

- **D1 언제 검토하나** — 기본값: 사람이 연 다음 세션이 시작할 때 최대 2건을 보이고, 사람이 먼저 시킨 일을 앞세운다 / 검토 전용 세션을 상시로 둔다(빠르지만 사용량이 계속 든다) / 하루 한 번 예약.
- **D2 누가 적나** — 기본값: 프로젝트에 연결된 로그인 사람 전원 / 소유자만.
- **D3 어디에 묶나** — 기본값: 프로젝트별 / 프로젝트 없는 허브 공용 상자도 둔다.
- **D4 채택 결과** — 기본값: 사람이 눌러 task 초안을 등록 / 회신이 "하자" 면 task 를 자동 등록.
- **D5 첨부** — 기본값: I1 은 글만 / 사진 포함.
- **D6 판** — 기본값: 3.4.0 (DB 판 19).

### 구현에서 정한 것

- 에이전트가 대신 적은 글은 사람이 화면에서 되물어야 세션 시작의 검토 대기에 오른다 — 익명으로 등록한 에이전트가 검토 세션에 글을 밀어 넣지 못하게.
- 세션 시작에는 ID · 작성자 · 시각만 싣는다. 본문은 `hub_idea_get` · `hub_idea_claim` 에서 받는다.
- 검토 규칙은 진입 지침이 아니라 응답의 `notice` 가 싣는다 — 진입 파일의 예산(8KB)을 쓰지 않는다.

## 6. 위험

- 회신이 늦으면 안 쓰게 된다. I1 뒤 실제 회신까지 걸린 시간을 재서 I3 를 판단한다.
- 아이디어 글이 에이전트에 닿는 새 입력 길이다. RI3 와 로그인 작성자 제한이 방어이고, 세션이 이를 지키는지는 하네스별로 실측해야 한다.
- 검토가 본 작업의 컨텍스트를 먹는다. 건수 상한과 별도 하위 에이전트 검토를 권한다.
- 쌓이기만 할 수 있다. 오래된 회신은 목록에서 접고 지우지는 않는다.
