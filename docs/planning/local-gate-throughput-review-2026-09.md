- 문서 목적: push 게이트(`run_all_checks.py --branch-context=all`)의 벽시계를 **같은 전량을 더 싸게** 돌리는 방향으로 줄일 수 있는지, 어느 수단이 얼마를 줄이는지 실측으로 판단 가능한 형태로 정리한다 (TASK-2026-09-23-main-019, M-014/WBS-14.1).
- 범위: 게이트 두 축의 벽시계·CPU 실측, 병렬 구간이 무엇에 묶여 있는가(임계경로 vs 처리량), 실행 순서·동시 실행 수·반복 계산·축 병렬화의 이득 상한, 제약(정숙 구간·워킹 트리 락·temp guard), 소유자 선택지
- 대상 독자: 소유자 (M-014 다음 단계 결정), maintainer
- 상태: **종결 (2026-09-28)** — 소유자 결정 = **① 안** (A LPT 순서 + B `--jobs auto` 상한을 코어 수로 — 러너 변경 1건, C 반복 계산 제거는 M-007/WBS-7.2 결함 수리로 건별, `wiki_score` 부터). 두 축 동시 실행(D)은 §4 근거로 기각
- 최종 수정일: 2026-09-28
- 관련 문서: [`M-014`](../../ai-workflow/memory/active/roadmap/M-014-ci-gate-throughput.md), [TASK-2026-08-14-main-004 게이트 축소 기각](../../ai-workflow/memory/active/main/backlog/tasks/TASK-2026-08-14-main-004.md), [`test-impact-tiering-review-2026-08.md`](./test-impact-tiering-review-2026-08.md)

## 0. 한 줄 결론

> **결정 (2026-09-28, 소유자)**: ① 안 채택. 구현 완료 기준에 같은 설정 2회 실측 + 시뮬레이션 추정치 대조를 넣는다 (§5).

> **게이트의 병렬 구간은 가장 긴 검사가 아니라 CPU 처리량에 묶여 있다.** 가장 긴
> 검사(k=8 에서 35~40s)는 병렬 구간의 처리량 하한(89~94s)의 절반 이하다. 그래서 임계경로 단축과 두 축
> 동시 실행은 지금 이득이 없고(시뮬레이션 0s), 효과가 있는 수단은 셋이다:
> ① **실행 순서를 긴 것 먼저로** (알파벳순 → LPT, push 당 −35s, 결과 불변)
> ② **`--jobs auto` 상한 8 을 코어 수로** (12스레드 호스트 실측 −29s, ①과 합치면
> 시뮬레이션 −69s = −25%) ③ **검사 내부 반복 계산 제거** (CPU 합을 직접 줄이는
> 유일한 수단 — 처리량이 묶여 있으므로 줄인 CPU 초가 대략 1/job수 만큼 벽시계로 온다).
> **권고: ①+② 를 러너 변경 하나로 묶고, ③ 은 M-007/WBS-7.2 결함 수리로 하나씩.**

## 1. 전제 — 무엇을 하지 않는가

- **게이트 축소는 하지 않는다.** 조건부 1축 생략·동적 선택은 기각됐다
  (TASK-2026-08-14-main-004, 53차 규칙 "전량 게이트는 필터로 대체되지 않는다").
  이 검토의 모든 수단은 **같은 294 검사 × 2 컨텍스트**를 돈다.
- **CI 는 없다** (2026-09-23 TASK-2026-09-23-main-022). M-014 착수 시점의 CI 실측
  (smoke 334s, 4 vCPU 포화)은 대상이 사라졌고, 2026-09-25 소유자 결정으로 범위가
  로컬 push 게이트로 바뀌었다. Linear 글의 원칙 중 **셋업 반복 제거 → 임계경로 →
  시간 기준 분배** 순서는 그대로 대입한다. 기계 간 샤딩은 로컬에 없으므로 **한 기계
  안의 스케줄링**으로 옮겨 읽는다.
- **in-process 실행은 가져오지 않는다.** 검사당 고정비(기동 + kit import)는 ~40ms
  로 병목이 아니다 (M-014 착수 실측).

## 2. 실측 (2026-09-28, Linux 호스트)

**호스트**: 13th Gen Intel i5-1335U — 12 스레드 (P코어 2 × HT + E코어 8), 저전력
U 시리즈, RAM 14GB. 해석기는 재생성한 `.venv` 의 **Python 3.14.4**. `--tmp-dir` 는
실디스크(`/var/tmp`).

### 2.1 게이트 전량 3회

| 실행 | `--jobs` | native | slash | 합 (`real`) | CPU (`user`+`sys`) |
|---|---|---|---|---|---|
| gate1 | auto(=8) | 133.1s | 134.5s | 267.9s | 1439s |
| gate2 | auto(=8) | 139.8s | 137.4s | 277.5s | 1512s |
| gate3 | 12 | 123.5s | 124.8s | 248.6s | 1794s |

- 세 실행 모두 **exit 1, 축당 red 2건, 같은 2건**이다 (§6 — 이 검토와 무관한 호스트
  상태 red). `--jobs 12` 에서 **새로 생긴 red 는 0건**이다.
- 같은 설정의 두 실행(gate1·gate2) 차이는 3.6% 다. 첫 실행이 새 venv 의 `.pyc`
  생성 비용을 치렀을 가능성은 gate2 가 더 느렸으므로 배제한다.
- 89차 macOS 10코어 기준선은 축당 92~97s 였다. 이 호스트가 ~40% 느리다.

### 2.2 병렬 구간은 무엇에 묶여 있는가

축 하나(gate2 native, `--jobs 8`)를 풀면:

| 항목 | 값 |
|---|---|
| 검사 수 | 294 (병렬 283 + 정숙 구간 11) |
| 검사별 소요 합 | 767s (병렬 739s + 정숙 28s) |
| 1초 미만 검사 | 170개 |
| 상위 8개 비중 | 소요 합의 32% |
| 가장 긴 검사 | `mypy_config_actually_loaded` 37.5s · `wiki_score` 37.0s · `branch_context_matrix` 35.8s |
| **처리량 하한** (병렬 합 / 8 + 정숙) | **120s** |
| 임계경로 하한 (최장 검사) | 37.5s |
| 실측 | 139.8s |

**처리량 하한이 최장 검사의 3배다.** 병렬 구간은 한 검사를 기다리는 것이 아니라
8개 슬롯이 다 찰 만큼 일이 많은 상태다. 실측과 하한의 차이(~20s)는 **꼬리**, 즉
끝물에 슬롯이 비어 있는 시간이다.

정숙 구간(`REQUIRES_QUIET_REPO`, 11개)은 축당 28s 로 일정하다. 최대는
`source_without_runtime_layer` 7.7s · `parallel_smoke` 6.4s 다.

### 2.3 스케줄 시뮬레이션 — 모델 검증

러너는 병렬 구간의 검사를 **알파벳순으로 제출**한다 (`run_all_checks.py` 의
`ThreadPoolExecutor` 에 `sorted(glob)` 순서 그대로). 측정한 검사별 소요 시간으로
"빈 슬롯에 다음 검사를 넣는" 스케줄을 재현하면 실측과 맞는다:

| 실행 | 실측 | 시뮬레이션 (알파벳순) |
|---|---|---|
| gate1 native (k=8) | 133.1s | 133s |
| gate1 slash (k=8) | 134.5s | 134s |
| gate2 native (k=8) | 139.8s | 139s |
| gate3 native (k=12) | 123.5s | 123s |
| gate3 slash (k=12) | 124.8s | 125s |

오차 1s 이내다. 그래서 순서만 바꾼 경우는 이 모델로 추정한다. 단 **입력 소요 시간은
그 실행의 부하에서 잰 값**이다 — 순서가 바뀌면 어느 검사가 겹치는지도 바뀌므로 §4 의
LPT 수치는 추정이고, 구현 후 실측으로 확인해야 한다.

### 2.5 temp guard 는 제약이 아니다

`MAX_AUTO_JOBS = 8` 의 근거는 "동시 temp 사용량이 guard 의 2GB 상한에 닿는다" 였다
(`run_all_checks.py` 주석). 이번 실측에서 **검사 하나의 temp 최대치는 20MB** 였다
(`tmp_peak_mb`, 세 실행 공통). 12개가 동시에 최대치를 찍어도 240MB 로 상한의 12%
다. 상한의 근거가 지금은 성립하지 않는다.

## 3. 반복 계산 — CPU 합을 줄이는 쪽

처리량에 묶인 게이트에서는 **CPU 합을 줄이는 것만이 모든 호스트에서 확실한 이득**이다
(순서·슬롯 수는 호스트 코어 수에 따라 효과가 다르다). M-014 착수 시점에 이미 두 건을
결함으로 닫았다 — `check_root_anchor_audit` (26s → 6s, main-020)과
`check_release_summary_v0_11_15` 의 CI 조회 제거 (main-021).

이번에 하나를 더 찾았다:

- **`check_wiki_score`** — 단독 27.3s 가 전부 점수 도구 subprocess 3회 (1회 9.1s)다
  (cProfile). `test_tool_runs` 가 1회, `test_score_idempotent` 가 **공유 실행
  `_score_once()` 를 쓰지 않고** 2회를 새로 돈다. 멱등성 판정은 "독립된 두 실행의
  점수가 같다" 이므로, 한쪽을 공유 실행으로 바꿔도 판정의 의미는 그대로다 →
  **3회 → 2회, 단독 −9s (−33%)**, 두 축이면 CPU 합 −18s 이상 (부하 늘어짐 포함).

상위 11개의 단독 합은 160s, 게이트 안의 합은 축당 ~290s 로 **소요 합의 39%** 다.
이 11개를 대상으로 "같은 인자의 subprocess 반복"을 전수로 세는 것이 다음 조사다.
M-014 착수 시점의 방법(cProfile 로 subprocess 호출 수 · 파싱 횟수)을 그대로 쓴다.
**결과가 같아야 한다는 조건**은 case 마다 되주입으로 확인한다 — 캐시가 case 간
독립성을 깨면 검사가 무력화된다 (메모리: 검사는 깨지지 않고 무력화된다).

## 4. 수단별 이득 상한

gate2(`--jobs 8`) 와 gate3(`--jobs 12`) 의 검사별 소요로 시뮬레이션했다. 두 축 합, push 당.

| 수단 | 현재 → 추정 | 이득 | 근거 | 위험 |
|---|---|---|---|---|
| **A. LPT 순서** (긴 것 먼저 제출) | 277s → 242s | **−35s (−13%)** | 시뮬레이션 (k=8) | 거의 없음. 판정 불변 — 검사는 각자 전용 TMPDIR·프로세스 그룹으로 격리돼 있고 정숙 구간은 그대로 |
| **B. `--jobs auto` 상한 8 → 코어 수** | 277s → 248s | **−29s (−10%)** | **실측** (gate3) | 호스트마다 다르다 (8코어 이하 호스트는 변화 0). 부하 늘어짐으로 타임아웃 상한에 가까워지는 검사가 생길 수 있다 (`branch_context_matrix` 48.8s, 상한 150s) |
| **A+B** | 277s → 208s | **−69s (−25%)** | 시뮬레이션 (k=12, gate3 소요) | 위 둘의 합 |
| C. 반복 계산 제거 | 건별 | `wiki_score` 1건만으로 CPU −18s+ (벽시계로는 ~1/k) | cProfile | case 독립성 — 건마다 되주입 |
| D. 두 축 동시 실행 (한 풀 또는 worktree 2개) | 242s → 242s (A 적용 후) | **0s** | 시뮬레이션 (k=8·12 모두 0) | 워킹 트리 락 우회 또는 worktree 셋업 비용만 늘어난다 |
| E. 임계경로 단축 (`branch_context_matrix` 등) | — | 지금은 0 | 최장 검사 < 처리량 하한 | A+B+C 로 처리량 하한이 45s 아래로 내려가야 의미가 생긴다 |

**D 가 0 인 이유**: 알파벳순에서는 축마다 꼬리가 있어 두 축을 섞으면 꼬리를 메울 수
있지만, LPT 로 꼬리를 먼저 없애면 남는 것은 처리량뿐이고 처리량은 섞어도 같다.
M-014 후보 ⑤(로컬 두 축 동시 실행)는 **이 근거로 기각을 권한다**.

**A 의 소요 시간 출처**: LPT 는 "어느 검사가 긴가" 를 알아야 한다. 선택지는 (a) 직전
게이트 실행의 검사별 소요 기록, (b) 검사 파일 안의 정적 선언(`CHECK_TIMEOUT_S` 처럼),
(c) 둘 다 없으면 알파벳순 fallback. (a)는 호스트마다 자동으로 맞지만 기록이 없는 첫
실행과 새 검사를 다뤄야 한다. 어느 쪽이든 **fallback 을 썼다는 사실을 출력에
남긴다** (메모리: 조용한 fallback 은 출처를 내놓아야 한다).

## 7. 한계

- **호스트 하나, 표본이 작다.** k=8 은 2회, k=12 는 1회다. i5-1335U 는 코어가
  이종이고 전력 한도가 낮아, 10코어 macOS(89차 호스트)에서는 B 의 이득이 다를 것이다.
  B 를 채택하면 macOS 호스트에서도 한 번 잰다.
