## 0. 요약

`python -m workflow_kit workbench` 가 작업 공간 호스트에서 표준 라이브러리 HTTP 서버를 띄운다. 기본 bind 는
`127.0.0.1` 이고, 어디서 접속하든 **항상 인증**한다(viewer / approver, 이름 붙은 토큰). 화면의 모든 링크 · 폼 · 리다이렉트는
**상대 경로**라 경로 접두사가 붙는 프록시 뒤에서도 그대로 동작한다 (§1.3 실측). approver 가 결정 폼을 제출하면 서버는
주장 R5 형식의 응답 파일을 받은편지함에 **다 쓴 뒤 한 번에 공개**한다 (§1.2 실측). 세션 알림은 당겨 오기(① — 보고와 MCP)만
만든다: 프롬프트 직전 hook 의 **주입**이 실측된 하네스는 지금 하나뿐이다 (§1.1).

### 1.3 경로 접두사 프록시 뒤 — 쿠키 · 리다이렉트 · 폼 · CSRF

프록시는 **프로토타입**이다: `/workbench` 접두사를 벗겨 넘기고 `Set-Cookie` · `Location` 을 고치지 않는다
(nginx `location /workbench/ { proxy_pass http://backend/; }` 의 동작을 흉내 낸 것). **nginx · Caddy 실물은 재지 않았다** —
이 호스트에 없다 (R11).

| 구성 | 로그인 뒤 도착 | 쿠키 `Path` | 폼 action 이 가리키는 곳 | 제출 뒤 도착 | 접두사 밖 경로에 쿠키가 실리나 |
|---|---|---|---|---|---|
| 직접 (`public_url` = 서버 주소) | `/` 200 | `/` | `/task/T1/respond` | `/task/T1` 200 | 실린다 (접두사가 없으니 당연) |
| 프록시 + 상대 리다이렉트 + `Path` = 접두사 | `/workbench/` 200 | `/workbench/` | `/workbench/task/T1/respond` | `/workbench/task/T1` 200 | **실리지 않는다** |
| 프록시 + **절대** 리다이렉트 `Location: /` (음성 대조) | `/` **404** (접두사 밖) | `/workbench/` | (같음) | `/task/T1` **404** | 실리지 않는다 |
| 프록시 + 쿠키 `Path=/` (음성 대조) | `/workbench/` 200 | `/` | (같음) | 200 | **실린다** — 같은 호스트의 다른 앱이 세션 쿠키를 받는다 |

로그인은 `POST login`(토큰은 본문)으로 쟀다 — `GET login?token=…` 은 400 으로 거절된다. 쿠키가 어느 경로에 실리는지는 Python
`http.cookiejar` 로 판정했다 (브라우저가 아니다 — `SameSite` 는 평가되지 않았다, R11).

모든 구성에서 같았던 것: 출처가 다른 POST (`Origin: http://evil.example`) → 403 · CSRF 토큰 불일치 → 403 · 쿠키 없는 POST → 401 ·
256KB + 1 바이트 본문 → 413 · viewer 세션의 계획 페이지에 폼 없음. 출처 대조는 `public_url` 에서 만든 출처와 요청의 `Origin` 을
비교했다 — 프록시 뒤에서 서버가 보는 `Host` 는 백엔드 주소라 `Host` 로는 맞출 수 없다.

결론: **상대 경로**(링크 · 폼 action · `Location`)와 **`Path` = `public_url` 의 경로**가 요구 사항이다 (R2.3 · R3.4). 둘 다 서버가
자기 주소를 추측하지 않고 `public_url` 하나에서만 얻는다.

### 1.4 실물 프록시 · 실제 브라우저 (design 전 실측, 2026-11-13, TASK-2026-11-13-claude-remote-sync-check-234c32-006)

R11 의 "design 전" 둘째 행이다. §1.3 과 같은 프로토타입 서버(표준 라이브러리, 측정 전용 — 저장소에 남기지 않는다)를 구성별로 띄우고,
그 앞에 **실물** 프록시를, 뒤에서 **실제 브라우저**로 로그인 → 계획 → 제출 → 다른 앱 → 다른 사이트의 링크 · 폼 순서로 잰다.

- 프록시: `nginx:1.27.5-alpine` (`sha256:65645c7b…2a10`) — `location /workbench/ { proxy_pass http://127.0.0.1:<port>/; }`,
  `caddy:2.10.0-alpine` (`sha256:ae445863…a3c`) — `handle_path /workbench/* { reverse_proxy 127.0.0.1:<port> }`. 둘 다 `Set-Cookie` · `Location` 을 고치지 않는다.
- 브라우저: Google Chrome 154.0.8037.57 (headless). 조작은 `playwright-core` 1.63.0 이 하고, 쿠키를 실을지는 **브라우저가** 판정한다.
- 같은 호스트의 다른 앱 = 같은 프록시의 `/other/` (받은 `Cookie` 머리를 그대로 돌려준다). 다른 사이트 = `http://localhost:<port>` 의 페이지
  (서버는 `127.0.0.1` — 둘은 다른 사이트다).
- 9 구성 × 2 회, 두 회의 결과가 같았다. 표는 nginx 와 Caddy 가 같았던 열을 합친 것이다.

| 구성 | 세션 없이 루트 | 로그인 뒤 | 쿠키 | 제출 뒤 | 다른 앱에 쿠키 | 다른 사이트의 링크 | 다른 사이트의 POST |
|---|---|---|---|---|---|---|---|
| 직접 | `/login` 200 | `/` 200 | `Path=/` · `Strict` | `/task/T1?ok=1` 200 | 실린다 (접두사 없음) | `/login` (쿠키 안 실림) | 403 · 쿠키 안 실림 |
| 상대 리다이렉트 + `Path` = 접두사 · `Strict` | `/workbench/login` 200 | `/workbench/` 200 | `Path=/workbench/` · `Strict` | `/workbench/task/T1?ok=1` 200 | **실리지 않는다** | `/workbench/login` (쿠키 안 실림) | 403 · 쿠키 안 실림 |
| **절대** `Location` (음성 대조) | `/login` — nginx 404, Caddy **빈 200** (접두사 밖) | `/` 접두사 밖 | `Path=/wb-abs/` | `/task/T1?ok=1` 접두사 밖 | 실리지 않는다 | `/login` 접두사 밖 | 403 |
| 쿠키 `Path=/` (음성 대조) | 200 | 200 | `Path=/` | 200 | **실린다** | 로그인 화면 | 403 · 쿠키 안 실림 |
| 상대 리다이렉트 + `Path` = 접두사 · **`Lax`** | 200 | 200 | `Path=/wb-lax/` · `Lax` | 200 | 실리지 않는다 | **`/wb-lax/task/T1` 200 (쿠키 실림)** | 403 · 쿠키 안 실림 |

- §1.3 의 네 열은 실물 프록시 · 실제 브라우저에서도 같다. 상대 경로 + `Path` = 접두사가 요구 사항이라는 결론은 그대로다.
- **새로 본 것 — `SameSite=Strict` 와 다른 사이트의 링크**: 웹 채팅 · 코드 리뷰 댓글 같은 **다른 사이트의 링크**로 계획 화면에 들어오면
  `Strict` 쿠키는 실리지 않아 로그인 화면으로 떨어진다 (로그인한 상태여도). 주소창에 치거나 같은 사이트 안에서 이동하면 실린다 (마지막 행의
  "다시 열기" 200). `Lax` 는 다른 사이트의 **링크(GET)** 에는 쿠키를 싣고 **POST** 에는 싣지 않는다 — 두 설정 모두 다른 사이트의 POST 는
  쿠키 없이 왔고 `Origin` 대조가 403 으로 막았다. → design 결정 (ADR-032).
- **Caddy 는 매치되지 않는 경로에 빈 200 을 준다** (nginx 는 404) — 접두사 밖으로 떨어져도 상태 코드로는 드러나지 않는다. 검사는 상태가
  아니라 도착 경로로 판정해야 한다.
- **끝 슬래시 없는 접두사**: nginx 는 `/workbench` → `/workbench/` 301 (위 `location` 으로 자동), Caddy 는 `handle_path /workbench/*` 가
  `/workbench` 를 매치하지 않아 빈 200 이다 — Caddy 예시에는 `redir /workbench /workbench/` 한 줄이 필요하다. `public_url` 은 끝 슬래시를 갖는다.
- 재지 않은 것: TLS 뒤의 `Secure` 쿠키(로컬 인증서 없음 — `Secure` 는 `https` `public_url` 에서만 붙이는 규칙이라 경로 판정과 독립),
  Firefox · Safari(이 표는 Chrome 하나다), 클라우드 작업 공간의 포트 공유.

## 2. 불변 조건 (R0)

1. **Claude 전용 표면에 기대지 않는다.** 서버 · 화면 · 알림은 파일 · CLI · MCP · 표준 HTTP 로만 선다.
2. **서버가 워크플로우 상태로 쓰는 곳은 받은편지함(`plan_responses/inbox/`) 하나다** (주장 R0-5, concept §1-2). task 파일 · 보관 경로 ·
   `state.json` · `roadmap_state.json` 은 **읽기만** 한다. 그 밖에 쓰는 것은 자기 실행 기록 한 파일(R1.3, gitignore)뿐이고,
   접근 기록은 파일이 아니라 표준 오류로 낸다 (R4.3).
3. **응답은 데이터다.** 서버는 폼으로 들어온 어떤 문장도 실행하지 않고, 경로로 쓰지 않고, 다른 곳으로 보내지 않는다.
4. **진척을 만들어 내지 않는다.** 화면의 숫자는 생성물과 task 파일에서만 오고, 재지 않은 것은 "미측정" 이다.
5. **접속 위치를 가정하지 않는다.** loopback 요청도 인증한다. 서버는 자기 공개 주소를 추측하지 않는다 (`public_url` 설정 하나).
6. **외부 자원 0.** 페이지는 CDN · 외부 글꼴 · 외부 스크립트를 부르지 않는다 — 오프라인에서 그대로 보인다.
7. **모델 호출 없음.** 서버는 결정적이다.
8. **파서 · 계산은 하나다.** 주장 · 결정 읽기, 계획 지문, 결정 상태 계산은 주장 R0-6 · R6.3 의 같은 함수를 쓴다.

## 3. 명령과 수명 (R1)

### R1.1 명령

`python -m workflow_kit workbench [옵션]` — 서버를 띄우고 끝날 때까지 앞에서 돈다.

| 옵션 | 뜻 | 기본 |
|---|---|---|
| `--bind <주소>` | 듣는 주소 | `127.0.0.1` |
| `--port <n>` | 듣는 포트. 사용 중이면 **실패**한다 — 다른 포트로 옮겨 가지 않는다 (포워딩 · 프록시 설정이 포트에 묶인다) | `8766` (`registry_server` 의 기본 8765 와 겹치지 않게) |
| `--public-url <URL>` | 브라우저가 보는 주소 (스킴 · 호스트 · 포트 · 경로 접두사). 출처 대조 · 쿠키 `Path` · 시작 시 출력 URL 의 유일한 원천 | `http://127.0.0.1:<port>/` |
| `--token <role>:<name>=env:<변수 이름>` 또는 `=file:<경로>` | 토큰 하나 (반복 가능). 값은 인자로 받지 않는다 | 없음 — **토큰이 하나도 없으면 시작하지 않는다** |
| `--trusted-proxy <주소>` | 이 주소에서 온 요청의 `X-Forwarded-For` 만 믿는다 (반복 가능) | 없음 |
| `--tls-cert <경로>` · `--tls-key <경로>` | 내장 TLS (표준 `ssl`, TLS 1.2 이상) | 없음 |
| `--allow-plain-http` | loopback 이 아닌 주소에 TLS 없이 여는 것을 허용 — "같은 망 한정" 선언 (W6) | 꺼짐 |
| `--status` | 실행 중인 서버의 기록(R1.3)을 JSON 으로 보이고 끝난다 | — |
| `--new-token <role>:<name> --out <경로>` | 토큰을 만들어 `0600` 파일로 쓰고 끝난다 (값은 출력하지 않는다) | — |

모르는 인자는 거절한다. 시작할 때 `public_url` 을 출력한다 — 출처 대조가 그 값에 묶이므로(`127.0.0.1` 과 `localhost` 는 다른 출처다),
출처가 어긋난 요청의 403 화면은 서버가 기대하는 출처를 보인다. TLS 를 켰는데 `--public-url` 이 `http` 면 시작하지 않는다.
`--bind` 가 loopback 이 아닌데 TLS 도 `--allow-plain-http` 도 없으면 시작하지 않는다.
loopback 이 아닌 bind 는 시작할 때 경고 한 줄을 낸다.

### R1.2 §11.1 문구

정본 `workflow-source/core/global_workflow_standard.md` §11.1 에 한 줄: `Review plans and progress in a browser: python -m workflow_kit workbench`.
(`plan-import` 줄은 주장 R10 이 더한다.) 플러그인 스킬은 §11.1 과 1:1 이라 `workbench` 스킬 하나가 는다 — 스킬 본문은
"서버를 띄우는 방법과 URL 을 사용자에게 알리는 것" 까지이고, 모델이 서버를 대신 조작하지 않는다.

### R1.3 수명

- `session-start` 는 서버를 **띄우지 않는다** (세션마다 프로세스가 쌓인다). 실행 중이면 그 사실과 `public_url` 을 보고에 싣는다.
- 실행 기록: **checkout 루트의** `.workbench/server.json` — `pid` · `port` · `public_url` · `started_at`. gitignore. 토큰 · 세션은 싣지 않는다.
  브랜치 메모리 아래가 아니다 — 서버는 브랜치가 아니라 checkout 에 묶이고, 띄워 둔 채 브랜치를 바꿔도 같은 기록이 보여야 한다
  (worktree 는 각자 루트가 있어 각자 기록을 갖는다). `.workbench/` 와 `plan_responses/inbox/` 를 무엇이 무시하게 하는지(저장소
  `.gitignore` 줄인지, 디렉터리 안의 자기 무시 파일인지)는 design 이 정한다 — 주장 M-026 의 같은 질문과 함께.
- **checkout 하나에 서버 하나.** 기록의 `pid` 가 살아 있으면 시작을 거절하고 그 URL 을 알려 준다. 죽은 `pid` 의 기록은 덮어쓴다.
- 서버는 요청마다 현재 브랜치를 다시 읽는다 — 띄워 둔 채 브랜치를 바꾸면 그 브랜치의 계획 · 받은편지함을 본다. 화면 머리에
  브랜치 이름을 보인다.
- 세션은 메모리에만 있다 — 서버를 다시 띄우면 다시 로그인한다.

## 4. 경로와 화면 (R2)

### R2.1 경로 — 이것 말고는 404

| 메서드 · 경로 (`public_url` 기준 상대) | 역할 | 인증 |
|---|---|---|
| `GET healthz` | `ok` 두 글자. 다른 정보 없음 (프록시 상태 확인용) | 없음 |
| `GET login` · `POST login` | 토큰 입력 폼 · 세션 시작 | 없음 |
| `POST logout` | 세션 끝 | 세션 |
| `GET ` (루트) | 진척 화면 (R6) | viewer 이상 |
| `GET task/<TASK-ID>` | 계획 화면 — 주장 트리 · 결정 · 범위 밖 · 완료 기준 (R2.4) | viewer 이상 |
| `POST task/<TASK-ID>/respond` | 결정 응답 제출 (R5) | approver |
| `GET api/state` | 진척 화면과 같은 내용의 JSON, `"schema": "workbench-state/1"` | viewer 이상 |
| `GET static/<이름>` | 서버에 내장된 스타일 · 스크립트 (고정 목록) | 없음 |

`<TASK-ID>` 는 task ID 문법(`project_docs` 의 정본 패턴)에 맞고 현재 브랜치에 그 task 파일이 있을 때만 받는다 — 경로 조각으로
파일 시스템을 가리킬 수 없다.

### R2.2 응답 머리

모든 응답에 `Content-Security-Policy: default-src 'none'; style-src 'self'; script-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`,
`X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` (`static/` 는 예외). 인라인 스크립트 · 인라인 스타일을
쓰지 않는다.

### R2.3 상대 경로

페이지의 모든 링크 · 폼 action · `Location` 은 **상대 경로**다 (§1.3 — 절대 `Location` 은 접두사 밖 404 로 떨어졌다).
절대 URL 이 나오는 곳은 시작 시 출력하는 주소 하나이고 `public_url` 에서 만든다.

### R2.4 계획 화면

task 파일에 **이미 있는 것만** 그린다 — 근거 자료(목업 · 호출 스택)는 그리지 않는다.

- 주장 트리: `<details>` 로 접는다. 접힌 상태가 1단계 주장 목록이다. 번호는 task 파일의 `C` ID 그대로.
- 3단계 `@ path:line`: 경로와 줄만. 코드 발췌는 싣지 않는다.
- 완료 기준과 `Verification` 줄: `[C<id>]` 인용으로 주장 아래에 묶는다 (주장 R4 의 묶음과 같은 계산).
- 결정: 가리키는 주장 안에 `<details>` 하나씩 — 질문, 선택지(radio), 기본값에 "추천" 표시와 `checked`, 지금 상태(주장 R6.3 의 **계산값**).
  머리에 "열린 결정 n건" 을 센다.
- `answered` 인 결정은 **읽기 전용**으로 보인다 (답과 함께). 웹 응답으로 덮을 수 없다 (주장 R6.3).
- `Out of scope` 는 끝에.
- 주장이 없는 task 는 Description · 완료 기준 · Plan 의 나머지 필드를 그대로 보인다 (폼 없음).
- viewer 에게는 폼이 없다 — 같은 내용을 읽기 전용으로.

## 5. 인증 · 권한 (R3 · R4)

### R3.1 토큰

- 역할은 `viewer` · `approver` 둘이다. 토큰마다 **이름**이 있고(`[A-Za-z0-9_-]{1,32}` — 주장 R5.3 의 `responder` 32자 이하), 이름은
  유일하다.
- 값은 **환경변수 이름** 또는 **파일 경로**로만 받는다. 파일은 POSIX 에서 모드가 `0600` 보다 넓으면 거절한다.
- 값은 32자 이상이어야 한다 (`--new-token` 은 `secrets.token_urlsafe(32)` — 256비트). 짧으면 시작하지 않는다.
- 비교는 상수 시간(`hmac.compare_digest`).
- 토큰을 거두는 방법은 값을 바꾸고 서버를 다시 띄우는 것이다 — 세션이 메모리에만 있어 그때 모두 끊긴다.

### R3.2 로그인 (Q1)

- 토큰은 **`POST login` 의 본문으로만** 받는다. URL 질의로 받지 않는다 — 프록시 로그 · 브라우저 기록 · `Referer` 에 남는다.
- 성공하면 세션 쿠키를 주고 상대 경로로 리다이렉트한다. 실패는 401 과 같은 폼.
- 실패 제한: 같은 요청자 주소에서 1분 안에 5회 실패하면 그 주소의 로그인을 60초 동안 429 로 막는다. 요청자 주소는 연결의
  상대 주소이고, `--trusted-proxy` 에서 온 요청만 `X-Forwarded-For` 의 마지막 값을 쓴다. 포워딩 · 터널이나 `--trusted-proxy` 없는
  프록시 뒤에서는 모든 사용자가 한 주소로 보여 **함께** 막힌다 — 알고 받아들이는 한계다 (막히는 쪽이 안전한 쪽이다).
- `POST login` · `POST logout` 도 `Origin` 을 대조하고 본문은 4,096 바이트 이하만 받는다. `POST logout` 은 CSRF 값도 대조한다.

### R3.3 세션

- 쿠키 `wb_session` — `HttpOnly` · `SameSite=Strict` · `Path` = `public_url` 의 경로 · `public_url` 이 `https` 면 `Secure`.
- 값은 서버가 만든 무작위 128비트 이상, 서버 메모리의 표로만 사용자 · 역할에 묶인다.
- 수명 12시간 (작업일 하나). 지나면 다시 로그인한다.

### R3.4 쿠키 경로

`Path` 는 `public_url` 의 경로다 — `/` 로 두면 같은 호스트의 다른 앱이 세션 쿠키를 받는다 (§1.3 넷째 행).

### R4.1 `POST task/<TASK-ID>/respond` 의 대조 — 순서대로, 하나라도 어긋나면 아무것도 쓰지 않는다

1. `Content-Length` 가 있고 **262,144 바이트(256KiB) 이하**다 (없으면 411, 넘으면 413 — 본문을 읽기 전에, 그리고 그 연결을 닫는다).
2. 세션이 있고 역할이 `approver` 다 (401 · 403).
3. `Origin` 이 `public_url` 의 출처와 같다 (없거나 다르면 403).
4. 폼의 CSRF 값이 그 세션의 것과 같다 (403). 값은 세션마다 다르고 상수 시간으로 비교한다.

### R4.2 위임 인증 (Q2)

신뢰 프록시의 사용자 머리로 로그인을 대신하는 것은 W7 이 "선택 · 기본 꺼짐" 으로 둔 것이다. **첫 구현 범위에 넣지 않는다** —
`--trusted-proxy` 는 요청자 주소 판정(R3.2)에만 쓴다. 넣을 때의 조건만 적는다: 신뢰 프록시에서 온 요청에 한해, 설정한 머리의
사용자 이름을 역할 표에 매핑한다.

### R4.3 기록

접근 기록은 표준 오류로 낸다 (파일에 쓰지 않는다 — R0-2). 시각 · 메서드 · 경로 · 상태 · 사용자 이름을 남긴다. 토큰 · 쿠키 · CSRF 값 · 폼 본문(주석 포함)은 남기지 않는다.

## 6. 응답 쓰기 (R5)

### R5.1 폼

- 폼은 그 task 의 **모든** 결정을 싣는다 (주장 R5.1 — 응답에는 모든 결정이 한 줄씩 있어야 한다).
  `answered` 인 결정은 고를 수 없고, 응답에는 `value` = 기본값 · `opened: no` (입장 없음)로 실린다 — 대화의 답과 다투지 않는다.
- 숨은 필드: CSRF 값, 페이지를 그릴 때 계산한 `plan_digest` (주장 R5.2), 결정별 `opened_<D id>`.
- 주석: 주장 · 결정마다 하나, 그리고 대상 없는 것 하나. 빈 칸은 싣지 않는다.

### R5.2 열림 측정 (W2 · 주장 Q6)

- 결정의 `<details>` 는 **닫힌 채** 그린다. 내장 스크립트는 한 가지 일만 한다: `toggle` 로 결정이 한 번이라도 열리면 그 결정의
  숨은 필드를 `yes` 로 바꾼다.
- 서버는 `yes` 만 `opened: yes` 로 적고 그 밖은 전부 `no` 다.
- 스크립트가 꺼진 브라우저: `<details>` 는 그대로 열리고 제출도 되지만 열림 기록이 없다 → `opened: no`. 기본값을 그대로 둔 결정은
  `unopened`, 다른 값을 고른 결정은 `changed` 다 (주장 R6.3 · Q6). 서버는 이 둘을 가르지 않는다 — `value` 와 `opened` 를 그대로 적는다.

### R5.3 쓰기

R4.1 을 통과한 뒤:

1. `plan_digest` 를 지금 task 파일에서 다시 계산해 폼의 값과 비교한다. 다르면 **409** — 쓰지 않고 "계획이 바뀌었다, 다시 열어라" 를 보인다.
2. `answered` 가 **아닌** 각 결정의 `value` 가 그 결정의 선택지 안에 있는지 본다. 아니면 422.
3. `answered` 인 결정에 대해 폼이 무엇을 보냈든 **무시**하고 `value` = 기본값 · `opened: no` 로 적는다 (R5.1 — 조작된 요청이 대화의 답과 다투는 응답을 만들지 못한다).
4. 주석의 줄바꿈을 LF 로 고친다 — 브라우저는 여러 줄 입력을 CRLF 로 보내고, 주장 R5.3 은 `\n` · `\t` 밖의 제어 문자를 거부한다.
   고친 뒤에도 남은 제어 문자가 있으면 422.
5. 응답 파일을 주장 R5.1 형식으로 만든다: `responder` = 토큰 이름, `role` = `approver`, `received_at` = 서버 시각(ISO 8601, 시간대
   오프셋, 마이크로초 — 주장 R5.1 의 예시는 초 단위지만 읽는 쪽은 소수 초를 받는다). 그 task 의 받은편지함 · 보관에 있는 **같은 응답자의 가장 늦은 `received_at`** 보다 늦지 않으면 그 값의 1마이크로초 뒤로 민다
   (주장 R6.3 — 응답자별로 겹치지 않게; 파일에서 읽으므로 서버를 다시 띄우거나 시계가 뒤로 가도 성립한다).
6. 만든 파일이 주장 R5.3 의 한도(전체 65,536 바이트 · 주석 20건 · 건당 1,000자 · 제어 문자)를 넘으면 **422** — 쓰지 않고 넘은 한도를 보인다.
7. 받은편지함에 쓴다: 같은 디렉터리의 임시 이름(`*.md` 가 아닌 이름)에 **다 쓰고**, 최종 이름 `<TASK-ID>-<n>.md` 로 **한 번에 공개**한다.
   `<n>` = 받은편지함과 보관(`.rejected.md` 포함)을 합친 가장 큰 번호 + 1 (주장 R8.1). 그 이름이 이미 있으면 다음 번호로 다시 한다. 있는 이름에는 쓰지 않는다
   (§1.2 행 2 · 4 · 5). 서버는 시작할 때 받은편지함에 남은 자기 임시 파일을 지운다 (checkout 에 서버는 하나다 — R1.3).
8. 성공하면 계획 화면으로 상대 리다이렉트(303)하고 "<응답자> 의 응답을 <received_at> 에 받았다 — 작업 세션이 `plan-import` 로 반영한다" 를 보인다.

서버는 `plan-import` 를 부르지 않고 task 파일을 고치지 않는다 (R0-2). 화면의 결정 상태는 다음 `plan-import` 뒤에 바뀐다 — 계획 화면은
"미반영 응답 n건" 을 그 사실과 함께 보인다.

### R5.5 보관 이동은 잠금 아래의 배타 이동이다 — 주장 R8.1 의 수정

1. **import 는 한 번에 하나다.** `plan-import --apply`(와 `--discard --apply`)는 그 브랜치의 `plan_responses/` 에 대한 배타 잠금을 쥐고
   돈다. 잠금을 못 쥐면 기다리지 않고 "다른 import 가 돌고 있다" 를 보고하고 끝난다 (다음 당겨 오기에서 다시 한다).
   잠금을 쥔 뒤 받은편지함을 **다시 읽는다** — 먼저 돈 쪽이 옮긴 응답은 더는 없고, 그것이 "이미 반영됨" 이다 (§1.2 행 9~11).
2. **이동은 있는 이름을 덮지 않는다.** 보관에 그 이름이 있으면 그 응답에 다음 번호를 주고 옮긴다 (§1.2 행 7 · 8). 잠금이 import 끼리만
   막고 쓰는 쪽은 막지 않으므로 이 규칙이 따로 필요하다. `.rejected.md` 로의 이동도 같다.
3. **번호는 보관될 때 바뀔 수 있다.** 받은편지함의 번호는 임시이고 보관의 번호가 정본이다 — Progress 줄(주장 R6.4)과 `plan_inbox` 는
   그때의 파일명을 싣는다. 번호는 식별자일 뿐 순서의 근거가 아니다 — 순서는 `received_at` 이다 (주장 R6.3). 서버가 제출 뒤에 보이는
   확인(R5.3-8)에는 번호가 아니라 응답자와 `received_at` 을 싣는다.
4. 쓰는 쪽(서버)은 잠금을 쥐지 않는다 — 긴 import 가 사용자의 제출을 막지 않는다.

### R5.4 256KiB 와 64KiB

둘은 층이 다르다 — 256KiB 는 **폼 인코딩된 본문**(한글 1자 = 9바이트), 64KiB 는 **만들어진 응답 파일**이다. 한글 주석 20,000자는
폼으로 180,000 바이트라 앞의 상한 안이고, 파일로는 61,259 바이트라 뒤의 상한 안이다 (주장 §1.3).

## 7. 진척 화면 (R6)

### R6.1 원천 — 이것뿐

| 보이는 것 | 원천 |
|---|---|
| 마일스톤 · WBS · 파생 진척 · issues · `deliverables_missing` | `roadmap/roadmap_state.json` |
| 진행 · 차단 · 계획 · 최근 완료 task | 브랜치 `state.json` |
| task 의 완료 기준 · 검증 줄 · 주장 · 결정 | task 파일 |
| 결정 상태 | 주장 R6.3 의 **계산값** (task 파일 + 보관된 응답) |
| 미반영 응답 건수 | `plan_responses/inbox/` 를 요청 시점에 센 값 |

### R6.2 표시 규칙

1. 선언 상태와 파생 상태가 다르면 **둘 다** 보인다.
2. 진척은 **센 값**으로 보인다 — "완료 잎 3 / 전체 4". 막대는 그 두 수에서만 그린다(내장 스타일, 외부 자원 없음).
   잎이 0 인 마일스톤은 "미측정" 이고 0% 로 그리지 않는다.
3. 검증 줄이 없는 완료 기준은 "미측정" 이다. 서버는 판정을 추론하지 않는다 — `Verification` 줄의 글을 그대로 보인다.
4. 결정 상태 칸이 계산값과 다르면 계산값을 보이고 "task 파일의 칸은 <값>" 을 덧붙인다 (주장 R6.3 — 정본은 계산값).
5. 생성물마다 `generated_at` 을 보인다. 서버는 생성물을 다시 만들지 않는다 (R0-2) — 낡았는지는 날짜로 사람이 본다.
6. **싣지 않는 것**: 작업 공간의 절대 경로 · 호스트 이름 · 사용자 홈 경로 · 환경변수 · 토큰 이름 목록. 경로는 저장소 상대로만,
   브랜치 이름은 싣는다 (W7 — viewer 에게도 열린다).
7. 다른 worktree 의 진척은 보이지 않는다 — 서버는 자기 checkout 만 읽는다.

### R6.3 `api/state`

진척 화면이 그리는 값과 같은 원천 · 같은 규칙의 JSON 이다. 화면에 없는 값을 더 싣지 않는다 (R6.2-6 이 그대로 적용된다).

## 8. 세션 알림 (R8) · MCP (R9)

### R8.1 ① 당겨 오기 — 정본

- `session-start` · `backlog-update` 의 `warnings`: `계획 응답 n건 미반영 (<TASK-ID> …) — plan-import 로 확인` (주장 R9.2 — 명령 시점에 센다).
- 실행 중인 서버가 있으면 `session-start` 보고에 `public_url` 한 줄.
- 응답의 내용(결정 값 · 주석)은 보고에 싣지 않는다 — task · 건수 · 경로만.

### R8.2 ② hook 머리말 — 지금은 만들지 않는다

§1.1 의 판정대로다. 다시 볼 조건: **Codex 의 `UserPromptSubmit` 출력이 모델 컨텍스트에 들어가는 것이 실측될 때** (그러면 Claude Code 와
둘이 된다). Antigravity 의 `PreInvocation` 은 내장 문서상 주입이 되지만 모델 호출 단위로 읽혀(§1.1 — 추론, 실행 미실측) 이 조건에 세지 않는다 —
그렇다면 같은 알림이 한 프롬프트에 여러 번 들어간다. 그때도 주입 문구는 "task · 건수 · 경로" 뿐이고, hook 이 없는 하네스는 ① 로 같은 사실을 얻는다.

### R9 MCP 도구 이름

| 번들 | 이름 | 하는 일 |
|---|---|---|
| read-only | `plan_inbox` | 받은편지함의 미반영 응답 목록 — task · 번호 · 응답자 · `received_at` · 자격 판정(주장 R6.2 의 단계 번호). 주석 본문은 싣지 않는다 |
| write | `plan_import` | `plan-import` 와 같은 동작. 기본 dry-run, 적용은 명시 인자 |

이름은 기존 도구(`latest_backlog` · `check_doc_links` · `apply_robust_patch`)의 표기를 따른다. write 번들을 받지 않는 하네스(Codex)의
반영 경로는 CLI 다. 서버를 띄우거나 멈추는 MCP 도구는 두지 않는다.

## 9. 노출 경로별 요구 (R7)

| 경로 | 사용자가 하는 설정 | 서버가 지키는 것 |
|---|---|---|
| 같은 호스트 | 없음 | bind `127.0.0.1`, 그래도 인증 (R0-5) |
| 포트 포워딩 · 터널 | 포워딩한 주소가 기본과 다르면 `--public-url` | 출처 대조 · 쿠키 `Path` 를 `public_url` 에서 (§1.3) |
| 리버스 프록시 (경로 접두사 포함) | `--public-url https://host/prefix/`, `--trusted-proxy <프록시 주소>` | 상대 경로만 (R2.3), `X-Forwarded-For` 는 신뢰 프록시에서만 (R3.2), TLS 는 프록시가 끝낸다 — `public_url` 이 `https` 면 쿠키에 `Secure` |
| 직접 노출 | `--bind <주소>` + `--tls-cert` · `--tls-key`, 또는 `--allow-plain-http` | 둘 다 없으면 시작하지 않는다, 시작할 때 경고 (R1.1). 인증서는 kit 이 만들지 않는다 |

프록시 설정 예시(nginx · Caddy 한 줄씩)는 design 의 문서 몫이다 — 실물 실측 뒤에 싣는다 (R11).

## 10. 검증 (R10) · design 진입 조건 (R12) · 남은 실측 (R11)

**R10 검사** — 각 case 는 되주입으로 red 를 확인한다:

1. 인증: 토큰 없이 시작 거절 · 세션 없는 요청 401 · viewer 의 POST 403 · 짧은 토큰 거절 · 넓은 모드의 토큰 파일 거절 · 로그인 실패 제한.
2. 쓰기 대조: R4.1 의 네 단계마다 하나씩 어긋난 요청 → 받은편지함 무변경.
3. 접두사: 접두사를 벗기는 프록시 뒤에서 로그인 → 계획 → 제출 → 도착이 전부 접두사 안 (§1.3 둘째 행), 쿠키 `Path` = 접두사.
   되주입: 절대 `Location` · `Path=/`.
4. 쓰기 경합: 동시 제출에서 유실 0 · 번호 연속, 독자가 덜 쓰인 파일을 보지 않는다 (§1.2 행 1 · 5). 되주입: 배타 생성 제거 · 이어 쓰기 —
   이어 쓰기 되주입은 만들기와 쓰기 사이에 **정해진 멈춤**을 넣어 결정적으로 만든다 (우연한 겹침에 기대면 세 번에 한 번 green 이다, §1.2 행 4).
   쓰는 쪽 × 옮기는 쪽: 배타 이동이면 유실 0, 되주입(rename)이면 유실 > 0 (§1.2 행 7 · 8).
   옮기는 쪽 둘 × 쓰는 쪽: 잠금 아래에서 중복 0 · 유실 0, 되주입(잠금 제거)이면 여러 회 중 중복이 난다 — 이 되주입은 확률적이라
   회수를 정해 두고 **1 회 이상 나는지**로 판정한다 (§1.2 행 9 · 11 — 한 번 잰 값은 30 회 중 5 회).
5. 왕복: 서버가 쓴 응답 파일을 `plan-import` 가 자격 있는 응답으로 받는다 (주장 R6.2 의 1~6 통과) — 쓰는 쪽과 읽는 쪽이 같은 형식을 안다.
6. 한도: 256KiB 초과 413 · 응답 파일 한도 초과 422 · 지문 불일치 409 — 셋 다 받은편지함 무변경.
7. 화면: 선언 ≠ 파생 둘 다 표시 · 잎 0 은 "미측정" · 절대 경로 · 호스트 이름이 어느 응답에도 없다 (`api/state` 포함).
8. 읽기 전용: 서버를 띄워 모든 GET 과 거절되는 POST 를 돌린 뒤 저장소의 추적 파일이 바뀌지 않았다 (`git status` 전후 동일).
9. 파서 단일성: 계획 화면 · 지문 · 결정 상태가 주장 R0-6 의 같은 함수를 부른다.

**R12 design 진입 조건**: ① 이 문서 sign-off (Q1 · Q2 — 완료, §13) ② R11 의 "design 전" 실측 완료 ③ 주장 트리 계획 design(M-026)과 **같은 ADR
묶음으로 낼지 따로 낼지**를 design 착수 때 정한다 — 응답 형식 · `plan-import` · 받은편지함이 두 마일스톤에 걸쳐 있다.
