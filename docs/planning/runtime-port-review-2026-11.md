# 허브 · PC 중계 런타임 전환 (Go / Rust) — concept 검토

- 문서 목적: 2.x 허브와 PC 중계를 Python 에서 Go 또는 Rust 로 옮길지, 옮긴다면 어디까지인지를 실측 근거로 정하고, 소유자가 정할 것을 기본값과 함께 모은다 (TASK-2026-11-22-main-021, M-049/WBS-49.1 · 49.2).
- 범위: 공식 MCP SDK 현황, 두 언어 탐침 서버 실측(빌드 · 크기 · 메모리 · 크로스 빌드 · 실제 하네스 연결), 현재 Python 허브 기준선, 이식량 인벤토리, 범위 선택지, 위험, 권고, 열린 결정. 코드 · 스펙 변경은 없다 (탐침은 저장소 밖 `/var/tmp`).
- 대상 독자: 소유자 (전환 결정), maintainer
- 상태: **종결 (2026-11-22)** — 소유자 결정: R1 = **D 전면 Go 전환**, R2~R5 = 권고안 (§11). 다음은 requirements (M-050)
- 최종 수정일: 2026-11-23
- 관련 문서: [`M-049`](../../ai-workflow/memory/active/roadmap/M-049-runtime-port-concept.md), [`hub_spec.md`](../../workflow-source/core/hub_spec.md) (§1 불변 조건 · R0.3 · R0.7), [`hub_orchestration_spec.md`](../../workflow-source/core/hub_orchestration_spec.md) (§9 중계), [`PURPOSE.md`](../../ai-workflow/memory/active/PURPOSE.md) (제외 영역 — Python 외 런타임)

## 0. 한 줄 결론

> **두 언어 모두 기술적으로는 된다** — 공식 MCP SDK(Go `go-sdk` v1.8.0 · Rust `rmcp` 3.11.0)로 허브와 같은 모양의 서버를 만들어
> 실제 Claude Code · Codex 가 붙어 도구를 불렀다. 막는 것은 언어가 아니라 **판정 코드의 공유**다: 허브는 1.x 판정 함수
> 약 **19k 줄**을 그대로 부르고(R0.7), 1.x 는 2028-07-20 까지 유지된다. 허브를 옮기면 그 판정이 두 언어로 갈라진다.
> 그래서 권고는 **단계 전환** — ① PC 중계(판정 없음, 909줄)만 **Go 단일 바이너리**로, ② 허브는 Python 유지 +
> `mcp<2` 상한 해제(최신 규격), ③ 허브 이식은 1.x 지원 종료(또는 판정 코드 동결) 시점에 다시 연다 (§8).

## 1. 질문

소유자 (2026-11-22): "2.1.0 은 유지하고 다음 버전에 go 나 rust 기반으로 전환을 고려하자."

기대 이점은 보통 셋이다 — (a) Python · venv 없는 **단일 바이너리 배포**, (b) 긴 폴링 · 대기 도구의 **동시성** · 메모리,
(c) 타입 안전 · 성능. 이 문서는 각 이점이 **어느 구성 요소에서** 실제로 생기는지와 그 대가를 잰다.

## 2. 실측 — SDK 와 탐침 서버 (Linux x86-64, 2026-11-22)

탐침: 허브와 같은 모양 — MCP **streamable HTTP · stateless · JSON 응답** · Bearer 인증 · SQLite 에 쓰는 도구 하나(`hub_note`).
저장소 밖 `/var/tmp/claude-rtprobe/` 에서 빌드했다.

## 3. 이식량 — 무엇이 함께 옮겨 가야 하나

허브 모듈(`workflow_kit/hub/*.py`)에서 출발해 `import` 만 따라간 **정적 닫힘** (패키지 `__init__` 의 재수출은 빼고):

| 묶음 | 줄 | 모듈 | 내용 |
|---|---|---|---|
| 허브 | 6,970 | 23 | 앱 · 도구 · 세션 · 오케스트레이션 · 중계 API · 화면 · 이전 · 위키 · 렌더 |
| `common` (공유) | 14,936 | 59 | memory_index · roadmap 진척 · purpose graph · workflow_writes · plan_claims · plan_responses · paths · project_docs … |
| `tools.backlog_update` | 1,609 | 1 | task 형식 · done 게이트 |
| `okf_export` · `okf_import` | 1,975 | 2 | 위키 OKF 운반 |
| `path_resolver` · `bootstrap_lib.harnesses` | 733 | 3 | 경로 · 진입 파일 생성 |
| **허브 외 공유 합계** | **19,253** | | **1.x CLI 와 같은 함수** — 2028-07-20 까지 `release/1.x` 에서 유지 |
| PC 중계 (`workflow_kit/relay`) | 909 | 9 | 표준 라이브러리만 · 판정 없음 · 하네스 프로세스 제어 + HTTP 긴 폴링 |
| 허브 검사 (`check_hub_*` 14 + `check_vscode_shell`) | 4,789 | 15 | 실제 허브 프로세스를 띄워 HTTP 로 두드리지만(12/14), DB 확인 · fixture 에 kit 내부도 import |

읽는 법:
- 허브 자체(7k)보다 **딸려 오는 판정 코드(19k)가 세 배 가까이 크다**. hub_spec §1-6 "판정은 1.x 와 **같은 함수**" 가 이것이다 —
  이 불변 조건 덕에 1.x 와 2.x 가 같은 task 에 같은 판정을 낸다 (들여오기 리허설 '로드맵 진척 차이 0').
- 중계는 판정이 없고 표준 라이브러리만 써서, 이식이 **닫혀 있다** — 다른 코드를 끌고 가지 않는다.
- 허브 검사는 이미 '실제 프로세스 + HTTP' 형태라, 허브를 옮길 날에는 **띄우는 명령만 바꿔 적합성 검사로 재사용**할 여지가 있다.

## 4. 범위 선택지

| 안 | 내용 | 얻는 것 | 대가 |
|---|---|---|---|
| **A** 유지 | 허브 · 중계 모두 Python. `mcp<2` 상한만 풀어 최신 규격으로 | 판정 한 벌 · 검사 그대로 | PC 에 Python 필요 (중계) · 메모리 79 MB 대 |
| **B** 중계만 이식 | PC 중계를 단일 바이너리로. 허브는 Python | **사람마다 까는 쪽**이 Python · venv 없이 파일 하나 — 이점 (a) 가 실제로 생기는 자리 | 중계 두 벌 기간(이행 중) · 어댑터 실측 재수행 · 서명 문제 (§6) |
| **C** 허브 앞단만 | MCP · HTTP · 인증 · 세션 · 긴 폴링을 Go/Rust, 판정은 Python 사이드카 | 허브 동시성 · 메모리 | **런타임 둘 + 프로세스 둘** — 배포가 오히려 무거워진다. 경계 직렬화 계약 신설 |
| **D** 전면 이식 | 허브 + 공유 판정 19k 줄 | 허브도 단일 바이너리 | **판정 두 벌** (1.x Python 이 2028-07-20 까지) — 이 저장소가 여러 번 겪은 '복제는 갈라진다'. 검사 하네스 재구축. 가장 비싸다 |

허브는 **한 기계에만** 깐다 (HUB_OPERATIONS §1). 그래서 단일 바이너리 이점 (a) 는 허브에서는 작고(컨테이너 · wheel 로 충분),
**PC 마다 까는 중계**에서 크다. 이점 (b) 는 허브 규모(프로세스 하나 · SQLite)에서 병목이 측정된 적이 없다.

## 5. Go 대 Rust (B 를 할 경우의 언어)

| 기준 | Go | Rust |
|---|---|---|
| 크로스 빌드 (Windows · macOS · arm64) | **도구 추가 없이 전부** (실측) | Windows 는 추가 도구 필요 (미측정) |
| 바이너리 · 메모리 | 12 MB · 13 MB | **3.4 MB · 6 MB** |
| SDK | v1.x 안정 (v1.0 이후 판 번호 규율) | 3.x — 주판이 자주 오르고 이름이 바뀐다 (탐침에서 확인) |
| 빌드 시간 | 클린 12초 | 클린 52초 · 증분 26초 |
| 중계의 일 (프로세스 띄우기 · stdio JSON-RPC · HTTP 긴 폴링) | 표준 라이브러리 `os/exec` · `net/http` 로 충분 | tokio · reqwest 등 의존 추가 |
| 정적 링크 | 기본 (`CGO_ENABLED=0`) | glibc 동적 (musl 대상으로 정적 가능 — 미측정) |

중계는 성능보다 **여러 OS 에 쉽게 까는 것**이 핵심이라 Go 가 맞다. 허브를 언젠가 D 로 옮긴다면 그때 다시 비교한다
(메모리 · 바이너리는 Rust 우위).

## 6. 위험

- **Windows 백신 평판 (미해결)** — `wk.exe` 차단 이력에 더해, 2026-11-23 사내 Windows에서 Go 허브가 AhnLab V3에 격리됐다는 소유자 보고가 있다. 파일명·탐지명·해시를 아직 몰라 공식 자산과 대조 중이며 오탐으로 단정하지 않는다 (`TASK-2026-11-23-main-014`).
  Go 릴리스 빌드에는 코드 서명 단계가 없고 `-s -w` strip을 쓴다. 사내/보안 관리 Windows 또는 환경 불명은 셋업에서 Python-only로 안내하고, Go는 보안 담당자 승인 뒤에만 선택한다.
- **macOS 공증 (미측정)** — 내려받은 서명 없는 바이너리는 Gatekeeper 가 막는다. Developer ID · 공증 비용.
- **PURPOSE 제외 영역** — "Python 외 runtime" 은 제외다. 예외는 VS Code 껍데기뿐 (2026-11-22). B 는 예외를 **중계 바이너리**로 넓히는 결정이다 → ADR.
- **두 벌 기간** — B 이행 중 Python 중계와 Go 중계가 함께 있다. 중계 HTTP 계약(`/v1/relay/*`)과 어댑터 실측(요구 §1.5)을 Go 판에도 다시 해야 한다. 끝나면 Python 중계를 deprecation 정책으로 내린다.
- **검사** — 중계 검사(`check_hub_relay`)는 프로세스 안 `Relay` 객체를 쓴다. Go 중계용으로는 실제 바이너리를 띄우는 형태로 바꿔야 한다.

## 7. 미측정 (통과로 세지 않는다)

- Windows · macOS 네이티브 Go 바이너리 실행은 미측정. AhnLab V3 격리 보고는 있으나 대상·탐지명 미확인이라 원인 판정도 미측정.
- Rust 의 Windows · musl 정적 빌드
- Go/Rust 서버에서 120초 이상 대기 도구 (하네스 상한은 2.1 실측으로 없음)
- 허브 규모(도구 74 · DB 판 12)를 옮긴 뒤의 메모리 · 지연 — 탐침은 도구 1개
- MiniMax Code · Antigravity 의 Go/Rust 서버 연결 (Claude Code · Codex 만 잼)

## 8. 권고

1. **B — PC 중계만 Go 단일 바이너리로** (다음 판 2.2 후보). 사람마다 까는 쪽에서 Python 을 없앤다. 판정이 없어 두 벌 문제가 없다.
   Windows 서명 문제가 실측으로 풀리기 전까지 Windows 는 Python 중계를 병행한다.
2. **A 의 일부를 지금 — 허브 `mcp` 상한 해제** (`>=1.27,<2` → 2.x, 최신 규격 2026-07-28). 언어 전환과 독립이고 SDK 매트릭스가 이미 2.1.1 을 통과한다.
3. **허브 이식(D)은 미룬다** — 다시 여는 조건: ① 1.x 지원 종료(2028-07-20) 또는 판정 코드 동결, ② 허브 규모에서 Python 병목이 **측정**됨,
   ③ 여러 조직에 관리형으로 배포할 필요. 그때 허브 검사를 적합성 검사로 재사용하는 방식을 먼저 설계한다.
4. **C 는 권하지 않는다** — 런타임 둘을 한 서버에 두면 배포가 오히려 무거워진다.

D 가 가져오는 것 — requirements 가 풀어야 할 문제로 넘긴다:

1. **판정 두 벌** — 1.x(`release/1.x`, 2028-07-20 까지)는 Python 판정을 유지한다. Go 판정이 같은 답을 내는지
   **차분 검사**(같은 fixture · 실제 저장소 데이터를 두 구현에 넣어 결과 대조)로 상시 잰다. 1.x 결함 수리는 두 쪽에 다 들어가야 한다.
2. **적합성 검사** — 허브 검사(실제 프로세스 + HTTP)를 '띄우는 명령'만 바꿔 Go 허브에도 돌게 한다. kit 내부 import 부분은 HTTP · DB 확인으로 바꾼다.
3. **이행 순서** — 판정 코드(19k 줄)가 가장 크다. 중계(909줄, 닫힘) → 허브 앞단 → 판정 순서 등 단계와 각 단계의 '같은 답' 기준을 정한다.
4. **생성물 형식 불변** — hub_spec §1-1 (1.x 생성물 형식을 그대로 낸다) · DB 판 · MCP 도구 계약 · HTTP 경로가 Go 판에서도 같아야 한다 — 기존 DB 를 Go 허브가 그대로 연다.
5. **검사 하네스 언어** — 게이트 러너 · 검사는 Python 이다. Go 코드의 단위 검사(`go test`)를 게이트에 어떻게 넣을지.
6. **배포** — 2.x 판은 wheel 대신 OS별 바이너리 (GitHub Releases). Windows 서명은 R4 실측 뒤.
