## 0. 요약

2.0.0 에서 작업 환경은 **kit 을 깔지 않는다**. 허브 주소 하나를 원격 MCP 서버로 등록하면 부트스트랩 도구가 보이고,
그 도구가 프로젝트 등록(git 원격 주소가 키) · 콜사인 합류 · 지침 셋업을 한다. 이후 task · handoff · 이력 · 결정 응답 · 로드맵 · 위키 · 공유 지침의
**정본은 허브**이고, 판정(계획 린트 · done 게이트 · 결정 상태 · 상태 생성)은 **허브 안의 kit 함수**가 한다. 작업 환경이 쓰는 로컬 파일은 진입 파일 ·
`.gitignore` 한 줄 · `.workflow-hub/` 뿐이고, 원격 MCP 는 로컬 파일을 쓰지 못하므로 **도구가 쓸 내용과 해시를 돌려주고 에이전트가 쓴 뒤 확인 도구가 대조**한다.
1.x 의 로컬 kit + git 흐름은 유지보수 줄로 남고, 1.x 프로젝트는 처음 2.0 부트스트랩을 부를 때 **전환 과정**으로 들어간다.

요구는 R0(불변) ~ R15 이고, 각 요구 끝의 **[검증]** 이 그 요구를 판정하는 방법이다. 숫자 상한은 design 이 바꿀 수 있는 **기본값**이며 그 경우 이 문서를 고친다.

## 1. 용어

| 말 | 뜻 |
|---|---|
| 허브 | kit(Python)이 서버로 도는 프로세스 하나 + 그 SQLite 파일 하나. 여러 프로젝트를 맡는다 (D2) |
| 프로젝트 | 허브 안의 작업 단위. 키 = 정규화한 git 원격 주소 (H7), 허브 내부 ID 는 따로 (F2) |
| 콜사인 | 한 작업 환경(클론 하나 + 그 worktree 들)의 이름. 토큰을 하나 가진다. 작업 기억의 단위 (H8) |
| 작업 환경 | 에이전트 · 사람이 저장소 클론에서 일하는 곳. kit 이 없다 (H4) |
| 허브 MCP | 허브가 여는 원격 MCP 서버 (MCP 의 HTTP 전송). 하네스가 허브 주소로 등록한다 (H10) |
| 선택 클라이언트 | 표준 라이브러리 한 파일. hook · 오프라인 보낼편지함용, **필수가 아니다** (I1) |
| 쓰기 지시 | MCP 도구가 돌려주는 "이 경로에 이 내용을 써라 + 해시". 에이전트가 쓰고 확인 도구가 대조한다 (I1) |
| 1.x 흐름 | 작업 환경의 kit + git state 문서 정본 흐름 (지금) |

## 2. 불변 조건 (R0)

- **R0.1 생성물 형식 유지** — `state.json` (`schema_version` "1") · `roadmap_state` v1 · `workbench-state/1` · `workflow-kit-plan-response/1` 은 형식을 바꾸지 않는다. 허브가 만드는 같은 이름의 산출물은 **같은 형식**이다 (concept §5).
  [검증] 허브가 만든 산출물을 1.x 의 형식 검사(지금의 `check_*` 스키마 검사)에 그대로 통과시키는 검사.
- **R0.2 stable API 는 추가만** — `workflow_kit.__all__` (지금 25개 이름)에서 빼거나 서명을 바꾸지 않는다. 허브용은 새 이름으로 더한다.
  [검증] 1.x 마지막 판의 `__all__` 과 2.0 의 `__all__` 대조 — 빠진 이름 0.
- **R0.3 Python 만** — 허브 · 선택 클라이언트 모두 Python. PURPOSE 제외 영역 '비 Python runtime' 은 그대로다 (concept §3 H2).
  [검증] 2.0 wheel 에 Python 아닌 실행 코드가 없다 (지금의 wheel 내용 검사 확장).
- **R0.4 선택 클라이언트 · 부트스트랩 원문은 표준 라이브러리만** — 작업 환경에 pip 설치를 요구하지 않는다 (H4). 하한은 kit 과 같은 Python 3.10 (`requires-python`).
  [검증] 깨끗한 Python 3.10 (venv 없이, site-packages 비움)에서 선택 클라이언트의 모든 명령이 import 오류 없이 돈다.
- **R0.5 비밀은 허브 기록에 싣지 않는다** — task · handoff · 체크포인트 · 지침 · 위키 본문에 토큰을 받지 않는다. 허브가 쓰기 전에 콜사인 토큰 · 허브 관리 토큰과 같은 문자열을 찾으면 거절한다 (concept §4.2.4 · §6).
  [검증] 각 쓰기 경로에 자기 토큰을 실은 요청 → 거절 · 저장 0건.
- **R0.6 모르는 것은 거절한다** — 허브는 모르는 인자 · 모르는 클라이언트 판 · 모르는 형식 판을 거절하고 이유를 돌려준다. 조용히 기본값으로 떨어지지 않는다 (concept §6 '판 갈림').
  [검증] 모르는 필드 · 판을 실은 요청 → 4xx + 이유, 상태 변화 0.
- **R0.7 판정은 kit 함수 하나로** — 허브의 계획 린트 · done 게이트 · 결정 상태 · 상태 생성은 1.x 와 **같은 함수**를 부른다. 허브용 사본을 따로 짜지 않는다 (규약 단일 출처).
  [검증] 같은 task 데이터를 1.x 경로(파일)와 허브 경로(데이터)로 판정한 결과가 같다 — 대조 fixture.

## 3. 허브 서버 (R1)

- **R1.1 기동** — `python -m workflow_kit hub serve` 꼴의 명령 하나로 뜬다 (이름은 design). 허브 쪽에만 kit 을 깐다.
  [검증] 깨끗한 venv 에 2.0 wheel 만 깔고 기동 → healthz 200.
- **R1.2 저장소** — 상태는 SQLite 파일 하나. 동시 쓰기는 레코드별 `version` 으로 대조하고, 다르면 **409** 로 거절한다 — 자동 병합하지 않는다 (concept §4.5 · D4 · E4).
  [검증] 같은 레코드에 낡은 `version` 으로 쓰기 → 409, 저장된 값 불변. 동시 쓰기 부하에서 유실 0 (워크벤치 requirements §1.2 와 같은 방식의 경합 측정).
- **R1.3 이관** — DB 형식 판을 DB 안에 적고, 기동 때 모자라면 순서대로 이관한다. 이관 전에 사본을 남긴다. 모르는(더 새) 판이면 기동을 거절한다.
  [검증] 판 n 의 DB 로 판 n+1 허브 기동 → 이관 + 사본 1개. 판 n+1 DB 로 판 n 허브 기동 → 거절.
- **R1.4 백업** — 허브가 돌고 있는 동안 일관된 사본을 만드는 명령을 낸다 (SQLite 온라인 백업). 운영 배치(정기 실행 · 보관)는 프로젝트 몫이다 (PURPOSE 제외 '인프라 IaC').
  [검증] 쓰기 부하 중 백업 → 사본으로 허브 기동, 무결성 검사 통과.
- **R1.5 이벤트 이력** — 모든 쓰기는 이벤트 한 줄을 남긴다: 프로젝트 · 대상 · 콜사인 · 시각 · 이전 값 · 새 값. 이벤트는 지우거나 고치지 않는다 (H4 '이력').
  [검증] 쓰기 n 번 → 이벤트 n 줄, 이전 값을 거꾸로 적용하면 처음 상태.
- **R1.6 판 보고** — healthz 와 모든 응답 머리에 허브의 kit 판 · 지침 판 · DB 판을 싣는다 (세션 시작 확인 R10 이 읽는다).
  [검증] 응답 머리 대조.

## 4. 허브 MCP 도구 (R2)

- **R2.1 원격 MCP** — 허브는 MCP 의 HTTP 전송으로 도구를 연다. 하네스는 허브 주소 하나를 MCP 서버로 등록한다 (H10 · I4). kit 의 기존 stdio MCP 서버는 1.x 줄에 남는다.
  [검증] 지원 하네스(R2.8) 4종 각각 등록 · 도구 목록 · 도구 호출 확인 (§16.3 의 탐침 방식).
- **R2.2 묶음** — 도구는 묶음으로 나뉜다: 부트스트랩 (프로젝트 조회 · 등록 · 콜사인 등록 · 지침 셋업 · 쓰기 확인) · 세션 (시작 확인 · compact 직후 확인 · 끝) · task · handoff · 상태 · 지침 · 위키 · 로드맵 · 결정 응답 (concept §14.1). 이름은 design.
  [검증] design 의 도구 표가 이 묶음을 모두 덮는다 — 추적표.
- **R2.3 등록 전에는 부트스트랩 묶음만** — 토큰 없는 MCP 연결에는 부트스트랩 묶음만 보이고, 다른 도구 호출은 거절한다 (I2). 화면 공용 토큰(R13.2)은 MCP 도구를 열지 않는다.
  [검증] 토큰 없이 도구 목록 = 부트스트랩 묶음, task 도구 호출 → 거절.
- **R2.4 쓰기 지시 + 확인** — 로컬 파일이 필요한 도구(진입 파일 · `.gitignore` · `.workflow-hub/env`)는 파일을 직접 쓰지 않고 **쓰기 지시**(경로 · 내용 · sha256)를 돌려준다. 확인 도구는 에이전트가 보낸 실제 파일 해시를 지시와 대조하고, 다르면 '미확인' 으로 보고한다 — 확인을 거치지 않은 셋업은 허브가 완료로 적지 않는다 (I1).
  [검증] 지시대로 쓴 경우 확인 통과 · 한 바이트 바꾼 경우 '미확인' · 확인 안 부른 경우 셋업 상태 '미완료'.
- **R2.5 토큰 전달** — 하네스 MCP 설정에는 `${WORKFLOW_HUB_TOKEN}` 꼴의 **환경 변수 참조만** 쓴다 (하네스마다 칸이 다르다 — Codex 는 `bearer_token_env_var`, §16.3. 참조를 못 하는 하네스는 R2.5a). 값은 `.workflow-hub/env` 에 둔다 (I3). 허브가 내주는 하네스별 설정 조각에 토큰 값이 들어 있으면 안 된다.
  [검증] 안내 페이지 · 도구가 내는 설정 조각에 토큰 문자열 0.
- **R2.5a 참조를 못 하는 하네스 — 사용자 범위에만 값 (Q7)** — 헤더의 환경 변수 참조를 확장하지 않는 지원 하네스(지금은 Antigravity — §16.3)는 **그 하네스의 사용자 범위 설정**(저장소 밖, Antigravity 는 `~/.gemini/config/mcp_config.json`)에 토큰 값을 직접 넣는다. 허브는 그 하네스의 등록 명령 · 쓰기 지시에 경고 한 줄(평문 저장 · 이 파일을 공유하지 말 것 · 토큰을 거두는 법)을 붙인다. **프로젝트 범위 파일(저장소 안)에는 어떤 하네스든 토큰 값을 쓰지 않는다** — 쓰기 지시 생성 단계에서 거절한다. 콜사인을 거두면(R4.7) 그 토큰은 허브에서 무효가 되므로 남은 파일 값은 쓸모가 없어진다.
  [검증] Antigravity 등록 지시 = 사용자 범위 경로 + 경고 문구. 프로젝트 범위 경로로 값을 쓰는 지시 요청 → 거절. 콜사인 거둔 뒤 그 토큰 → 401.
- **R2.6 안내 페이지** — 허브 주소 `/` 는 지원 하네스(R2.8)마다 한 줄 등록 명령을 보인다 (I4). 토큰을 보이지 않는다. 명령에는 그 하네스에서 허브 도구가 실제로 돌기 위한 설정을 함께 싣는다 — Codex 비대화 실행의 서버 단위 승인(`default_tools_approval_mode`), Antigravity 의 사용자 범위 토큰과 경고(R2.5a) (§16.3).
  [검증] 페이지에 지원 하네스마다 명령 한 줄 · 토큰 0.
- **R2.7 선택 클라이언트** — 허브는 선택 클라이언트 원문을 내려준다 (`/v1/bootstrap` 꼴). 클라이언트는 자기 판을 요청마다 싣고, 허브가 모르는 판이면 거절 + 갱신 안내 (R0.6). 같은 일을 MCP 도구와 클라이언트가 둘 다 하면 **같은 허브 API** 를 부른다 — 두 길의 결과가 갈리지 않게.
  [검증] 같은 조작을 MCP 와 클라이언트로 → 이벤트 이력 동일 (콜사인 · 대상 · 값).

- **R2.8 지원 하네스 — 4종 (소유자 2026-11-20, Q8)** — 2.0.0 이 지원하는 하네스는 **Claude Code · Codex · MiniMax Code · Antigravity** 다. '지원' 은 ① 안내 페이지의 등록 명령(R2.6) ② 진입 파일 렌더링(R7.2) ③ 하네스별 실측 검증(R2.1 · R11.3) 셋을 허브가 책임진다는 뜻이다. 그 밖의 하네스(Grok Build · OpenCode · pi-dev · Aider · Goose 등 1.x 가 아는 것)는 지원 대상이 아니다 — 허브가 막지는 않지만(표준 원격 MCP 라 수동 등록은 될 수 있다) 위 셋을 내지 않고, 추가는 하네스마다 실측 뒤 소유자 결정으로 한다.
  [검증] 안내 페이지 · 렌더링 대상 · 하네스 실측 검사의 하네스 집합이 이 4종과 같다 (하나의 목록에서 파생 — 사본 금지).

## 5. 부트스트랩 · 프로젝트 등록 · 식별 (R3)

- **R3.1 등록 전 부트스트랩** — 허브는 프로젝트가 없어도 부트스트랩 묶음을 낸다. 부트스트랩 하나가 식별 → (없으면) 등록 → 콜사인 합류 → 지침 셋업 → 확인을 한다 (H6 · concept §4.2).
  [검증] 빈 허브 + git 원격이 있는 빈 저장소에서 부트스트랩 → 프로젝트 1 · 콜사인 1 · 진입 파일 확인 통과.
- **R3.2 식별 키** — 키는 정규화한 원격 주소다: 스킴 · 사용자 · 포트 표기 · 끝의 `.git` · 끝의 `/` 를 떼고 호스트를 소문자로 (concept §4.2.1). `git@github.com:o/r.git` · `https://github.com/o/r` · `ssh://git@github.com/o/r.git` 는 같은 키다. 경로 대소문자 · 서브그룹 규칙은 design (R3.2 의 표를 design 이 넓힌다).
  [검증] 위 세 형태 + 대소문자 · 포트 · 서브그룹 변형 표 → 기대 키 표와 대조.
- **R3.3 원격 고르기** — `origin` 을 쓴다. 없으면 원격 목록을 보이고 고르게 한다. 원격이 하나도 없으면 **등록을 거절**하고 원격을 먼저 만들라고 안내한다 (F1 · F3).
  [검증] origin 있음 · origin 없고 둘 · 원격 없음 세 fixture.
- **R3.4 등록 권한** — 허브에 닿는 누구나 등록할 수 있고 등록자가 프로젝트 소유자다 (F4). 막는 수단은 노출 범위다 (R13).
  [검증] 토큰 없는 등록 → 프로젝트 + 소유자 콜사인.
- **R3.5 별칭** — 프로젝트 ID 와 키를 분리하고, 소유자가 다른 주소를 **별칭**으로 묶을 수 있다 (저장소 이전 · 미러). 포크는 별칭으로 묶지 않고 새 프로젝트로 등록된다 — 허브는 포크 여부를 판단하지 않고, 묶는 것은 소유자의 명시 조작뿐이다 (F2).
  [검증] 별칭 주소로 부트스트랩 → 같은 프로젝트에 합류. 묶지 않은 다른 주소 → 새 프로젝트.
- **R3.6 저장소 하나 = 프로젝트 하나** — 첫 판은 하위 경로 키를 받지 않는다 (F5).
  [검증] 같은 키로 두 번째 등록 → 등록이 아니라 합류.
- **R3.7 허브는 주소를 식별에만 쓴다** — 등록 · 합류 과정에서 허브는 그 주소에 접속하지 않는다. 원격 읽기는 위키 설정(R8.4)에서만, 프로젝트가 켤 때만 (concept §4.2.1).
  [검증] 등록 중 허브의 바깥 연결 0 (네트워크를 막은 환경에서 등록 성공).
- **R3.8 들여오기 후보** — 저장소에 이미 있는 진입 파일 · `ai-workflow/` 를 찾아 **후보로 보인다**. 무엇을 들일지는 등록자가 고른다. 고르지 않은 것은 들이지 않는다 (concept §4.2 3.2). 1.x 흔적이 있으면 R14 전환 과정으로 간다.
  [검증] 후보 보고에 찾은 파일 목록 · 고른 것만 허브에 생김.

## 6. 콜사인 · 인증 · 작업 기억 (R4)

- **R4.1 콜사인 등록** — 등록되면 토큰 하나를 받는다. 토큰은 허브에 해시로만 남는다. 새 콜사인의 권한은 프로젝트 설정을 따른다 (concept §4.2 3.3).
  [검증] DB 에 토큰 원문 0. 잘못된 토큰 → 401.
- **R4.2 `.gitignore` 먼저** — 토큰을 쓰기 전에 `.gitignore` 에 `/.workflow-hub/` 줄을 더하고 `git check-ignore` 로 실제로 무시되는지 확인한다. 무시되지 않으면(`!` 부정 · 이미 추적 중) **토큰을 쓰지 않고 멈춘다** (H9 · concept §4.2.2). 원격 MCP 에서는 이 순서가 쓰기 지시의 순서다: `.gitignore` 지시 → 확인 → 그다음에야 토큰 파일 지시.
  [검증] `!.workflow-hub/` 규칙이 있는 fixture → 토큰 지시가 나오지 않음. 이미 추적 중인 `.workflow-hub/x` fixture → 같음.
- **R4.3 토큰 파일** — `.workflow-hub/env`, POSIX 권한 600. Windows 는 사용자 프로필 ACL 을 따르고 그 사실을 보고한다 (권한을 적용했다고 꾸미지 않는다).
  [검증] POSIX 에서 mode 600. Windows 실측은 §16 밖의 남은 실측으로.
- **R4.4 worktree** — 같은 클론의 worktree 는 같은 콜사인을 쓴다. 새 worktree 에 `.workflow-hub/env` 가 없으면 세션 시작이 '복사하라' 를 안내한다 (concept §4.2.2).
  [검증] worktree fixture — 안내 문구 · 복사 뒤 같은 콜사인.
- **R4.5 콜사인별 작업 기억** — handoff · 상태 요약 · 작업 이력 메모리(세션 기록 · compact 체크포인트 · lessons)는 **콜사인 하나에 하나**다. 브랜치는 task · 기록의 칸이다 (H8 · G1).
  [검증] 한 콜사인이 두 브랜치에서 일함 → handoff 1개, 기록에 브랜치 칸 2종.
- **R4.6 읽기 공개 · 쓰기 본인** — 프로젝트 안의 콜사인은 다른 콜사인의 기록을 읽을 수 있고, 쓰기는 그 콜사인만 (G3).
  [검증] 다른 콜사인 handoff 쓰기 → 403, 읽기 → 200.
- **R4.7 거두기 · 휴면** — 소유자가 콜사인을 거두면 그 기록은 보관(읽기 전용)이 되고, 맡던 열린 task 는 맡은 이를 비운다. 휴면 판정 기준(며칠)은 프로젝트 설정이고 기본값은 없음(자동으로 거두지 않음) — 화면에 '마지막 활동' 만 보인다 (G2).
  [검증] 거둔 뒤 task 맡은 이 비어 있음 · 기록 쓰기 403 · 읽기 200.

## 7. task · 판정 · 이력 · 결정 응답 (R5)

- **R5.1 task 정본은 허브** — task 의 상태 · 계획 칸 · 진행 · 결과 · 검증 기록은 허브가 정본이다 (H1). task 는 프로젝트 공용이고 맡은 이 칸에 콜사인이 붙는다.
  [검증] task 조회는 허브에서만 — 작업 환경에 task 파일이 없어도 세션이 돈다.
- **R5.2 ID** — 형식은 1.x 와 같다 (`TASK-<날짜>-<네임스페이스>-<번호>`). 허브가 번호를 매기고 같은 번호를 두 번 내지 않는다. 들여온 task 는 원래 ID 를 지킨다 (concept §4.6).
  [검증] 동시 생성 부하 → 중복 0. 들여오기 뒤 ID 동일.
- **R5.3 맡기** — 같은 task 를 다른 콜사인이 이미 맡았으면 **409** (concept §4.4 '선점').
  [검증] 두 콜사인이 동시에 맡기 → 하나 성공 · 하나 409.
- **R5.4 상태 하나** — `planned` · `in_progress` · `blocked` · `done` 중 정확히 하나 (1.x 규칙).
  [검증] 다른 값 → 거절.
- **R5.5 게이트** — 계획 린트 · 결정 상태 · done 게이트(검증 기록 필수 · 열린 결정이 있으면 닫지 않음 · 대기 중 결정 응답)는 1.x 와 같은 규칙 · 같은 거절 코드 (R0.7).
  허브에는 작업 트리가 없어 L5 (git HEAD 줄 수) 가 조용히 빠진다 (§16.1) — 줄 수를 공급하지 못하면 그 규칙은 '미측정' 으로 보고한다. 응답은 `has_error_rules` → `qualify` → `compute_states` 순서로만 반영한다.
  [검증] 1.x 의 게이트 fixture 를 허브 경로로 돌려 같은 판정 · 같은 `error_code`. L5 를 공급하지 않은 경우 결과에 '미측정' 표식.
- **R5.6 WBS 게이트** — task 는 WBS leaf 또는 `exempt` + 사유를 단다. 로드맵이 허브에 있으므로 판정도 허브 로드맵으로 (D8).
  [검증] 없는 leaf → 거절 · `exempt` 사유 없음 → 거절.
- **R5.7 진행 기록** — 단계마다 진행 한 줄을 남길 수 있고 허브가 시각을 붙인다 (1.x `--progress-note`). 화면 '지금 하는 일' 이 이것이다.
  [검증] 진행 기록 → 시각 접두 · 화면 반영.
- **R5.8 결정 응답** — `workflow-kit-plan-response/1` 형식 그대로 허브가 받고 보관한다. 게이트가 바로 읽는다 (받은편지함 파일 · `plan-import` 단계가 없다). 같은 응답의 중복 수신은 한 번만 반영한다.
  [검증] 같은 응답 두 번 → 반영 1. 형식 판이 다르면 거절 (R0.6).
- **R5.9 커밋 묶기** — task 에 커밋 sha · 브랜치를 묶을 수 있다. 허브는 그 커밋을 읽지 않는다 (concept §4.4 '코드 · 문서 변경').
  [검증] sha 저장 · 허브 바깥 연결 0.
- **R5.10 이력** — task 의 모든 변경은 R1.5 이벤트로 남고, task 화면 · 도구로 볼 수 있다.
  [검증] 변경 n → task 이력 n.

## 8. handoff · 상태 요약 (R6)

- **R6.1 handoff** — 세션 끝 도구가 콜사인의 handoff (기준선 · 진행 · 막힘 · 다음 시작 포인트 · 위험)를 올린다. 다음 세션 시작이 그것을 돌려준다 (H4 · H8). 형식은 1.x handoff 의 절과 같은 칸 (design 이 칸을 고정).
  [검증] 올림 → 다음 시작 응답에 같은 내용.
- **R6.2 1.x 규칙 유지** — 진행 · 막힘 목록이 비면 빈 표시 · 최근 완료는 `TASK-` 로 시작하고 10개 이하 · 기준선 상한 넘으면 **옮긴다(지우지 않는다)** — 허브가 강제한다.
  [검증] 11번째 완료 → 가장 오래된 것이 보관으로 이동, 삭제 0.
- **R6.3 상태 요약** — 허브는 콜사인별 · 프로젝트 전체 상태 요약을 `state.json` v1 형식으로 만든다 (R0.1). 손으로 고치는 길이 없다 (1.x '생성물' 규칙).
  [검증] 생성물의 형식 검사 통과 · 쓰기 API 에 상태 요약이 없다.
- **R6.4 세션 끝 순서** — 세션 끝 도구는 '기억 갱신 → 커밋 → push' 순서를 안내하고, 허브 쪽 갱신(handoff · 진행 중 task 의 진행 기록)을 끝내지 못하면 끝을 '미완료' 로 보고한다.
  [검증] handoff 올림 실패 fixture → '미완료' 보고.

## 9. 공유 지침 (R7)

- **R7.1 세 층 정본** — 허브가 지침을 **표준 규칙 · 프로젝트 지침 · 하네스 어댑터** 세 층으로 들고 하네스별 진입 파일로 렌더링한다. 환경 덧붙임은 로컬 몫이고 허브는 모른다 (H5 · concept §4.3).
  [검증] 같은 프로젝트를 지원 하네스 4종으로 렌더링 → 표준 · 프로젝트 내용이 넷 다에 있음.
- **R7.2 하네스 범위** — 첫 판의 진입 파일은 지원 하네스(R2.8) 4종의 것: `CLAUDE.md` (Claude Code) · `AGENTS.md` (Codex) · `MiniMax.md` (MiniMax Code) · `ANTIGRAVITY.md` (Antigravity) — 파일 이름은 1.x bootstrap 의 하네스 표(`bootstrap_lib/harnesses`)와 같다. `AGENTS.md` 는 다른 하네스도 읽지만 지원 범위를 넓히지 않는다. 크기 예산은 1.x `check_entry_budget` 의 8KB 를 그대로 쓴다.
  [검증] 렌더링 결과마다 크기 ≤ 예산 · 하네스 표와 파일 이름 대조.
- **R7.3 표준 규칙은 2.0판** — 표준 규칙 층은 허브 흐름의 명령(허브 MCP 도구 이름)을 쓴다. 1.x 의 `python -m workflow_kit …` 명령이 2.0 진입 파일에 나오지 않는다. 세션 시작 확인(R10) · compact 직후 확인(R11) 규칙이 이 층에 있다 (H11 · H14).
  [검증] 렌더링 결과에 `python -m workflow_kit` 0건 · 세션 시작 · compact 규칙 문장 있음.
- **R7.4 판 머리** — 진입 파일 머리에 허브 · 프로젝트 · 지침 판을 적는다. 세션 시작이 이것과 허브 판을 비교한다.
  [검증] 머리 파싱 · 판이 다르면 시작 보고에 '[바뀜]'.
- **R7.5 로컬 편집 보호** — 렌더링 영역이 마지막으로 내준 판과 다르면 **덮어쓰지 않고 멈춰 알린다**. 고칠 것은 허브에 제안으로 올리게 한다 (concept §4.3 3).
  [검증] 렌더링 영역 한 줄 수정 fixture → 쓰기 지시 없음 · 멈춤 보고.
- **R7.6 커밋** — 허브가 쓴 진입 파일은 저장소에 커밋하는 것이 규칙이다 (D10). 세션 끝 안내에 포함한다.
  [검증] 세션 끝 안내 문구.
- **R7.7 편집 권한** — 프로젝트 지침은 편집 권한을 받은 콜사인이 고친다. 콜사인은 종류(`human` · `agent`)를 갖고, **에이전트의 변경은 제안**으로 남아 사람 콜사인이 승인해야 판이 오른다 (D11). 종류는 등록 때 본인이 고르고, **`human` 등록은 프로젝트 소유자가 승인할 때까지 `agent` 권한**이다 — 에이전트가 스스로 사람이라 적어 승인을 건너뛰지 못하게 (Q3). 프로젝트의 첫 콜사인(등록자)은 소유자이므로 `human` 이 바로 선다.
  [검증] 에이전트 콜사인 변경 → 판 불변 · 제안 1. 사람 승인 → 판 +1. 승인 전 `human` 콜사인의 지침 변경 → 제안 1 · 판 불변.
- **R7.8 받은 판 기록** — 허브는 콜사인마다 마지막으로 받은 지침 판을 적고 화면에 '옛 지침으로 도는 환경' 을 보인다.
  [검증] 판을 올린 뒤 시작 안 한 콜사인 → 화면 표시.

## 10. 위키 · memory_index · ADR (R8)

- **R8.1 정본** — 위키 · memory_index · ADR(`decisions/`)의 정본은 허브다. 계획 문서(`docs/planning/`)는 git 에 남는다 (E1 · E5 · E6).
  [검증] 들여오기 뒤 위키 쓰기는 허브 경로만.
- **R8.2 ingest = 묶음 쓰기 하나** — 여러 페이지를 한 번에 쓰는 묶음 하나가 ingest 하나이고, `log` 항목은 허브가 만든다. 페이지 단위 `version` 409 (E4 · concept §11.3).
  [검증] 묶음 안 한 페이지 version 충돌 → 묶음 전체 거절 · 부분 반영 0.
- **R8.3 lint** — 있는 검사(V-1 위치 · V-4 index 구조)는 **경로를 인자로 받게 고쳐** 허브가 펼친 임시 디렉터리에서 1.x 와 같은 함수로 돌린다. 없는 lint (모순 · 스테일 · 깨진 backlink)는 허브에서 새로 짠다 (E2). 인자화 범위는 §16 실측 S2 가 정한다.
  저장소 배치 규칙(V-1 의 금지 위치)과 저장소 · git 에 묶인 점수(operational · trend)는 허브 lint 에서 뺀다. freshness 는 소스 시각을 못 받으면 '미측정' 이고 측정 대상 수를 결과에 싣는다 (§16.2 — 지금 코드는 대상이 34 → 1 로 줄며 점수가 오른다).
  [검증] 같은 위키를 저장소 뿌리 · 펼친 디렉터리에서 판정 → 같은 결과. 소스 시각 없이 freshness → '미측정' · 대상 수 0 표시.
- **R8.4 저장소 참조** — 페이지 출처에 저장소 키 + 커밋 sha 를 싣는다. 프로젝트가 켜면 허브가 git 원격을 **읽기 전용**으로 읽어 링크 · 신선도를 잰다. 못 읽으면 결과를 '통과' 가 아니라 **'미측정'** 으로 보인다 (E3).
  [검증] 원격을 끈 프로젝트 → 링크 · 신선도 '미측정' (통과 0건).
- **R8.5 읽기 도구** — kit 없는 에이전트가 위키를 찾고 읽는 도구(검색 · 보기)를 낸다 (concept §11.3).
  [검증] 검색 · 보기 도구 왕복.
- **R8.6 운반 형식** — 위키 들여오기 · 내보내기는 OKF v0.2 (ADR-026) 를 쓴다.
  [검증] 1.x 위키 → OKF → 허브 → OKF → 비교, 페이지 · frontmatter 일치.

## 12. 세션 시작 확인 (R10)

- **R10.1 두 쪽 확인** — 세션 시작 도구는 허브와 저장소를 **함께** 확인하고 한 번에 보고한다 (H11 · concept §4.2.3).
  - 허브: 닿는가 · 지침 판 · 클라이언트 · 규칙 판 · 내 handoff · 내 task · 맡은 이 없는 열린 task · 보낼편지함에 남은 것
  - 저장소: `git fetch` 뒤 현재 브랜치와 원격의 차이 · 기본 브랜치 머리 · 커밋 안 된 변경 · `.gitignore` 규칙 (R4.2)
  원격 MCP 는 저장소를 볼 수 없으므로 저장소 쪽은 **에이전트가 실행할 명령과 판정 규칙**으로 내주고, 에이전트가 결과를 돌려주면 허브가 대조한다 (I1 과 같은 길 · Q5). 선택 클라이언트가 있으면 클라이언트가 직접 잰다. 결과를 돌려받지 못하면 저장소 항목은 '미확인' 이다 (R10.3).
  [검증] 허브 · 저장소 상태 조합 fixture 마다 보고 문구.
- **R10.2 다르면** — 뒤처졌으면 작업 전에 fast-forward 를 안내한다. 갈라졌거나 커밋 안 된 변경이 있으면 **멈추고 묻는다** (1.x 원칙 '먼저 원격과 동기화').
  [검증] 갈라짐 fixture → '멈춤' 판정.
- **R10.3 확인한 것과 못 한 것** — 보고는 확인한 항목과 확인하지 못한 항목을 나눈다. 허브에 닿지 않으면 캐시로 열되 **'허브 미확인'** 을 적는다 — 확인한 척하지 않는다.
  [검증] 허브를 끈 fixture → 보고에 '허브 미확인' · 확인 항목 목록에 허브 항목 0.
- **R10.4 교차 대조** — 허브 task 가 가리키는 커밋 · 브랜치가 저장소에 없으면(push 전 · 다른 원격) 그 사실을 보고한다.
  [검증] 없는 sha 를 묶은 task fixture → 보고.

## 13. compact 직후 확인 (R11)

- **R11.1 체크포인트 자리** — 압축 직전 체크포인트(진행 task · 브랜치 · 검증 / 미검증 사실 · 다음 걸음)는 허브의 **콜사인 공간**에 남는다 (H14 · concept §4.2.4). 형식은 1.x compact 중계(`compact_relay_spec.md`)의 칸과 같다.
  [검증] 체크포인트 왕복 · 1.x 체크포인트 들여오기.
- **R11.2 압축 직후 세 가지** — ① 허브 확인 (내 task 상태 · 진행 한 줄 · 결정 응답 도착 · 그 사이 다른 콜사인이 바꾼 것 = version 차이) ② 기록 대조 (체크포인트와 압축 요약을 대조해 빠진 식별자를 알림) ③ 이어 가기 (다음 걸음 · 진행 기록에서 잇고, 끝난 것으로 기록된 일은 다시 하지 않고, 미검증은 미검증으로 보고).
  [검증] 체크포인트 + 일부 식별자를 뺀 요약 fixture → 빠진 식별자 보고. 그 사이 다른 콜사인 변경 fixture → version 차이 보고.

  [검증] Claude Code hook 경로 실측 (1.x compact 중계 실측과 같은 방식) · 지침 문장 존재.
- **R11.4 비밀 없음** — 체크포인트도 R0.5 를 따른다.

## 14. 허브가 닿지 않을 때 (R12)

- **R12.1 캐시로 열기** — 마지막으로 받은 브리핑 · handoff · 내 task 를 로컬 캐시(`.workflow-hub/`)에 둔다. 허브가 꺼져도 세션을 열 수 있다 (concept §4.5). 원격 MCP 만 쓰는 환경(선택 클라이언트 없음)에는 캐시가 없다 — 그 경우 시작 보고는 '허브 미확인 · 캐시 없음' 이다.
  [검증] 허브를 끈 fixture 두 가지 (클라이언트 있음 · 없음).
- **R12.2 보낼편지함** — 허브에 닿지 않는 동안의 쓰기는 `.workflow-hub/outbox/` 에 남고 다음 연결 때 보낸다. 보낼 때 version 이 어긋나면 409 를 보고하고 **자동 병합하지 않는다** — 해당 항목은 보낼편지함에 남는다 (D4).
  [검증] 오프라인 쓰기 → 재연결 → 반영. 그 사이 다른 콜사인 변경 → 409 보고 · 항목 잔존 · 덮어쓰기 0.
- **R12.3 보낼편지함은 세션 시작에 보인다** — 남은 항목 수를 R10 보고에 싣는다.
  [검증] 항목 n → 보고 n.

## 15. 노출 · 보안 (R13)

- **R13.1 기본 loopback** — 허브 기본 bind 는 `127.0.0.1`. 바깥 노출은 프로젝트가 프록시로 한다 (concept §8 말미).
  [검증] 기본 기동의 listen 주소.
- **R13.2 모든 쓰기 · 읽기에 토큰** — 부트스트랩 묶음(R2.3) 말고는 토큰이 있어야 한다. 토큰은 `Authorization: Bearer` 머리로만 받는다 (쿼리 · 쿠키로 받지 않는다). 토큰의 역할은 `web` (화면 공용 — 읽기 · 콜사인 등록) · `editor` (콜사인 토큰 — task · handoff · 지침 제안 등 쓰기) · `admin` (허브 관리 — 콜사인 거두기 · 공용 토큰 발급) 이고 이름은 design.
  [검증] 토큰 없는 요청 → 401. `web` 토큰으로 task 쓰기 → 403. 쿼리 문자열 `?token=` → 거절.
- **R13.2a 화면 = arcturus 과제 대시보드 방식 (Q4)** — 화면에는 **로그인이 없다**. 사람은 화면에서 자기 콜사인을 등록하고, 허브가 **한 번만** 돌려주는 콜사인 토큰을 그 브라우저 저장소에 두어 쓰기 요청에 `Bearer` 로 싣는다 — 이 브라우저의 쓰기는 그 콜사인 이름으로 이력에 남는다. 토큰이 없는 화면 요청은 **화면 공용 `web` 토큰**의 권한(읽기 · 콜사인 등록)으로 돈다. 공용 토큰은 관리자가 발급하고, 앞단 프록시가 '토큰 없는 요청에만' 붙이거나 허브 설정으로 켠다 — **기본은 꺼짐** (R13.1 loopback 기본과 맞춤: 켜지 않으면 화면도 콜사인 토큰이 있어야 읽는다). 선례: arcturus-port `8d24fcd7` — `deploy/homelab/Caddyfile` (`@anon not header Authorization *` → `request_header … Bearer {$ARCL_PORTAL_WEB_TOKEN}`) · `backend/internal/store/callsign.go` (`CanRegister` = web · editor · admin, 토큰 1회 반환 · 해시 저장, 이미 쓰는 이름 409) · `site/src/pages/tasks/index.astro` (localStorage `portal.callsign_token`, 401 이면 '이 브라우저에서 지우기 뒤 다시 등록' 안내).
  - 브라우저에서 등록한 콜사인도 R7.7 의 종류 · 승인 규칙을 따른다 (`human` 은 소유자 승인 전 `agent` 권한).
  - 쿠키를 쓰지 않으므로 CSRF 토큰 대신 **`Bearer` 머리 필수**가 교차 출처 위조를 막는다 (브라우저가 다른 출처의 폼 제출에 이 머리를 붙이지 않는다). 대신 토큰이 브라우저 저장소에 있으므로 화면은 **인라인 스크립트 · 외부 스크립트를 막는 CSP** 를 낸다 (워크벤치 `connect-src` 선례).
  - 화면은 '이 브라우저에서 콜사인 지우기' 를 낸다 — 토큰은 다시 나오지 않는다는 경고와 함께 (arcturus 와 같음).
  [검증] 공용 토큰 꺼짐 + 토큰 없는 화면 요청 → 401. 켜짐 → 읽기 200 · 쓰기 403 · 콜사인 등록 200 + 토큰 1회. 같은 이름 재등록 → 409. 다른 출처 페이지의 폼 POST(머리 없음) → 401 · 쓰기 0. 화면 응답 머리에 CSP. 실브라우저 왕복(CDP)으로 등록 → 쓰기 → 이력의 콜사인 이름.
- **R13.3 loopback 밖 경고** — loopback 이 아닌 주소에 bind 하면 기동 때 경고 한 줄 · healthz 에 노출 상태를 싣는다. 바깥에 노출된 허브에서는 누구나 프로젝트를 등록할 수 있다는 사실(R3.4)을 경고에 적는다.
  [검증] `0.0.0.0` 기동 → 경고 문구.
- **R13.4 상대 경로** — 화면의 링크 · API 호출 · 리다이렉트는 상대 경로라 접두사 프록시 뒤에서 그대로 돈다 (워크벤치 requirements §1.3 · §1.4 의 실측 결론 재사용 · arcturus 는 `/arcturus/` 접두사 뒤에서 돈다). 브라우저 저장소의 키는 허브 · 프로젝트별로 나눠 같은 호스트의 다른 허브와 섞이지 않게 한다.
  [검증] 접두사 프록시 fixture (워크벤치와 같은 방식).
- **R13.5 크기 상한** — 요청 본문 상한을 둔다 (기본 256KiB, 워크벤치와 같음). 위키 묶음 쓰기는 별도 상한 (design).
  [검증] 상한 + 1 바이트 → 413.

결론 — R0.7 은 지킬 수 있다. 판정 **핵심**은 모두 '그대로' 또는 '얇은 입구'이고, '리팩터' 는 입력 수집 층(상태 생성 · handoff 파서 · 로드맵 수집)뿐이다. design 이 지켜야 할 결합 다섯:

1. **자격 판정과 상태 계산이 갈라져 있다** — `compute_states` 는 받은 응답의 자격을 다시 보지 않는다. 허브는 `has_error_rules` → `qualify` → `compute_states` 순서를 강제해야 한다 (지금은 FS 의 `qualified_archive` 가 걸러 준다).
2. **L5 린트가 git HEAD 에 묶여 있다** — 작업 트리가 없는 허브에서 L5 는 **조용히 빠진다**. 줄 수 콜백을 주거나 '미측정' 으로 표시한다 (R5.5 에 더함).
3. **시계** — `derive_state` 의 `generated_at` · 진행 기록 시각 · 요청 날짜. 같은 입력이 날짜마다 다른 바이트를 낸다 → 시각은 인자로.
4. **WBS 게이트 함수 하나가 확인 · 로드 · 판정을 다 한다** — 판정부를 떼고 기존 함수는 그 위의 래퍼로 남겨 정본을 하나로 (규약 단일 출처).
5. **handoff 파서의 경로 의존** — `next_documents` 가 파일 위치 기준 상대 경로다. 허브의 handoff 는 파일이 아니므로 이 칸의 뜻을 design 에서 다시 정한다.

### 16.2 S2 — 위키 검사를 펼친 임시 디렉터리에서

방법: `ai-workflow/wiki/` (100 페이지) 와 memory_index (30 entry) 를 임시 디렉터리에 저장소 배치로 복사(135 파일, `diff -r` 동일)하고, 원본과 사본에 같은 드라이버를 돌려 결과를 비교했다. 경로가 상수인 대상은 드라이버에서 상수를 바꿔 끼웠다. **바꿔 끼운 것이 먹혔는지** 사본에만 결함 3개(index 가 가리키는 페이지 삭제 · 금지 위치 `docs/wiki/a.md` · L2 stub 삭제)를 넣어 확인했다 — 원본 green 그대로, 사본만 바뀜.

| 대상 | 경로 고정 지점 | 저장소 밖 의존 | 실측 | 판정 |
|---|---|---|---|---|
| V-1 `check_wiki_location.py` | :10 `REPO_ROOT`, :13~14 위키 · index, :19~22 금지 위치 4곳 | 없음 — 금지 위치 규칙은 저장소 배치 규칙이라 허브에서는 뜻이 없다 | 같음 · 결함 사본 FAIL | 인자화 필요 (3곳) — 허브는 정위치 확인만 |

결론 — E2 (있는 검사 재사용) 는 성립한다. 요구에 더할 것:

- 허브가 위키 디렉터리 밖에서 공급해야 할 입력: freshness 의 소스 시각(E3 의 원격 읽기), L2 선언 목록, memory_index, 기준 시각.
- **freshness 는 소스를 못 받으면 '미측정' 이어야 하고, 측정 대상 수를 결과에 실어야 한다** — 지금 코드는 대상이 줄어도 점수가 오른다 (R8.4 의 '미측정' 이 실제로 필요한 자리. 1.x 결함 후보로도 남긴다).
- operational · trend 는 저장소 검사 · git 에 묶여 허브 lint 에서 뺀다.
- 부수 발견 (1.x 결함 후보): `bidir_link.py` 의 위키 쪽 비대칭 루프가 `entry_id_stem` 을 읽는데, 이 변수는 위키 언급이 있는 entry 에서만 만들어진다 — 정렬상 첫 entry 에 언급이 없으면 `UnboundLocalError`, 아니면 앞 entry 의 id 가 남는다 (사본에서 첫 entry 를 지워 재현). 이 저장소는 위키 → memory 링크가 0건이라 드러나지 않았다.

### 16.3 S3 — 하네스별 원격 MCP (HTTP)

탐침: 표준 MCP SDK(`mcp` 1.27.0)의 streamable HTTP 서버 + `Authorization: Bearer <토큰>` 이 맞지 않으면 401 을 내는 앞단, 도구 `hub_ping` 하나(표식 문자열 반환). 서버가 요청마다 인증 결과 · User-Agent · 도구 호출을 기록한다. 하네스 설정에는 **환경 변수 참조만** 넣고(I3), 같은 설정에서 변수를 뺀 실행을 대조로 했다. 사용자 설정은 건드리지 않았다 — 명령줄 덮어쓰기 · 프로젝트 범위 설정 · 실행 뒤 제거(Antigravity, 아래) 로만.

| 하네스 (이 호스트의 판) | 등록 방법 | 환경 변수 참조 인증 | 모델이 도구를 불렀나 | 대조 (변수 없음) | 판정 |
|---|---|---|---|---|---|
| Claude Code 2.1.330 | `--mcp-config` JSON (`type: http`, `headers.Authorization: "Bearer ${WORKFLOW_HUB_TOKEN}"`) + `--strict-mcp-config` | **확장됨** (요청 9 중 8 인증 통과) | **불렀다** — 표식 반환, 서버 기록 1 | 요청 2 · 인증 0 · `NONE` | **실측 지원** |
| Codex 0.167.1 | `-c mcp_servers.<n>.url=…` · `-c mcp_servers.<n>.bearer_token_env_var="WORKFLOW_HUB_TOKEN"` (`codex mcp add --url --bearer-token-env-var` 와 같은 칸) | **됨** (승인 설정 전 요청 3 중 3 · 뒤 5 중 4) | **불렀다** — 단 비대화 `exec` 는 승인 정책 `never` 라 `MCP tool call requires approval` 로 거절됐고, 서버 단위 `default_tools_approval_mode="approve"` 를 더하자 성공 | 서버에 연결 자체를 안 함 (요청 0) · `NONE` | **실측 지원** (비대화는 서버 단위 승인 설정 필요) |
| Grok Build 1.0.44 | `grok mcp add -s project -t http -H 'Authorization: Bearer ${…}'` → `./.grok/config.toml` | **확장됨** (요청 4 중 4) | **미실측** — 이 호스트 Grok 모델 자격 증명 없음 (`401 … no auth context`) | 요청 2 · 인증 0 | **연결 · 인증 실측, 도구 호출 미실측**. 프로젝트 범위 서버는 **폴더 신뢰**(`--trust` 또는 대화형 허용) 가 있어야 뜬다 |

측정 결함 하나와 정정: MiniMax 첫 대조 실행에서 에이전트가 MCP 등록 실패 뒤 **탐침 디렉터리의 토큰 파일을 찾아 HTTP 로 직접 호출**했다. 토큰을 파일 · 프로세스 인자에서 빼고(서버는 환경 변수에서 읽고 지움) 다시 잰 값이 위 표다. Claude Code 실행은 MCP 도구만 허용(`--allowedTools`)했고, Codex 는 출력에 `mcp: hubprobe/hub_ping (completed)` 가 남아 MCP 경로임이 확인된다. Antigravity 의 리터럴 토큰 실행은 토큰 파일이 남아 있던 때라 호출 경로를 가리지 못했다.

뒷정리: Antigravity 는 사용자 범위에만 쓰므로 추가 → 측정 → `agy mcp remove` 했다. 실행 뒤 `~/.gemini/config/mcp_config.json` 은 `{"mcpServers": {}}` 이고, 측정 전에 이 파일이 있었는지는 판별하지 못했다(제거가 파일을 새로 써 생성 시각이 지워졌다 — 내용은 빈 목록이라 동작 영향 없음). Grok 사용자 설정은 해시로 불변을 확인했다.

결론 — 5 하네스 모두 원격 MCP(HTTP)로 허브에 닿는다 (R2.1). 요구에 더할 것:

- **토큰 전달은 하네스별로 (R2.5)** — `${VAR}` 헤더 참조는 Claude Code · Grok · MiniMax, Codex 는 `bearer_token_env_var` 칸, **Antigravity 는 참조를 못 한다**. 그 하네스의 토큰 전달은 Q7 결정으로 R2.5a (사용자 범위에만 값 · 경고).
- **비대화 실행의 도구 승인** — Codex 비대화는 서버 단위 승인 설정이 없으면 허브 도구를 못 부른다. 안내 페이지(R2.6)의 하네스별 명령에 이것을 포함한다.
- **프로젝트 범위 설정의 신뢰** — Grok 의 프로젝트 범위 서버는 폴더 신뢰가 있어야 뜬다. Grok 은 지원 4종(R2.8)에서 빠졌으므로 기록으로만 둔다.
- **허브 토큰을 에이전트가 볼 수 있는 곳에 두지 않는다** — 위 측정 결함처럼, 에이전트는 MCP 가 막히면 작업 디렉터리의 비밀을 찾아 직접 부를 수 있다. `.workflow-hub/env` (R4.3) 는 에이전트 작업 공간 안에 있으므로, 토큰 권한은 그 콜사인의 권한을 넘지 않아야 하고(R4.6), 허브는 MCP 밖 직접 호출도 같은 인증 · 같은 이력으로 다룬다 (R2.7 의 '같은 API').

### 17.2 1.x 유지보수 정책 (R16)

- **R16.1 결함 수리만** — 1.x 줄은 새 기능 · 새 명령 · 새 하네스 지원을 받지 않는다. 결함은 ① 문서화된 동작과 다른 것 ② 데이터 손실 · 저장소 오염 ③ 보안 ④ Python · 하네스 판 변화로 깨진 것이다.
  [검증] 1.x 줄 발행의 등급 판정(`release-status`)이 `feat` 커밋을 보면 `requires_decision` 을 세운다.
- **R16.2 판 번호** — 1.x 줄은 patch(`1.N.x`)만 낸다. minor 는 R16.4 의 안내 판 하나뿐이다.
  [검증] 1.x 줄에서 안내 판 뒤 minor · major 요청 → 거절.
- **R16.3 기간 = 2028-07-20 (Q6 결정)** — stable_guarantee 의 보장 끝까지 결함 수리를 한다. 그 뒤 1.x 는 끝(EOL)이고, 끝난 뒤의 1.x `session-start` 는 EOL 을 한 줄로 알린다 (막지 않는다).
  [검증] 기준 시각을 주입한 fixture — 날짜 전 안내 없음 · 뒤 EOL 한 줄 · 종료 코드 불변.
- **R16.4 안내 판** — 2.0.0 발행과 같은 때 1.x 마지막 minor 를 낸다: `session-start` 의 2.0 안내 한 줄(R14.8) · '허브로 옮김' 표식 거절(R14.6) · README 와 발행 노트에 2.0 · 전환 경로(부트스트랩) · 1.x EOL 날짜. 이것이 G4 의 '1 release 경고' 의 흐름판이다 — 1.x 흐름은 1.x 줄에서 지워지지 않고 2.0 에서 대체된다.
  [검증] 안내 판의 `session-start` 출력 · 표식 저장소에서 쓰기 거절 · 노트의 세 항목.
- **R16.5 분기** — 2.0 작업이 기본 브랜치에 들어가기 **전에** 1.x 줄을 별도 브랜치로 분기한다(이름은 design). 1.x 발행은 그 브랜치 머리에서, 같은 전량 게이트 · 발행 절차(RELEASE.md)로 한다. 1.x 에서 고친 결함이 2.0 에도 있으면 2.0 에도 고친다 (1.x → 2.0 방향만).
  [검증] 1.x 태그가 1.x 브랜치 위에 있고 게이트 증거가 그 커밋의 것. 1.x 결함 수리 커밋마다 2.0 쪽 대응(고침 · 해당 없음)이 기록돼 있다.
- **R16.6 1.x 소비자는 자동 갱신으로 2.0 을 받지 않는다** — 지금 플러그인 채널(`.claude-plugin/marketplace.json` → `source: ./plugin`)은 저장소의 브랜치를 따라 갱신된다. 2.0 이 기본 브랜치에 들어가도 1.x 소비자의 채널 갱신은 1.x 를 받아야 한다. 방법 (Q10 결정): 2.0 은 같은 marketplace 이름 · 경로의 kit 플러그인 채널을 내지 않는다. 기존 채널은 1.x 소유로 1.x 브랜치(R16.5)에서 갱신하고, 1.x 안내 판(R16.4)이 채널을 1.x 브랜치로 다시 등록하는 하네스별 한 줄 명령을 싣는다. 2.0 에 플러그인이 필요해지면 새 이름으로 낸다.
  [검증] 1.x 를 설치한 하네스에서 2.0 발행 뒤 채널 갱신 → 설치 판이 1.x 그대로 (지원 4종 중 플러그인 채널이 있는 하네스마다).
- **R16.7 'latest' 는 2.0** — 2.0.0 발행 뒤 1.x patch 발행은 GitHub Release 의 'latest' 표시를 가져가지 않는다.
  [검증] 1.x patch 발행 뒤 저장소의 latest release = 2.x.
- **R16.8 1.x 결함 후보의 자리** — 2.0 작업 중 드러난 1.x 결함(예: §16.2 의 `bidir_link` · freshness)은 1.x 줄 backlog 에 올리고 R16.1 로 분류한다.
  [검증] 1.x 줄 backlog 에 해당 task 존재.

## 18. 1.x 전환 (R14)

- **R14.1 감지** — 부트스트랩은 1.x 흔적을 감지해 전환 과정으로 들어간다: `ai-workflow/memory/active/` (브랜치 네임스페이스 · `state.json` · handoff · backlog) · `roadmap/` · `ai-workflow/wiki/` · memory_index · 진입 파일의 kit 생성 블록 · kit 플러그인 · hook · stdio MCP 설정. 찾은 것과 kit 판을 보고한다 (H13 · concept §16.1). 원격 MCP 는 파일을 못 보므로 감지는 **에이전트가 실행할 목록 명령 + 결과 대조**다 (I1).
  [검증] 1.x 저장소 fixture → 감지 보고에 위 항목.
- **R14.2 전환 계획 확인** — 무엇을 들이고 무엇을 남기는지 표(concept §16.1 2)로 보이고, 등록자가 확인한 것만 들인다. 원본 파일은 지우지 않는다.
  [검증] 일부만 고른 경우 허브에 그것만 · 저장소 파일 삭제 0.
- **R14.3 같은 ID 충돌** — 같은 task ID 가 여러 브랜치에 있으면 하나를 정본으로 들이고 나머지는 그 task 의 이력으로 들인다. 정본은 **그 task 파일을 마지막으로 바꾼 커밋의 시각이 가장 늦은 브랜치**, 같으면 기본 브랜치다 (Q1). 고른 근거(브랜치 · 커밋 · 시각)를 전환 보고에 싣는다.
  [검증] 같은 ID 3 브랜치 fixture (커밋 시각을 달리함 · 같은 시각 + 기본 브랜치 포함) → task 1 · 이력 2 · 정본 = 기대 브랜치.
- **R14.4 브랜치 기록 보관** — 브랜치마다의 handoff · sessions 는 브랜치 이름 그대로 **보관 기록**으로 들이고, 전환한 콜사인의 첫 handoff 는 현재 브랜치의 handoff 에서 시작한다 (H8 · G1). 보관 형식은 **원문 markdown 그대로 + 메타(브랜치 · 원래 경로 · 들인 시각 · 원래 커밋)**, 읽기 전용이고 구조화하지 않는다 (Q2).
  [검증] 브랜치 2개 fixture → 보관 2 · 콜사인 handoff 1 · 보관 본문 = 원문 바이트 일치.
- **R14.5 생성 블록** — 진입 파일의 kit 생성 블록은 들이지 않고(허브가 다시 렌더링), 손으로 쓴 부분은 프로젝트 지침 **초안**으로 들인다 (D11 의 승인을 거쳐 판이 된다).
  [검증] 생성 블록 + 손 문단 fixture → 초안에 손 문단만.
- **R14.6 git 쪽 표식** — 들여오기 뒤 `ai-workflow/` 에 '허브로 옮김' 표식(허브 · 프로젝트 · 시각 · kit 판)을 쓰기 지시로 남기고 커밋을 안내한다. 1.x 유지보수 판의 kit 쓰기 도구(`backlog-update` · handoff 갱신 · `refresh-state` 등)는 이 표식을 보면 **쓰기를 거절**하고 허브를 가리킨다 (두 정본 재발 방지 — concept §6).
  [검증] 표식이 있는 저장소에서 1.x `backlog-update --apply` → 거절 · 파일 변화 0.
- **R14.7 되돌리기** — 표식만 걷으면 1.x 흐름으로 돌아간다. 전환이 원본을 바꾸지 않았으므로 되돌림에 데이터 이동이 없다.
  [검증] 표식 제거 → 1.x `session-start` 정상.
- **R14.8 반대쪽 유도** — 1.x 안내 판(R16.4)부터 `session-start` 는 2.0 의 존재와 전환 방법(허브 주소 · 부트스트랩)을 안내한다 (G4 의 deprecation 안내와 같은 자리). 안내는 한 줄이고 막지 않는다.
  [검증] 1.x 유지보수 판 `session-start` 출력에 안내 1줄 · 종료 코드 불변.
- **R14.9 플러그인 · MCP 설정** — kit 플러그인 · hook · stdio MCP 설정은 허브 MCP 로 바꾸는 하네스별 안내를 내고, 지우는 것은 등록자 확인 뒤 (I4). 1.x 가 지원하던 하네스 가운데 2.0 지원 4종(R2.8) 밖의 것(Grok Build · OpenCode · pi-dev 등)을 쓰는 프로젝트에는 '2.0 지원 대상 아님 — 1.x 줄에 남거나 원격 MCP 수동 등록' 을 감지 보고에 적는다.
  [검증] 안내 문구 · 확인 전 삭제 지시 0.

## 19. git 내보내기 · 범위 밖 (R15)
