## 0. 한 줄 결론

> 지금 kit 은 **각 작업 환경에 깔려** git 의 state 문서를 다룬다. 허브는 그 무게중심을 서버로 옮긴다 —
> **작업 환경에는 kit 이 없어도 되고**, 허브 주소 하나로 부트스트랩해 허브가 워크플로우 규칙대로 task · handoff · 이력을 관리한다.
> kit(Python)은 **허브 서버 안에서** 돈다. 작업 환경이 받는 것은 허브가 내려주는 얇은 클라이언트와 진입 규칙뿐이다.
> 특히 **프로젝트가 공유하는 지침(AGENTS.md · CLAUDE.md 등)을 허브가 들고**, 새 환경의 셋업과 기존 환경의 갱신을 허브가 한다 (§4.3).
> 이것은 kit 의 기본 명제(git 의 state 문서 = 세션 복원 정본)를 바꾸는 일이고, **2.0.0 으로 낸다** (H12) — 2.0 의 흐름은 허브 하나, 로컬 kit + git 흐름은 1.x 유지보수 줄에 남는다.

그리고 "**부트스트랩퍼 등 필요한 도구는 허브에서 mcp로 제공**하자".

그리고 "이번 변경은 **2.0.0 준비**야 완전히 흐름이 바뀐다." → 물음 'D1 재결정' 답: **2.0 은 허브 단일, 1.x 유지보수**.

그리고 "**compact 동작 직후에도 허브 확인 및 기록된 작업 내역 f/u** 수행하도록 하자".

## 2. arcturus 실험 — 구성 · 효과 · 드러난 문제

### 2.1 구성

- 서버: Go 백엔드 (`arcl-portal`) + PostgreSQL + Astro 정적 사이트 + Caddy, 홈랩 한 대. 이관 9개 (`0001_init` … `0009_standard_task`).
- kit 서비스: `portal/kit/kitd.py` — 표준 라이브러리 HTTP, `GET /v1/rules` · `POST /v1/plan/check`. workflow_kit 을 **판 고정**으로 깐다 (`KIT_VERSION=1.27.0`).
- 클라이언트: `docs/tools/portal_task.py` — 표준 라이브러리만, 설치 없음 (Windows · macOS · Linux). `register` · `whoami` · `list` · `show` · `new` · `set` · `start` · `a2a …`. 옛 판은 `GET /v1/briefing/tool` 로 최신 도구를 받는다.
- 정본 배치: task = 포털 DB (이력 `ptask_event`, 동시 수정 `version` → 409) · 로드맵 · 카테고리 = git (수집기가 5분마다 `origin/main`) · **세션 서술(handoff) = git** · 작업 환경에는 여전히 kit 이 깔려 있다 (`session-start` 로 handoff 복원).

### 2.2 효과 (그 저장소 문서가 적은 것)

- 모든 환경의 task 가 한곳에 있고 바로 고친다. 누가 언제 무엇을 바꿨는지 콜사인으로 남는다 (ADR-043 §4).
- 같은 task 의 브랜치별 복사본 문제가 '넘겨받기' 로 끝난다 (ADR-043 §4).
- 세션 시작 브리핑이 main 의 최신 지침을 나른다 — 브랜치의 문서가 낡아도 따른다 (docs/42 §10).
- **클라이언트가 설치 없이 돈다** — 표준 라이브러리 한 파일, 서버가 최신판을 내려준다 (docs/42 §2 · §10). 이 문서의 목표(kit 없는 부트스트랩)의 씨앗이다.
- 서버가 제목 규칙과 done 게이트(검증 기록 · 열린 결정)를 강제한다 (docs/42 §3.4 · §11).
- 유휴 점검이 '진행 중인데 멈춤' · '커밋은 있는데 task 기록 없음' 을 묻는다 (docs/42 §9).

### 2.3 드러난 문제

| # | 문제 | 근거 |
|---|---|---|
| P1 | **두 정본** — git task 파일과 포털 task 가 같이 있다. 넘겨받지 않은 git task 는 여전히 git 이 정본이다 | ADR-043 §2 'git task' · 이식 개념 §5 |
| P2 | **kit 집계가 포털 task 를 모른다** — `state.json` · backlog 색인 · `roadmap_state.json` 파생 진척이 정본에서 밀려났다 | ADR-043 §2 '진행률' · §4 · docs/42 §5 |
| P3 | **kit 규칙의 예외** — 그 프로젝트에서는 `backlog-update` 로 task 를 만들지 않는다. kit 의 도구 · hook · 검사가 그 예외를 모른다 | docs/42 §1 원칙 1 · §7 |
| P4 | **반쪽 이전** — task 는 포털, handoff · 세션 종료 순서는 여전히 git + 로컬 kit. 세션 하나가 두 시스템을 오간다 | docs/42 §3.3 · §5 |
| P5 | **서버가 꺼지면 task 를 못 고친다** — 그동안은 손으로 적어 두고 나중에 옮긴다 (ADR-043 §4 는 'git task + workflow_kit 으로', docs/42 §6 은 'handoff 에' — 두 원문도 갈린다) | ADR-043 §4 · docs/42 §6 |
| P6 | **판 고정의 지연** — kit 서비스가 1.27.0 고정, 정본은 1.29.0. 환경의 kit 과 서버의 kit 판이 갈릴 수 있다 | `Dockerfile.kit` · homelab `docker-compose.yml` |
| P7 | **노출** — 공개 · 로그인 없음 (소유자 선택). 누구나 콜사인을 등록해 task 를 쓴다 | ADR-043 §2.2 |
| P8 | **이식 비용** (이 문서의 해석) — 프로젝트 하나를 위해 Go · Postgres · Astro · Caddy · 홈랩 배치를 지었고, 다른 프로젝트가 쓰려면 다시 짓는다 | 구성: `portal/README.md` · 홈랩 배치 |

P1~P4 · P6 은 '포털이 kit 밖에 있고, 작업 환경에도 kit 이 따로 있어서' 생긴다. 허브를 kit 안에 두고 작업 환경의 kit 의존을 걷어내면 풀린다.
P5 · P7 은 허브 정본을 고르는 순간 kit 이 같이 떠안는다 (§6).

## 4. 개념 — kit 허브

### 4.1 두 쪽의 몫

```
작업 환경 (kit 없음)                         허브 (kit 이 서버 안에서 돈다)
─────────────────────                        ──────────────────────────────
얇은 클라이언트 한 파일 (표준 라이브러리)  ⇄  HTTP API (콜사인 토큰)
진입 규칙 블록 (CLAUDE.md · AGENTS.md …)   ←  표준 규칙 · 프로젝트 규칙 렌더링
로컬 보낼편지함 (닿지 않을 때)             →  SQLite: task · handoff · 이력 · 결정 응답 · 콜사인
                                             판정: 계획 린트 · done 게이트 · 결정 상태 (kit 함수 직접 호출)
                                             생성: state.json · roadmap_state 형식의 상태 (같은 v1)
                                             화면: 워크벤치 확장 — 목록 · 계획 · 결정 답 · handoff · 이력
```

### 4.2 부트스트랩 — 프로젝트 등록부터 (H4 · H6)

허브는 **프로젝트가 없어도** 부트스트랩퍼를 내준다. 부트스트랩퍼 하나가 프로젝트 등록 · 환경 합류 · 지침 셋업을 모두 한다.
**H10 에 따라 부트스트랩퍼와 도구는 허브의 MCP 로 제공한다** — 아래 단계의 `hub.py …` 는 같은 일을 하는 MCP 도구로 읽는다. 로컬 파일 쓰기 · hook · 오프라인의 몫은 §14.

1. 소유자가 허브를 띄운다 — 허브 쪽에만 kit 을 깐다 (`python -m workflow_kit hub serve` 꼴, 이름은 design).
2. 작업 환경은 **허브 주소 하나**로, 저장소 뿌리에서 시작한다:
   `curl -fsS <허브>/v1/bootstrap -o .workflow-hub/hub.py && python3 .workflow-hub/hub.py init --hub <허브>`
3. `init` 이 하는 일:
   1. **프로젝트 식별** — `git remote get-url origin` 을 정규화한 값으로 허브에 묻는다 (§4.2.1).
   2. **등록 전이면 등록 과정** — 허브에 프로젝트를 만든다: 정규화한 git 주소 · 표시 이름 · 등록자(첫 콜사인 = 소유자 권한).
      저장소에 이미 있는 것을 **들여오기 후보로 보여 준다** — 진입 파일(AGENTS.md · CLAUDE.md …)은 프로젝트 지침 초안으로,
      kit 의 `ai-workflow/` (task · handoff · 로드맵 · 위키)가 있으면 들여오기(§4.6)로. 무엇을 들일지는 등록자가 고른다.
   3. **등록돼 있으면 합류** — 콜사인 등록 · 토큰 저장(`.workflow-hub/env`, 600). `.gitignore` 규칙은 §4.2.2. 새 콜사인의 권한은 프로젝트 설정(D11)을 따른다.
   4. **지침 셋업** — 허브가 렌더링한 진입 파일을 쓴다 (§4.3).
4. 그 뒤 세션은 `hub.py start` (브리핑 + 내 task + 마지막 handoff) → 작업 (`hub.py task …`) → `hub.py end` (handoff 보고) 로 돈다.
   Windows 는 `python` (백신이 막는 실행 파일을 만들지 않는다 — kit 의 `wk.exe` 교훈).
5. 클라이언트 · 규칙 판이 바뀌면 `start` 가 알리고 `--update` 로 받는다 (arcturus `start --update-tool` 과 같은 길).

하네스 플러그인 · hook 은 선택이다 — 있으면 `start` · `end` 를 자동으로 부르고, 없어도 진입 규칙만으로 돈다.

#### 4.2.1 프로젝트 식별 — git 주소 (H7)

- **키 = 정규화한 원격 주소** — 호스트 · 경로만 남긴다: `git@github.com:ykylee/standard_ai_workflow.git` · `https://github.com/ykylee/standard_ai_workflow` · `ssh://git@github.com/ykylee/standard_ai_workflow.git` 가 모두 `github.com/ykylee/standard_ai_workflow` 하나가 된다
  (스킴 · 사용자 · 포트 표기 · 끝의 `.git` · `/` 제거, 호스트는 소문자). 경로의 대소문자는 호스트 규칙에 맡긴다 (GitHub 은 구분 안 함 · Gitea 등은 설정 따라) — 정규화 규칙은 design.
- 허브 안의 프로젝트 ID 는 따로 두고, git 주소는 **별칭 목록**으로 매단다 — 저장소 이전 · 이름 바꾸기 · 미러를 같은 프로젝트로 묶을 수 있게 (F2).
- 허브는 주소를 **식별에만** 쓴다 — 그 주소에 접근하지 않는다 (위키 저장소 참조를 읽는 E3 는 별도 설정).
- 같은 원격의 worktree · 클론은 모두 같은 프로젝트다. 브랜치는 프로젝트 안의 구분으로 남는다 (task 의 브랜치 칸).

#### 4.2.2 콜사인 등록 정보는 git 에 들어가지 않는다 (H9)

- 콜사인 등록 정보(허브 주소 · 프로젝트 ID · 콜사인 · 토큰)는 `.workflow-hub/` 아래에 두고, **이 디렉터리를 `.gitignore` 에 넣는 것이 규칙**이다.
  클라이언트 원문(`hub.py`)도 같은 디렉터리라 커밋되지 않는다 — 허브에서 언제든 다시 받는다.
- 부트스트랩퍼(`init`)가 **토큰을 쓰기 전에** `.gitignore` 에 `/.workflow-hub/` 줄을 더하고, `git check-ignore` 로 실제로 무시되는지 확인한다.
  무시되지 않으면(다른 규칙의 `!` 부정 · 이미 추적 중인 파일) **토큰을 쓰지 않고 멈춘다** — 토큰이 커밋되는 길을 먼저 막는다.
- `.gitignore` 에 줄을 더한 변경은 커밋 대상이다 (모든 클론이 같은 규칙을 갖게). `start` 도 매번 같은 확인을 하고, 규칙이 빠졌으면 알린다.
- 같은 클론의 worktree 는 같은 콜사인을 쓴다 — 새 worktree 면 `.workflow-hub/env` 를 복사한다 (arcturus `.portal.env` 와 같은 길, docs/42 §2).

#### 4.2.3 세션 시작 — 허브와 저장소의 최신 상태를 항상 확인한다 (H11)

허브가 렌더링하는 **표준 규칙 층**(§4.3)에 들어가는 규칙이다 — 모든 프로젝트 · 모든 하네스의 진입 파일에 실린다.
세션 시작 도구(`start`, MCP 로는 같은 일을 하는 도구 — H10)가 두 쪽을 함께 확인하고 결과를 한 번에 보고한다.

| 쪽 | 확인하는 것 | 다를 때 |
|---|---|---|
| 허브 | 닿는가 · 지침 판(바뀜이면 먼저 읽음, 진입 파일 갱신 — §4.3) · 클라이언트 · 규칙 판 · 내 handoff · 내 task · 맡은 이 없는 열린 task · 보낼편지함에 남은 것 (D4) | 닿지 않으면 캐시로 열되 '허브 미확인' 을 보고에 적는다 — 확인한 척하지 않는다 |
| 저장소 | `git fetch` 뒤 현재 브랜치와 원격의 차이(뒤처짐 · 앞섬 · 갈라짐) · 기본 브랜치 머리 · 커밋 안 된 변경 · `.gitignore` 규칙 (H9) | 뒤처졌으면 작업 전에 fast-forward 로 맞춘다 · 갈라졌거나 커밋 안 된 변경이 있으면 멈추고 묻는다 (kit 원칙 '먼저 원격과 동기화') |

- 두 쪽의 결과를 대조한다: 허브 task 가 가리키는 커밋 · 브랜치가 저장소에 없으면(push 전 · 다른 원격) 그 사실을 보고한다.
- 보고에는 무엇을 확인했고 무엇을 확인하지 못했는지를 나눠 적는다.

#### 4.2.4 compact 직후 — 허브 확인 · 기록된 작업 이어 가기 (H14)

1.x 는 압축 전후를 `compact-checkpoint` 로 중계한다 (ADR-030, `core/compact_relay_spec.md`) — 압축 직전 기계 층(진행 task · 브랜치)과
판단 층(검증 · 미검증 사실 · 다음 걸음)을 `.compact/` 에 적고, 압축 뒤 `SessionStart(compact)` 가 재주입한다.
2.0 에서는 그 기록의 자리가 **허브의 콜사인 공간**(H8)이고, 압축 직후 할 일이 셋이다:

1. **허브 확인** — 세션 시작 확인(§4.2.3)의 허브 쪽 가벼운 판: 내 task 의 지금 상태 · 진행 한 줄 · 결정 응답 도착 · 다른 콜사인이 그 사이 바꾼 것 (version 차이).
2. **기록 대조** — 압축 직전 체크포인트(다음 걸음 · 미검증 사실)와 압축 요약을 대조해 빠진 식별자를 알린다 (1.x §5 의 대조를 허브가 한다).
3. **이어 가기 (f/u)** — 체크포인트의 '다음 걸음' 과 진행 중 task 의 진행 기록에서 이어 간다. 이미 끝난 것으로 기록된 일을 다시 하지 않고, 미검증으로 남은 것은 미검증으로 보고한다.

- 전달 경로: 압축 hook 이 있는 하네스(Claude Code `PreCompact` · `PostCompact` · `SessionStart(compact)`)는 hook 이 체크포인트를 올리고 재주입한다 —
  hook 은 MCP 도구를 못 부르므로 **선택 로컬 클라이언트(I1)** 가 이 몫이다. hook 이 없는 하네스는 **표준 규칙 층의 지침**("압축 직후 첫 행동은 허브 확인 · 기록 대조")이 받친다.
- 체크포인트도 비밀을 싣지 않는다 (허브에 남는다).

### 4.3 프로젝트 공유 지침 — 허브에서 셋업 · 공유 (H5)

지금은 두 갈래다. kit 은 표준 규칙 블록을 **생성물**로 진입 파일에 넣고(`core/global_workflow_standard.md` → CLAUDE.md · AGENTS.md 의 `## Working Principles` 등), 나머지는 프로젝트가 손으로 쓴다.
arcturus 는 main 의 AGENTS.md · docs/42 를 브리핑으로 나른다 — 정본은 여전히 저장소 파일이고, 고치려면 main 에 커밋한다 (docs/42 §10).

허브에서는 **지침을 허브가 정본으로 들고 하네스별 파일로 렌더링**한다:

| 층 | 내용 | 누가 고치나 |
|---|---|---|
| 표준 규칙 | kit 판의 Working Principles · Session Close Order · 메모리 갱신 경로 — **허브 모드 판** (명령이 `hub.py …`) | kit 릴리스 (허브의 kit 판) |
| 프로젝트 지침 | 프로젝트 프로파일 · 실행 · 검증 명령 · 금지 사항 · 역할 (지금 CLAUDE.md 의 '프로젝트 실행 기본값' 같은 것) | 허브 화면 · API — 편집 권한 콜사인, 이력 · 판 번호가 남는다 |
| 하네스 어댑터 | 같은 내용을 하네스마다의 파일 · 형식으로 — `AGENTS.md` (Codex · 공용) · `CLAUDE.md` · `MiniMax.md` · `ANTIGRAVITY.md` 등 (지금 bootstrap 이 아는 진입 파일), 크기 예산 | kit (지금 플러그인 · 진입 파일 생성기의 렌더러) |
| 환경 덧붙임 (선택) | 그 환경만의 경로 · 장비 메모 | 그 환경 (로컬, 허브는 모른다) |

흐름:

1. **셋업** — `hub.py init` 이 그 환경의 하네스를 묻거나 감지해, 허브가 렌더링한 진입 파일을 쓴다. 파일 머리에 허브 · 프로젝트 · 지침 판을 적는다.
2. **공유 · 갱신** — `hub.py start` 가 지침 판을 비교해 바뀌었으면 알리고 다시 쓴다 (`[바뀜]` 을 먼저 읽게 — arcturus 브리핑과 같은 길). 콜사인마다 마지막으로 받은 판을 허브가 적어 둔다 — '이 환경은 옛 지침으로 돈다' 가 화면에 보인다.
3. **로컬에서 고친 것** — 진입 파일의 렌더링 영역이 허브 판과 다르면 덮어쓰지 않고 멈춰 알린다 (조용히 덮으면 작업이 사라진다). 고칠 것은 허브에 제안으로 올린다.
4. **저장소에 커밋하나** — D10. 커밋하면 git 만 보는 사람 · 도구도 지침을 읽지만 두 정본이 된다. 커밋하지 않으면(`.gitignore`) 허브가 유일한 정본이다.

### 4.4 무엇을 허브가 관리하나

| 대상 | 지금 (kit, git) | 허브 모드 | 근거 |
|---|---|---|---|
| task (상태 · 계획 칸 · 진행 · 결과 · 검증) | `active/<branch>/backlog/tasks/*.md` | **허브 정본** | H1 |
| handoff (기준선 · 진행 · 다음 시작 · 위험) | `active/<branch>/session_handoff.md` | **허브 정본 · 콜사인별** — 세션 끝에 `hub.py end` 로 올리고, 그 콜사인의 다음 `start` 가 돌려준다 | H4 · H8 |
| 이력 | git log | 허브 이벤트 표 — 누가 (콜사인) · 언제 · 무엇 · 이전 값 | H4 · arcturus `ptask_event` |
| 결정 응답 (`workflow-kit-plan-response/1`) | 받은편지함 파일 → `plan-import` | 허브가 받아 같은 형식으로 보관 · 게이트가 바로 읽음 | claim_plan_spec 형식 그대로 |
| 상태 요약 (`state.json` 형식) | 브랜치마다 git 파일에서 생성 | 허브가 **콜사인별로** 같은 형식으로 생성 · `start` 가 돌려줌 (프로젝트 전체 요약도 따로) | P2 · H8 |
| 작업 이력 메모리 (세션 기록 · compact 중계 · lessons) | `active/<branch>/sessions/` 등 | **콜사인별** | H8 |
| 로드맵 · 마일스톤 · WBS | git | D8 | — |
| 선점 | 브랜치 push | 허브 '맡기' (같은 task 두 번째 = 409) | arcturus 409 |
| 환경 식별 | `host_id` (registry) | 콜사인 + 토큰 | registry 와 하나로 |
| 프로젝트 공유 지침 | 진입 파일 (표준 블록은 생성물 · 나머지는 손으로) | **허브 정본** — 하네스별 파일로 렌더링해 셋업 · 갱신 (§4.3) | H5 |
| 코드 · 문서 변경 | git | **git 그대로** — 허브는 커밋 sha 를 task 에 묶어 둘 뿐 | 허브는 프로젝트 산출물을 갖지 않는다 |
| git 사본 | 정본 | **내보내기** (선택) — 정기 스냅샷을 저장소에 커밋 · 감사 · 허브 소실 대비 | D6 |

### 4.5 허브가 닿지 않을 때

- arcturus 는 handoff 에 적어 두고 손으로 옮긴다 (P5). kit 허브에서는 클라이언트가 **로컬 보낼편지함**(`.workflow-hub/outbox/`)에 쓰고 다음 연결 때 보낸다.
  충돌(다른 환경이 먼저 고침)은 `version` 409 로 드러내고 자동 병합하지 않는다 — D4.
- 마지막으로 받은 브리핑 · handoff · 내 task 는 클라이언트가 로컬 캐시에 둔다 — 허브가 꺼져도 세션을 열 수는 있다.

### 4.6 기존 kit 소비자

**2.0.0 은 허브 단일 흐름이다** (H12 · 고친 D1). 로컬 kit · git 정본 흐름은 **1.x 유지보수 줄**에서 결함 수리만 받는다 — G3 (SemVer 보장)의 범위는 1.x 이고, 2.0 은 major 라 흐름을 바꿀 수 있다. G4 에 따라 1.x 마지막 판에 deprecation 안내 (2.0 으로 옮기는 길 = 들여오기).
이미 git 에 task · handoff 가 있는 프로젝트는 허브로 **들여오기**(import) 한 번으로 옮긴다 — 같은 ID 를 지킨다 (arcturus 넘겨받기의 일괄판).

## 6. 위험

- **명제 변경의 파급** — git 정본을 전제로 한 검사 · 문서가 많다. 허브 모드를 별도 경로로 두어 기존 경로는 손대지 않는 것이 완화책이다.
- **서버 운영을 kit 이 떠안는다** — 백업 · 업그레이드 · 이관 · 노출. kit 은 기본값(loopback · 토큰)과 운영 가이드까지만 내고 배치는 프로젝트 몫으로 둔다 (PURPOSE 제외 '인프라 IaC').
- **허브가 단일 장애점** — handoff 까지 허브로 가면 허브가 꺼진 동안 세션 복원이 캐시에 의존한다. 로컬 캐시 · 보낼편지함 · git 내보내기가 완화책이다.
- **얇은 클라이언트의 판 갈림** — 클라이언트 판과 허브 판이 어긋나면 조용히 틀린다. 클라이언트가 판을 실어 보내고 허브가 모르는 판은 거절한다 (kit 의 '모르는 인자는 거절' 교훈).
- **두 정본의 재발** — 들여오기 뒤 git 쪽 task · handoff 를 계속 고치면 P1 이 돌아온다. 들여오기가 git 쪽에 '허브로 옮김' 표식을 남기고 kit 도구가 그 표식에서 쓰기를 거절해야 한다.
- **A2A 범위** — 메시지 중계는 kit 의 '중앙이 하네스에 메시지를 보내지 않는다'(multi_workspace_orchestration §0.6)와 부딪친다. 첫 판에서 빼는 것이 기본값 (D5).
- **arcturus 와의 갈래** — kit 허브가 생기면 두 구현이 된다 (D7).
- **지침의 조용한 덮어쓰기 · 낡음** — 허브가 진입 파일을 다시 쓰면 로컬 편집이 사라질 수 있고, `start` 를 안 부른 환경은 옛 지침으로 돈다. 렌더링 영역 대조(다르면 멈춤)와 콜사인별 받은 판 표시가 완화책이다.
- **공개 노출 시 원문 유출** — 허브에 handoff 까지 실리면 노출 범위가 넓어진다. 비밀을 싣지 않는 규칙과 기본 비공개가 필요하다.

## 11. 위키도 허브에서 — 검토 (결정 2026-11-20)

소유자 제기: "워크플로에서 구축하는 위키도 허브에서 관리 가능하도록 구축할 수 있는지 검토해보자" (TASK-2026-11-20-claude-workflow-hub-concept-003, M-030/WBS-30.2).

### 11.1 지금의 kit 위키

- 자리 · 추적: `ai-workflow/wiki/` 하나 (R1), git 추적. 이 저장소 기준 `.md` 100개 — 5종 페이지 78 (entities 12 · concepts 28 · decisions 34 · patterns 4 · queries 0), 나머지는 SCHEMA · index · log · INGEST_GUIDE · `sources/` · `topics/`. `log.md` 2,059줄 — SCHEMA §0 · §1.
- 쓰기: ingest = 소스(handoff · backlog)를 읽어 5~15 페이지 갱신 + `log.md` 한 줄 + **1 커밋 = 1 ingest** (SCHEMA §2, R2). 병합은 additive (R5), 브랜치 병합의 의미 충돌은 `merge-doc-reconcile` + LLM 검토 (R7 · A4).
- 판정: SCHEMA 는 lint 5항목 (모순 · 스테일 · 고아 · 누락 · 깨진 backlink) 과 V-1~V-8 을 정하지만, **자동화는 대부분 계획(planned) 상태**다 (SCHEMA §4.1 · §5.3). 실제로 있는 것은 `check_wiki_location.py` (V-1) · `check_wiki_index_structure.py` (V-4, 고아 · 누락) 와 둘을 묶는 `check_wiki_lint.py` 이고, 경로가 `REPO_ROOT / ai-workflow / wiki` 로 고정돼 있다. `[CONTRADICTION]` 을 찾는 kit 코드는 없다. 신선도 점수(`score_wiki_maintainability`)는 `last_ingested_from` 이 가리키는 **코드 파일의 시각**과 비교한다.
- 연결: memory_index ↔ wiki 양방향 링크 감사 · 동기화 (`common/state/bidir_link.py`) — 발행 노트 끝 감사 절이 이것이다.
- 형식 교환: OKF 내보내기 · 들여오기 (`okf_export.py` · `okf_import.py`, OKF v0.2 — ADR-026).

### 11.2 허브로 옮기면 맞는 까닭

- **ingest 입력이 이미 허브에 있다** — 허브 모드에서는 handoff · backlog(task)가 허브 정본이다 (D9). 위키만 git 에 남으면 ingest 가 두 시스템을 오간다 (§2.3 P4 와 같은 반쪽 이전).
- **kit 없는 환경 (H4) 에는 lint · index 도구가 없다** — 허브가 판정해야 규칙이 지켜진다.
- **여러 환경의 동시 ingest** — 지금은 git 병합에서 충돌이 나고 R7 이 그 뒤처리다. 허브에서는 페이지 단위 `version` 409 로 쓰는 순간 드러난다.
- **지침(H5)과 같은 성격** — 프로젝트가 공유하는 지식이다.

### 11.4 어려운 점

- **저장소를 가리키는 참조** — 페이지의 `last_ingested_from` · 상대 링크가 저장소 파일을 가리킨다. 허브는 저장소를 갖지 않으므로 링크 검사 · 신선도 점수(코드 파일 시각)를 그대로 못 한다.
  출처에 **저장소 + 커밋 sha** 를 싣거나, 허브가 프로젝트 git 원격을 읽기 전용으로 읽어야 한다 (arcturus 수집기가 `origin/main` 을 읽는 것과 같은 길). 못 읽으면 '통과' 가 아니라 '미측정' 으로 보여야 한다.
- **memory_index 의 자리** — 양방향 링크의 상대편이다. 위키만 허브로 가면 링크가 시스템 경계를 넘는다.
- **ADR 과 계획 문서의 경계** — ADR 은 위키 `decisions/` 에, concept · requirements 문서는 `docs/planning/` (git) 에 있다. 위키가 허브로 가면 둘이 갈라진다.
- **발행 파이프라인의 위키 감사** — kit 자기 저장소의 발행 노트가 위키를 읽는다. 허브 모드 프로젝트에서는 허브에 물어야 한다.
- **규모** — 페이지 100 · log 2,059줄은 SQLite 에 작다. 문제는 크기가 아니라 위의 참조다.

design 전 조사: `check_wiki_location` · `check_wiki_index_structure` · `score_wiki_*` · `bidir_link` 를 저장소 뿌리 대신 **펼친 임시 디렉터리**로 돌릴 수 있게 하는 범위 (지금은 경로 고정 — E2 기본값의 전제).

## 12. 프로젝트 등록 · 식별 — 결정: 권고안 F1~F5 (2026-11-20)

소유자 지시 (H6 · H7): 부트스트랩퍼가 프로젝트 등록부터 하고, 프로젝트는 git 주소로 구분한다 (§4.2 · §4.2.1). 남은 세부:

| # | 물음 | 기본값 (권고) | 다른 길 |
|---|---|---|---|
| F1 | 원격이 없는 저장소 (로컬 전용) | **등록을 거절하고 원격을 먼저 만들라고 안내** — git 주소가 식별 키이므로 | 허브가 임시 ID 를 주고 나중에 주소를 매단다 |
| F2 | 주소가 바뀌거나 미러 · 포크 | **이전 · 미러는 별칭으로 같은 프로젝트**(등록자가 묶음), **포크는 다른 프로젝트** (포크는 갈라진 작업이다) | 주소마다 언제나 다른 프로젝트 |
| F3 | 원격이 여럿일 때 | **`origin`**, 없으면 하나를 고르라고 묻는다 | 모든 원격을 별칭으로 등록 |
| F4 | 누가 프로젝트를 등록하나 | **허브에 닿는 누구나 등록 가능, 등록자가 소유자** — 허브 노출 범위(loopback + 토큰)로 막는다 | 허브 관리자가 등록 허용 토큰을 내준다 |
| F5 | 한 저장소에 여러 프로젝트 (모노레포) | **첫 판은 저장소 하나 = 프로젝트 하나** | 주소 + 하위 경로를 키로 |

정규화 규칙(호스트별 대소문자 · 포트 · 서브그룹)은 결정이 아니라 design 의 몫이다.

## 13. 콜사인별 작업 기억 — 결정: 권고안 G1~G3 (2026-11-20)

소유자 지시 (H8): 작업 이력 메모리 · handoff · state 는 콜사인별로 관리한다.

- kit 의 지금은 **브랜치가 작업 공간 단위**다 — `active/<branch>/` 에 handoff · backlog · state · sessions 가 있고, 새 브랜치는 seed 로 시작해 기본 브랜치로 합류할 때 반영 · 아카이브된다 (`multi_workspace_orchestration.md` §2.1).
  허브에서는 그 단위가 **콜사인**이 된다. 콜사인은 '한 작업 환경' 이므로 브랜치보다 수명이 길고, 브랜치 seed · 합류 반영이 필요 없어진다.
- **task 는 프로젝트 공용**이다 — 맡은 이 칸에 콜사인이 붙고 맡기(409)로 선점한다. 그래서 kit 의 '브랜치마다 같은 task 의 복사본' 문제가 생기지 않는다 (arcturus P1 의 뿌리).
- 프로젝트 화면은 콜사인별 handoff · state 를 모아 '지금 누가 무엇을' 을 보인다 (kit 대시보드의 브랜치 취합과 같은 자리).

| # | 물음 | 기본값 (권고) | 다른 길 |
|---|---|---|---|
| G1 | 콜사인 안에서 브랜치 구분 | **콜사인 하나에 handoff · state 하나**, 브랜치는 task · 기록의 칸으로만 | 콜사인 × 브랜치마다 따로 |
| G2 | 콜사인을 거두거나 오래 쉬면 | **기록은 보관(읽기 전용)으로, 맡던 열린 task 는 맡은 이를 비워 다른 콜사인이 이어받게** — kit 합류 반영 · 아카이브의 허브판 | 맡은 이를 그대로 두고 사람이 정리 |
| G3 | 다른 콜사인의 기록 접근 | **프로젝트 안에서 모두 읽기, 쓰기는 그 콜사인만** | 본인 · 소유자만 읽기 |

## 14. MCP 로 도구 제공 — 결정: 권고안 I1~I4 (2026-11-20)

소유자 지시 (H10): 부트스트랩퍼 등 필요한 도구는 허브가 MCP 로 제공한다.

### 14.1 그림

- 허브가 **원격 MCP 서버**(MCP 의 HTTP 전송)를 연다. 하네스는 허브 주소 하나를 MCP 서버로 등록하면 도구가 보인다 — 설치 없음 (H4).
  주요 하네스(Claude Code · Codex 등)가 원격 MCP 를 지원하므로 하네스 중립 원칙과 맞는다 (지원 범위는 requirements 에서 하네스별로 잰다).
- 도구 묶음 (이름은 design): **부트스트랩** (프로젝트 조회 · 등록 · 콜사인 등록 · 지침 셋업) · task · handoff · 상태 · 지침 · 위키 · 결정 응답.
- kit 의 지금 MCP 는 **로컬 stdio 서버**다 (읽기 전용 · 쓰기 서버). 허브 MCP 는 새 표면이다 — 원격 전송 · 인증 · 다중 콜사인.

### 14.2 원격 MCP 가 못 하는 것

허브 MCP 는 **작업 환경의 파일을 쓸 수 없다**. 그런데 부트스트랩에는 로컬 쓰기가 있다 — 진입 파일 (H5 · D10), `.gitignore` 와 `git check-ignore` 확인 (H9), 콜사인 토큰 저장, 세션 hook, 오프라인 보낼편지함 (D4).
또 하나의 문제: **등록 전**에는 토큰이 없다 — MCP 연결 자체를 어떻게 인증하나.

### 14.3 정할 것 — **결정: 권고안 I1~I4**

| # | 물음 | 기본값 (권고) | 다른 길 |
|---|---|---|---|
| I1 | 로컬 파일 쓰기 (진입 파일 · `.gitignore` · 토큰) | **MCP 도구가 '쓸 파일과 내용 · 해시' 를 돌려주고 에이전트가 쓴다 → 확인 도구가 해시를 대조**. hook · 오프라인 보낼편지함용 얇은 로컬 클라이언트(표준 라이브러리 한 파일)는 **선택**으로 남긴다 | 로컬 클라이언트 필수 (MCP 는 조회 · 쓰기 API 만) |
| I2 | 등록 전 인증 | **토큰 없이 부를 수 있는 도구는 부트스트랩 묶음뿐** (프로젝트 조회 · 등록 · 콜사인 등록). 등록 뒤에는 토큰이 있어야 나머지가 보인다 | 등록 전용 초대 토큰을 허브 관리자가 내준다 |
| I3 | 토큰을 하네스에 주는 길 | **환경 변수 참조** — 하네스 MCP 설정에는 `${WORKFLOW_HUB_TOKEN}` 꼴만, 값은 `.workflow-hub/env` (H9 로 git 밖) | 하네스 MCP 설정 파일에 값을 직접 (그 파일도 `.gitignore`) |
| I4 | 허브 MCP 를 하네스에 등록하는 첫걸음 | **하네스별 한 줄 명령을 허브가 안내 페이지로 제공** (`<허브>/` 에 접속하면 보임) — 사람이 한 번 실행 | kit 플러그인이 등록 (kit 설치가 필요해 H4 와 어긋남) |

하네스 hook 은 MCP 도구를 부르지 못하는 경우가 많다 — 세션 시작 · 끝 자동화가 필요하면 I1 의 선택 클라이언트가 그 몫이다.

## 16. 2.0.0 (2026-11-20 소유자)

"이번 변경은 2.0.0 준비야 완전히 흐름이 바뀐다" → D1 재결정 "2.0 은 허브 단일, 1.x 유지보수".

- **2.0.0** = 허브 흐름 하나 (H1~H12). 작업 환경은 kit 을 깔지 않고 허브 MCP · 진입 지침으로 일한다.
- **1.x** = 지금의 로컬 kit + git 흐름. 유지보수 줄 — 결함 수리만, 새 기능 없음. 마지막 1.x 판에 deprecation 안내와 2.0 으로 옮기는 길(들여오기)을 싣는다 (G4).
- PURPOSE 의 G1 · G3 · §4 명제는 2.0 판으로 다시 쓴다 (D9 는 '허브 모드에서는' 이 아니라 2.0 의 명제가 된다) — requirements 에서.
- 고칠 것 영향: §4.6 · §5 (기존 도구는 1.x 줄에 남음) · §7 단계 끝에 '2.0.0 발행 · 1.x 분기'.

### 16.1 1.x 프로젝트의 전환 — 부트스트랩이 이끈다 (H13)

1.x 프로젝트가 처음 2.0 허브의 부트스트랩(`init`)을 부르면, 부트스트랩이 **1.x 흔적을 감지해 전환 과정으로 들어간다** — 등록 과정(§4.2)의 한 갈래다.

1. **감지** — `ai-workflow/memory/active/` (브랜치 네임스페이스 · `state.json` · handoff · backlog) · `ai-workflow/memory/active/roadmap/` · `ai-workflow/wiki/` · memory_index · 진입 파일의 kit 생성 블록 · `.claude` 등의 kit 플러그인 설정. 찾은 것과 kit 판(1.x)을 보고한다.
2. **전환 계획을 보인다** — 무엇을 허브로 들이고 무엇을 남기는지, 등록자가 확인한다:

   | 1.x | 2.0 허브 |
   |---|---|
   | 브랜치마다의 task (`backlog/tasks/*.md`) | 프로젝트 공용 task (같은 ID). 같은 ID 가 여러 브랜치에 있으면 가장 최근 것 하나 + 나머지는 이력 |
   | 브랜치마다의 handoff · sessions (`active/<branch>/`) | **보관 기록**으로 들이고(브랜치 이름 그대로), 전환을 한 콜사인의 첫 handoff 는 현재 브랜치의 handoff 에서 시작 (H8 · G1) |
   | 로드맵 · WBS (`roadmap/`) | 허브 로드맵 (D8) |
   | 위키 · memory_index | 허브 위키 · memory_index (E1 · E5, OKF 로 운반) |
   | 진입 파일의 kit 생성 블록 · 손으로 쓴 프로젝트 지침 | 생성 블록은 버리고 허브가 다시 렌더링 · 손으로 쓴 부분은 프로젝트 지침 초안 (H5 · D11) |
   | kit 플러그인 · hook · MCP(stdio) 설정 | 허브 MCP 로 바꾸는 하네스별 안내 (I4) — 지우는 것은 등록자 확인 뒤 |

3. **들여오기** — 확인한 것만 들인다. 원본 파일은 지우지 않는다.
4. **git 쪽 표식** — `ai-workflow/` 에 '허브로 옮김' 표식(허브 · 프로젝트 · 시각 · kit 판)을 남겨 커밋을 안내한다. 1.x 유지보수 판의 kit 도구는 이 표식을 보면 쓰기를 거절하고 허브를 가리킨다 (두 정본 재발 방지 — §6).
5. **반대쪽 유도** — 1.x 유지보수 판의 `session-start` 가 2.0 의 존재와 전환 방법(허브 주소 · 부트스트랩)을 안내한다 (G4 deprecation 안내와 같은 자리).

전환은 되돌릴 수 있어야 한다 — 원본을 지우지 않고, 표식만 걷으면 1.x 흐름으로 돌아간다. 세부(같은 ID 충돌 규칙 · 브랜치 기록의 보관 형식)는 requirements.
