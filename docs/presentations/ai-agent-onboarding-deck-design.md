# [학습회] AI 에이전트 워크플로우 발표자료 — 컨셉 및 설계 (v2.3)

- 문서 목적: 30분 핵심형·60분 학습형·90분 확장형 발표자료의 컨셉, 논리 사슬, 슬라이드 구성, 제작 방식을 확정한다.
- 범위: 발표 설계까지. 실제 HTML 덱 제작은 별도 산출물(`ai-agent-onboarding.html`)
- 대상 독자: 발표자, 발표자료 제작자
- 상태: draft (v2.3 — 30/60/90분 삼중 트랙 + 확장 실습 설계)
- 최종 수정일: 2026-09-04
- 관련 문서: `standard-ai-workflow-intro.html`(기존 소개 덱, 보존), `../../ai-workflow/core/workflow_design_principles.md`

## 0. 확정된 전제

| 항목 | 값 |
|---|---|
| 형식 | **30분 핵심형**, **60분 학습형**, **90분 확장형** + Q&A (별도) |
| 청중 | **AI 코딩 도구 입문자 중심** |
| 액자 | 매일 기억을 잃는 신입 + **당신은 그 신입의 PL** |

| 산출물 | 단일 파일 HTML 마스터 덱 (1920×1080, 키보드 내비) + 30/60/90분 트랙 전환 |

### v1 → v2 변경 요지

- **뼈대 교체**: 첫날/둘째날/수습 달력 전개를 버리고, 발표자가 제시한 인과 사슬을 척추로.
  은유(기억 잃는 신입)는 액자로 유지 — 달력만 버리고 인물은 남긴다.
- **무게중심 이동**: "에이전트를 다루는 법"(도구 중심) → "당신이 어떤 리더가 되나"(사람 중심).
- **신규 축 4개 편입**: PL/위임·확인 2다이얼, 탐색 실패, 대안 대응표(메모리·위키·백로그),
  기록의 자연화 4단계.
- **분량 정리**: 누적 ~58장 → 44장.

### v2.1 보강 요지 (리뷰 제안 반영)

- **슬라이드 9**: 2×2 매트릭스 사분면에 4가지 리더 유형 별칭 명시 (방임형 / 마이크로매니저 / 묻지마 던지기 / 시스템적 리더).
- **슬라이드 35**: 자연화 3단계("안 하면 다음이 막힌다")에 실감형 1줄 예시(인계서 미발견 시 경고/작업 중단) 추가.
- **사례 3건 레이아웃 & 페이싱**: `case` 4비트 레이아웃(이렇게 됐다 → 왜 못 잡았나 → 무엇을 붙였나 → 당신 팀에서는) 고정 적용 및 6부 사례 B/C 페이싱용 시각적 대조(Before/After) 가이드 추가.
- **예상 질문(Q&A) 확장**: 개별 툴 메모리 기능과의 차이점, 완료 조건 작성 불가 시 업무 분해(Decomposition) 지침 등 2종 추가.

### v2.2 보강 요지

- **이중 트랙**: 38장 마스터에서 60분은 전량, 30분은 핵심 22장만 사용한다. 별도 덱을 복제하지 않는다.
- **학습목표 명시**: 참가자가 설명을 듣는 데서 끝나지 않고, 에이전트 업무의 완료 조건·범위 밖·검사와 최소 기록 구조를 직접 설계하도록 한다.
- **참여 장치**: 60분형에는 2분 미니 실습과 1분 회수 질문을 넣고, 30분형에는 90초 압축 실습을 유지한다.
- **페이싱 현실화**: 사례 A는 2분, 사례 B/C는 한 장에 통합해 3분. 전환 전용 슬라이드를 줄여 60분형에 5분 버퍼를 둔다.
- **표현 정밀화**: "에이전트는 되묻지 않는다" 같은 절대 표현을 "필요할 때 항상 되묻는다고 기대할 수 없다"는 운영 가정으로 바꾼다.
- **검사 강도 구분**: 모든 누락을 작업 중단으로 처리하지 않고 알림 → 확인 요청 → 차단의 세 단계로 설계한다.

### v2.3 보강 요지

- **90분 확장형 추가**: 기본 38장에 확장 슬라이드 `E1–E8`을 삽입해 총 46장으로 운영한다.
- **설명보다 연습을 확장**: 늘어난 30분은 개념 슬라이드를 더 쌓지 않고 진단·작성·토론·적용에 사용한다.
- **안정적인 식별자**: 기존 1–38 번호는 유지하고 확장 슬라이드는 별도 ID를 써 30분·60분 트랙의 번호와 링크가 흔들리지 않게 한다.
- **확장형 학습 산출물**: 참가자는 발표가 끝날 때 자기 업무의 위임 카드와 최소 워크플로우 캔버스를 한 장씩 가진다.

### 학습목표

발표가 끝나면 참가자는 다음을 할 수 있어야 한다.

1. 모호한 에이전트 업무를 **완료 조건·범위 밖·허용할 방법**으로 다시 쓸 수 있다.
2. 에이전트의 "없습니다"를 결론이 아니라 **검증할 가설**로 다룰 수 있다.
3. 자기 팀의 누수 하나를 골라 **남길 자리 1개 + 검사 1개**의 최소 워크플로우로 바꿀 수 있다.
4. 개인 도구의 메모리와 팀이 공유하는 **버전 관리 가능한 기록**을 구분할 수 있다.

발표의 커뮤니케이션 잡:

> 발표가 끝나면 AI 코딩 도구 입문자는 에이전트를 단순한 채팅 도구가 아니라
> 위임·기록·검사가 필요한 협업자로 보고, 자기 업무에 최소 워크플로우를 설계할 수 있다.

## 1. 발표의 척추 — 인과 사슬

모든 슬라이드는 이 사슬 위의 한 점이다. 사슬에서 떨어진 슬라이드는 넣지 않는다.

```
에이전트와 일한다 = 당신은 이미 PL이다
  → PL은 위임과 확인을 배워야 한다 (다이얼 2개)
    → 그런데 이 부하는 매일 기억을 잃는다
      → 기억이 없으니 매번 다시 찾는다
        → 찾기는 구조적으로 실패한다 (부재를 증명 못 함)
        → 못 찾은 결과를 "없다"고 취급하면 → 중복·충돌·중구난방
            → 대안: 메모리 / wiki·인덱스 / 작업 등록 / 규칙 한 벌
              → 이것들을 "잘 하자"로는 못 지킨다 → 워크플로우에 녹인다
                → 에이전트가 쓴 기록이 사실인가 → 검사로 확인한다
                  → 좋은 PL은 자기 없이 굴러가게 만든다 (결론)
```

### 은유 계약 (액자용 — 유지)

| 은유 | 실체 |
|---|---|
| 매일 아침 기억을 잃는 유능한 신입 | 세션 경계 — 컨텍스트 초기화 |
| 당신은 그 신입의 PL | 에이전트와 일하는 순간 전원이 리더 역할 |
| 업무 매뉴얼 | 진입점 문서 (매 세션 자동 read) |
| 매뉴얼 복사본이 갈라짐 | 규칙 사본 드리프트 → 단일 출처 + 생성 |
| 인수인계서 | 상태 파일 / 인계 노트 |
| 인계서가 오래되면 거짓말 | 기록 신선도 |
| 상사가 매번 안 봐도 되는 장치 | 자동 검사 |

### 은유가 깨지는 3지점 (결론부에서 발표자가 직접 부순다)

| 사람 신입 | AI 에이전트 | 그래서 |
|---|---|---|
| 경험이 쌓인다. 온보딩은 대개 한 번 | 세션·도구의 기억을 팀 공용 맥락으로 가정할 수 없다 | 온보딩을 **반복 가능하게 자동화**한다 |
| 못 찾으면 물어본다 | 필요할 때 항상 되묻는다고 기대할 수 없다 | 사각지대를 **문서로 명시**한다 |
| 신뢰가 쌓여 확인이 준다 | 세션을 넘어선 신뢰·맥락이 자동으로 공유된다고 볼 수 없다 | 확인을 사람에서 **장치로** 옮긴다 |

## 2. 핵심 논지 목록 (발표자 구술 반영분)

슬라이드 작성 시 이 문장들을 그대로 헤드라인/키 메시지로 쓴다.

**A. PL 프레임**
- 에이전트와 일하는 순간 우리는 모두 PL이 된다. 그런데 갑자기 PL이 될 수는 없다 —
  그래서 일하는 방식을 배워야 한다. (= 이 학습회의 존재 이유)
- 리더 유형: 던져주는 리더 vs 분해해 주는 리더. 정답은 분해량이 아니라
  **무엇을 고정하고 무엇을 풀어주는가** — 완료 조건·범위 밖·크기는 고정, 방법은 자유.
- 던지기가 에이전트에게 유독 위험한 이유: 사람은 막히면 묻지만 에이전트가
  **필요할 때 항상 되묻는다고 기대할 수 없고, 빈칸을 그럴듯하게 채울 수 있다.**
- 위임과 확인은 하나의 다이얼이 아니라 **두 개의 다이얼** — 위임은 방법에, 확인은
  결과에 건다. 둘 다 최대로 올릴 수 있다.
- 확인을 조이면 내가 병목이 된다. 리더의 성장 경로: 내가 다 한다 → 맡기고 내가
  확인한다 → **맡기고 확인이 저절로 걸린다.**
- 확인은 뒤가 아니라 앞으로: 완료 조건을 먼저 정하면 확인이 판단에서 **대조**로
  바뀌고, 대조는 기계에 넘길 수 있다.
- 위임의 크기 기준: **완료 조건을 한 문장으로 쓸 수 있는 크기.**

**B. 기억**
- 세션이 넘어가는 순간 작업 내용을 잊고, 이전 내역 확인에 큰 토큰·시간을 쓴다.
- 비용은 세 겹: ① 재탐색(토큰·시간 — 보이지만 가장 싸다) ② 재현성 없음(그날 뭘
  읽었는지에 따라 결론이 달라짐) ③ **기각한 선택지가 되살아남** — git은 무엇을
  했는지는 기억하지만 무엇을 하지 않기로 했는지는 기억하지 않는다.
- "처음에는 괜찮다"가 함정: 초기엔 전체를 훑을 수 있어 재탐색이 기억을 대체한다.
  커지면 어디를 볼지 자체가 이전 세션의 지식이다. 증상 전환: **느려진다 → 틀린다.**
  틀림은 보이지 않고, 늦은 도입은 증발한 결정을 소급 복원할 수 없다.

**C. 탐색**
- 전체를 훑을 수 없어 키워드 검색에 의존하는데, 한계가 많고 누락 가능성이 크다.
- 실패 4모드: ① 어휘 불일치(찾는 단어≠쓴 단어) ② **부재 증명 불가**(0건 = 없다? 틀린
  단어로 찾았다?) ③ 중요한 연결일수록 문자열이 없다 ④ 부분 표본에서 생기는 확신.
- 못 찾은 결과를 "없다"는 결론으로 취급하기 쉽다 → **여기서 중복 작업이 태어난다.** (B→D 를 잇는 다리)
- 처방 방향: 더 잘 찾게 하는 게 아니라 **찾지 않아도 되게** — 지도(진입점), 시작점
  (상태 파일), 사각지대 명시(인계 노트), 링크(wiki).
- 운영 규칙: 에이전트의 "없습니다"는 결론이 아니라 **가설**이다.

**D. 협업**
- 여러 사람이 각자 에이전트로 협업하면: 산출물 중구난방, 작업 내역 미공유,
  중복 작업, 충돌.
- 혼자일 때는 "내가 기억하면 되지"가 통하지만, 여럿이면 **아무의 머릿속에도 없는
  결정**이 생긴다 — 규모 문제가 아니라 종류가 다른 문제.
- **중복은 충돌보다 나쁘다**: 충돌은 git이 그 자리에서 알려주지만, 중복은 다른
  파일에 생겨 조용히 머지되고 한참 뒤 버그로 발견된다.

**E. 대안과 자연화**
- 대응표: 기억→메모리 관리 / 규모·탐색→wiki·인덱스 / 중복→**작업 등록(백로그, 사전
  공개)** / 중구난방→규칙 한 벌. (백로그는 발표자 구술의 빈칸을 채우는 항목 —
  메모리·위키는 사후 기록이라 중복을 못 막는다)
- 메모리와 위키는 다른 물건: 메모리는 시간축 **원장**(쌓인다), 위키는 주제축
  **파생물**(갱신된다). 위키는 메모리에서 나와야 한다 — 손으로 따로 유지하면 갈라진다.
- **오래된 지도는 없는 지도보다 나쁘다**: 검색은 틀려도 "못 찾았다"로 끝나지만 stale
  위키는 틀린 답을 자신 있게 준다. 생성하거나 신선도를 재거나, 대개 둘 다.
- 버리는 설계: "다 기록하자"는 읽기 비용으로 되돌아온다. 전량 기록 → 결정·근거만
  → 위키 승격 → 오래된 것 폐기.
- "잘 기록합시다"는 지켜지지 않는다(끝난 뒤의 일 = 동기 0). 자연화 4단계:
  ① 사람이 쓰지 않게(에이전트가 쓰고 사람은 확인) ② 별도 행위로 두지 않게(작업
  커밋에 동봉) ③ **안 하면 다음이 막히게**(기록 = 다음 세션의 입력) ④ 빠지면 알려주게.
- 자동 기록의 새 문제: **그 기록이 사실인가.** → 검증 파트로 가는 문.

**F. 검증**
- 검사는 "썼는가"가 아니라 "쓴 것이 사실인가"를 본다.
- 지켜지는 문장 vs 소망: 검사로 옮길 수 있는 문장만 규칙이다.
- 커밋을 막을 필요 없다 — 다음 세션 브리핑 첫 줄에 뜨면 충분. 혼내는 장치가 아니라
  잊은 것을 되돌려 놓는 장치.

## 3. 세 가지 발표 길이

하나의 46장 마스터를 유지한다. 기본 슬라이드는 1–38, 90분 전용 확장 슬라이드는
`E1–E8`이다. 60분형은 기본 38장 전량, 30분형은 `공통` 22장, 90분형은 46장 전량을
사용한다. HTML은 트랙 선택으로 슬라이드를 숨기며, 복제 파일은 만들지 않는다.

### 90분 확장형 — 설명 + 연습 + 자기 업무 적용

| 시간 | 부 | 제목 | 장수 | 학습 장치 |

#### 확장 활동 진행 원칙

- 타이머·진행 지시는 발표자 노트에만 두고, 화면에는 청중이 해야 할 질문과 산출물만 남긴다.
- 활동마다 전체 공유를 받지 않는다. `개인 작성 → 짝 비교 → 대표 1명`을 최대 두 번만 사용한다.
- E2의 위임 카드는 E6의 캔버스 입력이 되고, E6은 E8의 7일 실험으로 이어져야 한다.
- 시간이 밀리면 E3과 E7의 전체 공유를 생략한다. 개인 작성과 E8의 적용 선언은 유지한다.
- 참가자가 노트북을 쓰지 않는 환경을 위해 위임 카드와 캔버스는 종이 한 장에도 적을 수 있는 형식으로 설계한다.

#### 확장형 워크시트 규격

| 산출물 | 필드 | 완료 기준 |
|---|---|---|
| 위임 카드 | 업무 / 완료 조건 / 범위 밖 / 방법 자율성 / 결과 검사 | 다른 참가자가 읽고 “언제 끝인지” 한 문장으로 말할 수 있다 |
| 최소 워크플로우 캔버스 | 가장 자주 새는 것 / 남길 자리 / 다음 행동의 입력 / 검사 / 검사 강도 | 기록이 언제 쓰이고 다음에 어떻게 읽히며, 빠지거나 틀릴 때 무엇이 드러나는지 연결되어 있다 |
| 7일 실험 | 적용 업무 / 첫 실행일 / 확인 날짜 / 유지·수정·폐기 판단 | 발표 후 실제로 시험할 범위가 한 업무로 제한되어 있다 |

## 5. 사례 3건 — 출처와 각색

해시)는 슬라이드에 노출하지 않고** 은유 층으로 번역, 원본은 발표자 노트에만.

| # | 슬라이드 | 원본 (발표자 노트용) | 슬라이드 번역 |
|---|---|---|---|
| A | 30 (60·90분형) | task ID 정규식이 4곳에 복제, branch-scoped ID를 셋이 몰랐음. 규약 검사 부재로 장기 방치 | "매뉴얼을 네 부 복사해 줬더니 넷 다 달라졌고, 아무도 몰랐습니다" |
| B | 34 (공통) | state.json reader만 신규 경로로 이동, writer는 legacy에 잔류. "refreshed" 보고 지속 | "인계서를 다른 서랍에 넣어두고 '넣었습니다'라고 보고했습니다" |
| C | 34 (공통) | 미분류 status가 fallback으로 done 승격, 미완료 3건이 "최근 완료"로 집계 | "애매한 건 일단 완료로 적었습니다" |

전개는 4비트 고정: **이렇게 됐다 → 왜 못 잡았나 → 무엇을 붙였나 → 당신 팀에서는.** (슬라이드 레이아웃: 4분할 `case` 카드 고정 적용)

> [!TIP]
> **5부 사례 B/C (슬라이드 34) 페이싱 및 연출 가이드**
> 두 사례를 한 장의 **두 실패 / 한 원리** 구조로 묶는다. 왼쪽은 읽기·쓰기 위치 불일치,
> 오른쪽은 분류 실패가 완료로 승격된 장면을 Before/After로 보여주고, 하단에
> “썼는지가 아니라 실제 상태와 맞는가”를 한 줄로 회수한다. 총 3분을 넘기지 않는다.

### 예상 질문 대비 (발표자 노트)

- *"검색 도구가 좋아지면 해결되지 않나?"* — 부재 증명 불가는 성능이 아니라 성질의
  문제. 부분만 보고 판단하는 이상 0건의 의미는 확정되지 않는다.
- *"기록을 에이전트가 쓰면 그게 또 틀리지 않나?"* — 맞다, 그래서 5부가 있다.
  누락은 자동화로, 진실성은 검사로.
- *"개별 도구의 메모리/Rules 기능을 쓰면 다 해결되는 것 아닌가요?"* — 기능 유무보다
  세 가지를 확인한다. ① 팀이 같은 기록을 보는가 ② 변경 이력이 리뷰 가능한가
  ③ 작업 등록·검사와 연결되는가. 셋 중 빠진 부분은 저장소 워크플로우로 보완한다.
- *"완료 조건을 한 문장으로 쓸 수 없을 만큼 큰 작업은 어떻게 하나요?"* — 한 문장 완료 조건이 나올 때까지 업무를 하위 단위로 분해(Decomposition)해야 비로소 에이전트에 맡길 준비가 된 것이다.

## 6. 시각 설계

기존 소개 덱(warm espresso + amber)과 의도적으로 구별. 테마명 `saw-onboard`,
무드는 "첫 출근 / 종이와 잉크" — 차분하고 밝게.

| 토큰 | 값 | 용도 |
|---|---|---|
| `--bg-light` | `#FBFAF7` | 본문 |
| `--bg-dark` | `#16232E` | Section/Title/CTA |
| `--fg-on-light` | `#16232E` | 본문 텍스트 |
| `--accent` | `#0D7C6B` | 강조, 번호, ✓ |
| `--danger` | `#B4462E` | ✕, 실패 사례 |
| `--muted` | `#6B7A85` | 캡션 |
| `--rule` | `#E3E0D9` | 구분선 |

- 타이포: Pretendard Variable. h1 80 / h2 64 / body 32 / caption 20
- 레이아웃 프리미티브: `cols` / `steps` / `terminal` / `case`(사례 4비트) /
  `compare`(✕✓ 대조) / `matrix`(2×2, 슬라이드 8용) / `chain`(사슬 지도, 슬라이드 4·23용)
- 기술: 단일 HTML, 1920×1080 고정 캔버스 + viewport 스케일, 키보드 내비.
  각 슬라이드에 `data-track="common|full|extended"`를 두고 시작 화면 또는 URL 파라미터로
  30분/60분/90분 트랙을 선택한다. `extended`는 삽입 위치 메타데이터를 함께 가진다.
  발표 중 전환은 막아 현재/전체 장수 표기가 흔들리지 않게 한다.
- 폰트 CDN 의존 주의: 오프라인 발표장 대비, 시스템 폴백으로 레이아웃 안 깨지는지 빌드 후 확인
