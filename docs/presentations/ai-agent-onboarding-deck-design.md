## 1. 발표의 척추 — 인과 사슬

모든 슬라이드는 이 사슬 위의 한 점이다. 사슬에서 떨어진 슬라이드는 넣지 않는다.

```
에이전트와 일한다 = 당신은 이미 PL이다
  → PL은 위임과 확인을 배워야 한다 (다이얼 2개)
    → 그런데 이 부하는 매일 기억을 잃는다
      → 기억이 없으니 매번 다시 찾는다
        → 찾기는 구조적으로 실패한다 (부재를 증명 못 함)
          → 못 찾으면 "없다"고 결론낸다 → 중복·충돌·중구난방
            → 대안: 메모리 / wiki·인덱스 / 작업 등록 / 규칙 한 벌
              → 이것들을 "잘 하자"로는 못 지킨다 → 워크플로우에 녹인다
                → 에이전트가 쓴 기록이 사실인가 → 검사로 확인한다
                  → 좋은 PL은 자기 없이 굴러가게 만든다 (결론)
```

### 은유 계약 (액자용 — 유지)

| 은유 | 실체 |
|---|---|
| 매일 아침 기억을 잃는 유능한 신입 | 세션 경계 — 컨텍스트 초기화 |
| 당신은 그 신입의 PL | 에이전트와 일하는 순간 전원이 리더 역할 |
| 업무 매뉴얼 | 진입점 문서 (매 세션 자동 read) |
| 매뉴얼 복사본이 갈라짐 | 규칙 사본 드리프트 → 단일 출처 + 생성 |
| 인수인계서 | 상태 파일 / 인계 노트 |
| 인계서가 오래되면 거짓말 | 기록 신선도 |
| 상사가 매번 안 봐도 되는 장치 | 자동 검사 |

### 은유가 깨지는 3지점 (결론부에서 발표자가 직접 부순다)

| 사람 신입 | AI 에이전트 | 그래서 |
|---|---|---|
| 배운다. 온보딩은 한 번 | 안 배운다. 매 세션 처음부터 | 온보딩을 **자동화**한다 |
| 못 찾으면 물어본다 | 못 찾으면 "없다"고 결론낸다 | 사각지대를 **문서로 명시**한다 |
| 신뢰가 쌓여 확인이 준다 | 신뢰가 누적되지 않는다 | 확인을 사람에서 **장치로** 옮긴다 |

## 2. 핵심 논지 목록 (발표자 구술 반영분)

슬라이드 작성 시 이 문장들을 그대로 헤드라인/키 메시지로 쓴다.

**A. PL 프레임**
- 에이전트와 일하는 순간 우리는 모두 PL이 된다. 그런데 갑자기 PL이 될 수는 없다 —
  그래서 일하는 방식을 배워야 한다. (= 이 학습회의 존재 이유)
- 리더 유형: 던져주는 리더 vs 분해해 주는 리더. 정답은 분해량이 아니라
  **무엇을 고정하고 무엇을 풀어주는가** — 완료 조건·범위 밖·크기는 고정, 방법은 자유.
- 던지기가 에이전트에게 유독 위험한 이유: 사람은 막히면 묻지만 에이전트는
  **되묻지 않고 빈칸을 그럴듯하게 채운다.**
- 위임과 확인은 하나의 다이얼이 아니라 **두 개의 다이얼** — 위임은 방법에, 확인은
  결과에 건다. 둘 다 최대로 올릴 수 있다.
- 확인을 조이면 내가 병목이 된다. 리더의 성장 경로: 내가 다 한다 → 맡기고 내가
  확인한다 → **맡기고 확인이 저절로 걸린다.**
- 확인은 뒤가 아니라 앞으로: 완료 조건을 먼저 정하면 확인이 판단에서 **대조**로
  바뀌고, 대조는 기계에 넘길 수 있다.
- 위임의 크기 기준: **완료 조건을 한 문장으로 쓸 수 있는 크기.**

**B. 기억**
- 세션이 넘어가는 순간 작업 내용을 잊고, 이전 내역 확인에 큰 토큰·시간을 쓴다.
- 비용은 세 겹: ① 재탐색(토큰·시간 — 보이지만 가장 싸다) ② 재현성 없음(그날 뭘
  읽었는지에 따라 결론이 달라짐) ③ **기각한 선택지가 되살아남** — git은 무엇을
  했는지는 기억하지만 무엇을 하지 않기로 했는지는 기억하지 않는다.
- "처음에는 괜찮다"가 함정: 초기엔 전체를 훑을 수 있어 재탐색이 기억을 대체한다.
  커지면 어디를 볼지 자체가 이전 세션의 지식이다. 증상 전환: **느려진다 → 틀린다.**
  틀림은 보이지 않고, 늦은 도입은 증발한 결정을 소급 복원할 수 없다.

**C. 탐색**
- 전체를 훑을 수 없어 키워드 검색에 의존하는데, 한계가 많고 누락 가능성이 크다.
- 실패 4모드: ① 어휘 불일치(찾는 단어≠쓴 단어) ② **부재 증명 불가**(0건 = 없다? 틀린
  단어로 찾았다?) ③ 중요한 연결일수록 문자열이 없다 ④ 부분 표본에서 생기는 확신.
- 못 찾으면 "없다"고 결론낸다 → **여기서 중복 작업이 태어난다.** (B→D 를 잇는 다리)
- 처방 방향: 더 잘 찾게 하는 게 아니라 **찾지 않아도 되게** — 지도(진입점), 시작점
  (상태 파일), 사각지대 명시(인계 노트), 링크(wiki).
- 운영 규칙: 에이전트의 "없습니다"는 결론이 아니라 **가설**이다.

**D. 협업**
- 여러 사람이 각자 에이전트로 협업하면: 산출물 중구난방, 작업 내역 미공유,
  중복 작업, 충돌.
- 혼자일 때는 "내가 기억하면 되지"가 통하지만, 여럿이면 **아무의 머릿속에도 없는
  결정**이 생긴다 — 규모 문제가 아니라 종류가 다른 문제.
- **중복은 충돌보다 나쁘다**: 충돌은 git이 그 자리에서 알려주지만, 중복은 다른
  파일에 생겨 조용히 머지되고 한참 뒤 버그로 발견된다.

**E. 대안과 자연화**
- 대응표: 기억→메모리 관리 / 규모·탐색→wiki·인덱스 / 중복→**작업 등록(백로그, 사전
  공개)** / 중구난방→규칙 한 벌. (백로그는 발표자 구술의 빈칸을 채우는 항목 —
  메모리·위키는 사후 기록이라 중복을 못 막는다)
- 메모리와 위키는 다른 물건: 메모리는 시간축 **원장**(쌓인다), 위키는 주제축
  **파생물**(갱신된다). 위키는 메모리에서 나와야 한다 — 손으로 따로 유지하면 갈라진다.
- **오래된 지도는 없는 지도보다 나쁘다**: 검색은 틀려도 "못 찾았다"로 끝나지만 stale
  위키는 틀린 답을 자신 있게 준다. 생성하거나 신선도를 재거나, 대개 둘 다.
- 버리는 설계: "다 기록하자"는 읽기 비용으로 되돌아온다. 전량 기록 → 결정·근거만
  → 위키 승격 → 오래된 것 폐기.
- "잘 기록합시다"는 지켜지지 않는다(끝난 뒤의 일 = 동기 0). 자연화 4단계:
  ① 사람이 쓰지 않게(에이전트가 쓰고 사람은 확인) ② 별도 행위로 두지 않게(작업
  커밋에 동봉) ③ **안 하면 다음이 막히게**(기록 = 다음 세션의 입력) ④ 빠지면 알려주게.
- 자동 기록의 새 문제: **그 기록이 사실인가.** → 검증 파트로 가는 문.

**F. 검증**
- 검사는 "썼는가"가 아니라 "쓴 것이 사실인가"를 본다.
- 지켜지는 문장 vs 소망: 검사로 옮길 수 있는 문장만 규칙이다.
- 커밋을 막을 필요 없다 — 다음 세션 브리핑 첫 줄에 뜨면 충분. 혼내는 장치가 아니라
  잊은 것을 되돌려 놓는 장치.

## 5. 사례 3건 — 출처와 각색

셋 다 이 저장소에서 실제 겪은 일. **입문자 대상이므로 내부 구조(파일명·함수명·커밋
해시)는 슬라이드에 노출하지 않고** 은유 층으로 번역, 원본은 발표자 노트에만.

| # | 슬라이드 | 원본 (발표자 노트용) | 슬라이드 번역 |
|---|---|---|---|
| A | 33 | task ID 정규식이 4곳에 복제, branch-scoped ID를 셋이 몰랐음. 규약 검사 부재로 장기 방치 | "매뉴얼을 네 부 복사해 줬더니 넷 다 달라졌고, 아무도 몰랐습니다" |
| B | 38 | state.json reader만 신규 경로로 이동, writer는 legacy에 잔류. "refreshed" 보고 지속 | "인계서를 다른 서랍에 넣어두고 '넣었습니다'라고 보고했습니다" |
| C | 39 | 미분류 status가 fallback으로 done 승격, 미완료 3건이 "최근 완료"로 집계 | "애매한 건 일단 완료로 적었습니다" |

전개는 4비트 고정: **이렇게 됐다 → 왜 못 잡았나 → 무엇을 붙였나 → 당신 팀에서는.**

### 예상 질문 대비 (발표자 노트)

- *"검색 도구가 좋아지면 해결되지 않나?"* — 부재 증명 불가는 성능이 아니라 성질의
  문제. 부분만 보고 판단하는 이상 0건의 의미는 확정되지 않는다.
- *"기록을 에이전트가 쓰면 그게 또 틀리지 않나?"* — 맞다, 그래서 6부가 있다.
  누락은 자동화로, 진실성은 검사로.

## 6. 시각 설계

기존 소개 덱(warm espresso + amber)과 의도적으로 구별. 테마명 `saw-onboard`,
무드는 "첫 출근 / 종이와 잉크" — 차분하고 밝게.

| 토큰 | 값 | 용도 |
|---|---|---|
| `--bg-light` | `#FBFAF7` | 본문 |
| `--bg-dark` | `#16232E` | Section/Title/CTA |
| `--fg-on-light` | `#16232E` | 본문 텍스트 |
| `--accent` | `#0D7C6B` | 강조, 번호, ✓ |
| `--danger` | `#B4462E` | ✕, 실패 사례 |
| `--muted` | `#6B7A85` | 캡션 |
| `--rule` | `#E3E0D9` | 구분선 |

- 타이포: Pretendard Variable. h1 80 / h2 64 / body 32 / caption 20
- 레이아웃 프리미티브: `cols` / `steps` / `terminal` / `case`(사례 4비트) /
  `compare`(✕✓ 대조) / `matrix`(2×2, 슬라이드 9용) / `chain`(사슬 지도, 슬라이드 5·26용)
- 기술: 단일 HTML, 1920×1080 고정 캔버스 + viewport 스케일, 키보드 내비
- 폰트 CDN 의존 주의: 오프라인 발표장 대비, 시스템 폴백으로 레이아웃 안 깨지는지 빌드 후 확인
