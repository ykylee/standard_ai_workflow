# Hub PostgreSQL backend and SQLite transfer specification

- Purpose: define the database contract shared by the Go 3.x hub and Python 1.x hub.
- Scope: runtime selection, schema version upgrades, and a one-time copy of an existing SQLite hub database into PostgreSQL.
- Audience: hub operators and maintainers.
- Status: design
- Updated: 2026-11-23
- Related: [`hub_spec.md`](hub_spec.md), [`hub_go_spec.md`](hub_go_spec.md), [`docs/HUB_OPERATIONS.md`](../../docs/HUB_OPERATIONS.md)

## 1. Support contract

- SQLite remains the default database for development, tests, local use, and backward-compatible installs.
- PostgreSQL is an optional server backend for both `hub-go` and the Python hub. Both runtimes must read and write the same schema and schema-version contract.
- A database target is either a filesystem path (SQLite) or a PostgreSQL URL (`postgresql://` or `postgres://`). Do not infer PostgreSQL from a filename.
- The runtime opens the selected backend through one database boundary. Business and HTTP behavior must not branch on the backend.
- PostgreSQL migrations run automatically on hub startup/connect, under a PostgreSQL advisory lock. Each schema version and its `meta.schema_version` update commit in one transaction. A database newer than the runtime is rejected without writes.
- SQLite tests remain the required portable test baseline. PostgreSQL integration checks use an isolated disposable database when a server is available; they never use an operator's configured database.

## 2. Schema and SQL compatibility

- SQLite and PostgreSQL implement the same logical schema and monotonically increasing migration versions. Migration SQL is authored for both dialects and reviewed together; SQLite-only PRAGMA/catalog statements stay inside the SQLite adapter.
- Portable query code uses one placeholder abstraction, conflict-safe insert/update semantics, and explicit generated identifier retrieval. PostgreSQL uses `RETURNING`; code must not rely on SQLite `lastrowid` or `INSERT OR IGNORE`.
- The Python project-bundle transfer path discovers tables and columns through the selected backend catalog and imports in foreign-key order. Existing `rowid` tie-break ordering is mapped to PostgreSQL `ctid` only for query-local ordering.
- PostgreSQL uses `BIGINT GENERATED BY DEFAULT AS IDENTITY` for the event sequence. Existing explicit sequence values are preserved during copy, then the identity sequence is advanced beyond the maximum copied value.
- Booleans use logical true/false values at the adapter boundary; timestamps remain the existing normalized ISO-8601 text representation during this compatibility phase.
- Migrations are append-only. A failed migration rolls back its DDL and version marker. The SQLite online-backup behavior remains SQLite-only; PostgreSQL operational backups are owned by the server operator (for example, `pg_dump` or managed snapshots).

## 3. Startup and connection behavior

- `--db <path>` and the existing SQLite environment setting continue to select SQLite.
- `--db <postgres-url>` and the corresponding documented environment setting select PostgreSQL. URL credentials must never be written to logs, error details, task output, or process diagnostics.
- Startup verifies the connection, acquires a migration lock, reads the current version, applies all missing versions atomically, and releases the lock. Migration failures fail startup; the process must not silently fall back to SQLite.
- Concurrent instances serialize schema upgrades. A lock timeout or connection failure is a clear startup error and changes no schema version.
- Health/readiness reports the selected backend kind but never exposes the DSN.

## 4. SQLite-to-PostgreSQL data copy

Schema upgrades happen automatically at PostgreSQL startup. Copying an existing SQLite database is a separate explicit operator action so merely configuring a PostgreSQL URL cannot unexpectedly duplicate or overwrite data.

The CLI contract will be `hub migrate --from-sqlite <path> --to-postgres <url>` (equivalent entry point for Go and Python). It is an import operation, not a bidirectional or continuous replication feature.

1. Open SQLite read-only and take a consistent SQLite snapshot (online backup or a read transaction that holds a stable snapshot). Never modify, rename, or delete the source.
2. Require an empty PostgreSQL target, except for the runtime-created schema and migration metadata. Refuse any non-empty application table before copying.
3. Copy tables in foreign-key dependency order within one PostgreSQL transaction, preserving primary keys, nullable values, booleans, text, JSON text, and explicit event sequence values. Defer/check constraints as supported by PostgreSQL.
4. Compare every application table's source and destination row count and a deterministic digest over ordered primary-key rows. Any mismatch aborts and rolls back the complete PostgreSQL import.
5. Advance generated identity sequences, then commit. Re-run against a populated target fails closed; there is no implicit merge, truncate, or overwrite mode.
6. Return a summary of table counts and digests without row contents or secrets. The SQLite source remains available for rollback and operator comparison.

For a large database, the first implementation may stream bounded batches while retaining one target transaction. The digest definition and table ordering must remain deterministic across runtimes.

## 5. Failure and recovery

- PostgreSQL connection, schema upgrade, and copy errors fail visibly and do not select a different database.
- A failed schema upgrade is transactionally rolled back. Operators retain their normal PostgreSQL backup/restore procedure for failures outside a single transaction (for example, infrastructure loss).
- A failed copy leaves the PostgreSQL target with no imported application rows. If transaction rollback cannot be confirmed, the CLI reports that state as indeterminate and refuses automatic cleanup.
- The source SQLite database is read-only throughout export and is the rollback source until the operator has validated production behavior.
- Logs may include backend type, migration version, table name, and row counts, but must redact URL username/password and never log token or project data.

## 6. Verification and rollout

- Keep SQLite unit and end-to-end tests as the default suite and run the same hub behavior tests against SQLite in both runtimes.
- Add backend-independent migration/copy tests with tiny temporary databases, including empty data, nullable fields, foreign keys, Unicode, explicit event sequence, mismatch rollback, rerun refusal, and concurrent startup migration.
- Run an isolated PostgreSQL smoke in both runtimes when PostgreSQL is available: fresh schema, upgrade from an older schema, hub CRUD, copy, digest/row-count match, identity continuation, and failure rollback.
- Rollout sequence: take a SQLite backup; import to a disposable PostgreSQL database; compare import summary; exercise Go and Python against that database; retain SQLite unchanged until the operator explicitly switches the production DSN.

## 7. Decisions

- Runtime scope: Go and Python hubs.
- SQLite data is copied into PostgreSQL; source is retained and never modified.
- Schema migration is automatic on PostgreSQL startup; bulk data copy is explicit.
- Tests continue to use SQLite by default; PostgreSQL tests are isolated integration checks.
